# v342 · trade_decisions 写入口径统一

> 2026-11-15 · 分支 `v342-judgment-grain` · 纯增量（不删列、不改老数据、调用方签名保留）

## 一、原来乱在哪

`trade_decisions` 有三个写入点，同一个表三种口径：

| 写入点 | 写 status | score/confidence | 事前权重 | 备注 |
|---|---|---|---|---|
| `trade_decisions.log_decision` | ✗ | ✗ | ✓ | 主力打点路径 |
| `decision_engine.propose_one` | ✓ | `algo_score` 直接当 confidence 用 | ✗ | 方向分被当成 0-100 置信度 |
| `bridge_server./api/decision/record` | ✓ | 只塞进 `context_json`，注释写明「不再落库」 | ✗ | 两个写 `status` 的路径中之一 |

直接后果：

1. 胜率 / 闸门拒绝率 / 结算率无法按来源分层统计 —— 同名 `confidence` 在不同行的含义不同。
2. **`status` 列从来没被迁移建过**（只在两条 INSERT 里出现）。全新库跑 `decision_engine` 或 bridge 会直接 `OperationalError: no such column: status`。
3. 只有一条路径写「事前权重」（验收 #2 只认 `trigger_kind='insert'`），另两条永远缺。

## 二、改了什么

### 1. `db.py` 迁移补列（幂等，全部可空）
`status / decision_source / score / confidence / structure_score / confidence_detail`

不建表、不回填、不改老行。老读数逻辑照旧可跑。

### 2. `decision_writer.py`（新增，唯一写入口）
```
write_decision(conn, *, asset, intended_action, ..., source, score, confidence,
               structure_score, confidence_detail, status, persist_signal_weight)
```
规则：
- 一个 INSERT，列集合固定；缺的写 NULL，不猜值。
- 口径落成显式列，不再依赖 `context_json` 里的自由字段。
- `entry_price` 缺失 → `db.resolve_entry_price` 回溯；查不到留 NULL。
- 落库后统一写事前权重（`trigger_kind='insert'`，`now_ts=decision_ts`）。
- 越界夹住：`score ∈ [-1,1]`、`confidence ∈ [0,100]`、`structure_score ∈ [-2,2]`。

### 3. 三个调用点改为调用它
| 写入点 | `decision_source` | 口径修正 |
|---|---|---|
| `log_decision` | `log_decision` | 签名/返回值不变，多写 status 与来源 |
| `decision_engine` | `algo_move` | `algo_score` 落到 `score`（方向分），`confidence` 留 NULL |
| `bridge_server` | `bridge_api` | `score/confidence` 同时落列；`context_json` 里原来那份保留，老读者不受影响 |

## 三、验证

```
python -m pytest tests/test_v342_decision_writer.py -q          → 9 passed
python -m pytest tests/test_v336_optimizations.py tests/test_policy_engine_regression.py \
                 tests/test_v3213_fixes.py ... -q                → 90 passed
```

新增 9 条用例钉死：
- 三条路径列集合一致、`decision_source` 各不相同、`status='open'`
- `algo_score` 不再冒充 `confidence`（NULL 而不是错值）
- bridge 的 `score/confidence` 真的落列，`context_json` 仍可读
- `log_decision` 老签名兼容、返回 id
- 无行情表时 `entry_price` 留 NULL（不猜价）
- 越界值被夹住
- 空 asset 抛 `ValueError`

> 本机跑全量前需补 `requests / aiosqlite / pydantic / fastapi / python-multipart / yfinance`（系统 python 原本一个都没装），与本改动无关。

## 四、不变量（这次刻意没动）

- 三条路径的**业务判定**一个字没改：动作、拒绝原因、回链新闻、结算口径全部照旧。
- 老数据不迁移、不回填；`context_json` 结构不变。
- `log_decision` 的事前权重时机不变（仍是落库那一刻，`now_ts=decision_ts`）。

## 五、遗留

| 项 | 说明 |
|---|---|
| 存量行回填 | `decision_source` 对历史行仍为 NULL，可按 `guard`/`decision_type` 推断，但属于猜测，未做 |
| `status` 存量 | 历史行没有 status，`settle` 逻辑需要有 NULL 兼容（已在读侧保持宽松） |
| 三条路径的候选去重 | `decision_engine` 有 `_is_already_decided`，其他两条没有 → 仍可能重复落库 |
