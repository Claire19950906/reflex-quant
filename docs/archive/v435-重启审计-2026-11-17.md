# v435 · 重启审计：抓「谁在杀引擎」

> 日期：2026-11-17 20:05–20:12　｜　承接：v434（熔断干等可视性）、v424（批末 spool）

## 一、为什么做这件事

`~/.trident/log/engine.out.log` 里，今天引擎被外部 `SIGTERM` 的时点：

```
17:38:37  17:42:13  17:44:13  17:45:03  17:51:37
18:00:27  18:08:06  18:17:50  18:26:52  18:52:50
19:14:53  ← 本轮为让 v434 生效的一次主动重启
19:21:08
```

`ops-audit` 同日告警原文：

> [严重] 引擎被反复重启：近 1 小时 SIGTERM × 9
> → 批次落库在批末一次性提交，重启会整批作废；先停掉外部 kickstart

但排查结果是：**仓库里根本没有动手的人**。

| 排查项 | 结果 |
|---|---|
| 仓库内 `kickstart` / `bootout` 调用点（排除 watchdog 自身） | 无 |
| `master_api.py` 是否有重启接口 | 无（只有 `/`、`/health`、`/signal`、`/backtest`、`/batch`） |
| `~/.trident/log/restart_calls.log`（restart_backend.sh 自带调用链记录） | 无相关记录 |
| crontab / LaunchAgents 里带 `kickstart` 的条目 | 无 |
| `~/.trident/watchdog.sh` | 只重启 api / bridge，不动 engine |

也就是说：我们只有「被杀」的视角，没有「谁动手」的视角。v424 的 spool 只能把**已经分析完**
的结果捞回来，无法回答「这一批是谁打断的、打断时引擎在做什么」。本轮的审计就补这个视角。

## 二、改法

### 1. 进程表采样（`backend/scripts/restart_audit.py`）

每 0.1 秒采一次全量进程表：

```bash
ps -axo pid=,ppid=,uid=,tty=,command=
```

命中下列任一模式即进入候选：

| 模式 | 说明 |
|---|---|
| `launchctl kickstart` / `launchctl bootout` | launchd 侧重启/卸载（最常见） |
| `restart_backend.sh` | 项目自带的重启脚本 |
| `kill … engine.py` / `pkill -f engine.py` / `killall engine` | 直接杀进程 |

**两个必须绕开的坑**

1. **不能只按文本匹配**。`bash -c "...launchctl kickstart..."` 这种包装层、
   以及任何正文里提到该命令的脚本（包括审计脚本自己），命令行里都含这段字面量。
   → 处理：命中后进「候选」，**下一个采样周期确认 pid 已消失**才落盘。真正的杀手是
   短命进程（几十毫秒），长驻 shell 会被这一道剔除；命令行含 `restart_audit` 的
   一律直接跳过。
3. **长命令行直接排除**（实测 20:11:25 的误报）：真实的调用命令很短（直接调用约 50 字符，
   套一层 `bash -c "cd … && … && launchctl …"` 也就一百出头）；而「在 heredoc 里写文档／
   写 CHANGELOG」这类命令动辄几百上千字符，正文里提到 kickstart 纯属巧合。
   → 处理：命令行超过 220 字符一律不匹配。
2. **父子链必须一起记**。只记到 `launchctl` 说明不了是谁调用的。
   → 处理：沿 `ppid` 往上走最多 5 层，遇 `launchd(1)` 或成环即停，
   落盘成 `cmd ← cmd ← …` 的链条。

落盘位置：`backend/runtime/restart_audit.jsonl`，一行一条：

```json
{"ts":1794917299.339,"ts_str":"2026-11-17 20:08:19","pid":"52492","uid":"501",
 "tty":"??","cmd":"/bin/bash -c exec -a \"launchctl kickstart -k …\" sleep 0.05",
 "ancestry":["52492 /bin/bash -c …","52473 /bin/bash --noprofile …","29852 …AgentInfraService","<launchd pid=1>"]}
```

### 2. 引擎侧记账（`src_python/engine.py`）

SIGTERM 钩子里追加一条：

```json
{"role":"engine_sigterm","ts":…,"ts_str":"…","pid":…,"step":"analyze"}
```

- 只读 `runtime/ai_worker_progress.json`（小文件），**不碰数据库**，避免在信号上下文阻塞；
- 整段包在 `try/except`：记账失败绝不影响退出；
- **不改退出语义**（仍然立刻退出）。当前这一轮只要「看清」，不要「改变行为」。

两份记录按 `ts` 对照，就能回答：**每次重启是谁动手的、动手时引擎卡在哪一步。**

## 三、验收

| 指标 | 命令 | 期望 |
|---|---|---|
| 审计进程在跑 | `ps -ef \| grep restart_audit` | 有 pid |
| 能抓到短命调用方 | `cat backend/runtime/restart_audit.jsonl` | 每次被杀前后出现一条，含完整 ancestry |
| 引擎侧记账 | 同上，`role=engine_sigterm` | 与 SIGTERM 日志一一对应 |
| 不误伤长驻进程 | 观察 jsonl | 没有把 shell / 编辑器 / 采集脚本记进去 |

单测：`python3 -m pytest tests/test_v435_restart_audit.py -q` → **7 passed**
（连 v434 两组共 **23 passed**）。

端到端自检（造一个 50ms 的假调用）：

```bash
bash -c 'exec -a "launchctl kickstart -k gui/501/com.trident.fake" sleep 0.05'
```

实测被抓到，ancestry 为 `bash -c … ← agent_infra bash ← AgentInfraService ← launchd`。

## 四、当前状态

- 审计进程：后台运行（pid 54698，`--duration 14400`，限时 4 小时），日志 `~/.trident/log/restart_audit.out`，
  jsonl 在 `backend/runtime/restart_audit.jsonl`。
- 引擎侧记账：**下一次引擎启动才生效**（当前进程更早启动）。
- 采样间隔 0.1s 意味着单个 50ms 的调用约 50% 命中；按当前每几十分钟被杀的频率，
  运行 4 小时基本必中。

## 五、未做 / 边界

- **没有加自动「重启频率闸」**：限流会把调用方藏起来，先把人找出来更划算；
  真要限流，应放在调用方那一侧而不是引擎里。
- 采样法对被 `bootout` 后立刻消失、又恰好落在两次采样之间的调用**可能漏记**；
  漏记时仍能从 `engine_sigterm` 记录看到「被杀时刻 + step」，只是缺调用方。
- 审计只覆盖「命令行里能看到的东西」：如果有进程用 API（`launchctl` 已被 SIP 保护，
  不存在第三方拦截）或者别的方式杀进程，需要换手段（sudo + EndPointSecurity 级工具）。
