## 二、本轮修了什么

### 1. 置信度占位 0 → NULL（违反铁律 4 的真缺陷）

根因链：`decision_guard.evaluate_decision` → `evidence.unified_confidence`

```
confidence = |final_score| × 100 × 显著性 × 覆盖度因子 × 风险 × 佐证
```

降级路径里 `final_score = 0` 且 `coverage = 0` → 公式输出 `0.0`。
**这在数学上是"没有证据"，在库里却被当成"置信度很低"**：
447/494 条被算进"低置信度决策"，漏斗日报据此说"闸门依赖 evidence_confidence，
而 447 条是默认值 0"——把一个缺失值报成了分数。

修法（新模块 `confidence_availability.py`，纯函数零依赖）：

- `coverage > 0` 才算"算过"；否则 `is_unavailable = True`
- 落库：没算过 → `NULL`；算过且真为 0 → 保留 `0.0`（不许把真结论洗成缺失）
- 闸门原因：没算过 → `无可证据（coverage=0，置信度不适用）：<降级原因>`；
  算过但低分 → 保留「统一置信度 X 低于闸门 Y」

### 2. 反思语料两类混算（测量口径）

`trade_reflections_v2` 里 82% 是 `c_technical_reflections.py` 按行情断档批量写的
`data_feed_timeout`（hit 全 0）。它们与"模型想错了"无关，却和 A/B 推理错因共用分母，
于是"反思命中率"永远趋 0，且看起来像"84% 的错误都是技术错误"。

修法：`/api/v237/reflection-dimension-stats` 复用 v398 的 `insight_pool`
（A/B = 交易错因、C = 技术故障），新增 `n_reasoning` / `n_infra` /
`hit_rate_reasoning` / `hit_rate_infra`，每条样本带 `sample_class`。
另：`c_technical_reflections.py` 的 `confidence_at_time` 由占位 `0.0` 改 `NULL`。

### 3. 真 bug：线程错峰包装器自递归（`api_server.py`）

```python
_ORIG_THREAD_START = threading.Thread.start   # 模块级无条件赋值
...
threading.Thread.start = _staggered_thread_start
```

模块被导入两次时（脚本方式 `api_server` + 包方式 `src_python.api_server`，
pytest 与 uvicorn reload 都会发生），第二次把**已包装的函数**当成原始函数，
`start()` 调自己 → `RecursionError: maximum recursion depth exceeded`。

影响面：任何二次导入的进程建不了线程（后台任务、ThreadPoolExecutor 全部炸）。
实测 `tests/test_security_p1_fixes.py`：5 failed + 5 errors。
修法：包装器打 `_trident_staggered` 标记，只包一次 → 该文件 **36 passed**。

## 四、明确没做的（及原因）

1. **没动生产 DB**。`backfill_confidence_placeholder.py` 只预演（394 条可改，
   `server_fallback` 29 条刻意保留）。落库需要你按项目惯例先备份再 `--commit` ——
   AGENTS.md 铁律 3 明确"不动生产 DB 文件"，我不越这条线。
2. **没拆 `api_server.py`**（20,594 行 / 352 路由）。你已经开了第一刀（`routers/meta.py`，
   带切片规矩），这是多轮工作，不是一次提交能完成的；本轮只保证它不再因递归而炸。
3. **没补样本**。有效样本 1 笔这件事，代码改不出来：需要放低门槛的影子账本跑 2–4 周，
   攒到 ≥60 笔已结算样本，才谈得上"反思有没有用"。建议的下一个实验：
   同一批新闻，带反思闸门 / 不带反思闸门各跑一条影子账本，比较扣费后胜率。
4. **没改任何阈值**（闸门 15/20、过度分析惩罚、池内品种）。按铁律 6 属产品决策，不夹带。
