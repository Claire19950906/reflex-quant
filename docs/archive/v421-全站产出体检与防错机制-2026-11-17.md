## 1. 最严重的一件：整个 backend 的 import 被改成 `from signals import ...`

### 现象
某个批量改写脚本把

```python
import asyncio / import json / import db / import urllib.request
```

改成了

```python
from signals import asyncio / json / db / urllib.request
```

### 为什么是灾难
`signals/` 只是**信号/决策领域包**（只有 `decision_*`、`signal_*` 共 14 个模块），
拿不出 `os / json / db / urllib` 这些名字。于是：

- `from signals import urllib.request` —— **纯语法错误**，文件根本编译不过；
- `python3 -c "import api_server"` 直接 `SyntaxError`；
- 线上服务没死，只因为它 08:27 就把旧代码载进了内存 —— **任何一次重启，全站起不来**。

### 证据
| 证据 | 内容 |
|---|---|
| `git show HEAD:backend/src_python/api_server.py` | 原版是正常的 `import asyncio` |
| 工作区同一位置 | `from signals import asyncio` |
| 规模 | 1120 个 `.py` / 6827 处错误导入 |
| 直接后果 | `ImportError: cannot import name 'os' from 'signals'`；`SyntaxError` |

### 谁改的
不是本会话：`ps` 里能看到另一个并发会话在反复跑 `/tmp/deshim2.py signals` 这类 codemod，
每跑一轮全仓又被改回去一次（我修好一次，40 秒后又回涨到 6800+ 处）。
**这也说明"一次修完"不够，必须有能重复执行的修复 + 会自动变红的断言。**

### 修法（可重复执行）
```bash
python3 backend/scripts/fix_signals_imports.py --check   # 只报，退出码 1 = 有污染
python3 backend/scripts/fix_signals_imports.py --apply   # 还原成 import X
```
判定不是猜的：`signals/` 包里真实存在的模块名保留 `from signals import X`，
其余一律还原成 `import X`（与 HEAD 语义完全一致）；逗号多模块、`as` 别名、行尾注释一并还原。

实测：`--check` 报 1120 文件 / 6827 处 → `--apply` → 复检 0 处 → 全仓 `compileall` 通过 → `openapi` 生成 383 条路径。

## 4. 为什么"检查过却出错"——四个结构性根因

1. **断言在代码里，不在跑起来的产物上。**
   函数被搬到 `routers/` 之后，`api_server` 里的老调用点不会报错，直到有人第一次点那个接口。
   静态检查能抓到（`undefined name`），前提是有人跑。
2. **异常被吞，0 被当成"没问题"。**
   `/metrics` 的 `json` 没导入 → `except Exception: pass` → 恒 0；
   `pipeline_guard._count()` 吞 `OperationalError` 返回 0 → "结构化缺失 0% → ok"。
   **守卫自己变成"看起来检查了、其实没查"**，比不查更坏。
3. **一个字段装两种事实。**
   `FILTERED` 同时表示"判为噪音"和"超龄归档"；`evidence_confidence=0` 同时表示"算过没信心"和"根本没算"。
   口径一混，看板就开始说谎（v419/v420 已拆）。
4. **工具本身会说谎。**
   并发 8 线程探活 → 把自己造成的线程池饱和当成"8 个接口 25s 超时"；
   线上扫描时服务被外部重启 → 把"服务没了"记成"210 个 5xx"。
   这两次都是**方法论**出错，不是代码出错。

## 5. 规避规则（照这五条做就不会再犯）

1. **禁止 `except Exception: pass`**。要么 `log`，要么把结果标成 `unknown`；不许悄悄变成 0 / ok。
2. **守卫算不出来必须报 unknown**，不许报 ok（"不知道"≠"没问题"）。
3. **任何函数搬家/改名，必须留一条 import 冒烟测试**（本轮的 `/api/news/report` 就是漏了这条）。
4. **探活一律串行**；超时、不可达、5xx 三类分开记（本工具已这么分）。
5. **改完必跑** `python3 backend/scripts/site_audit.py --static --inproc`，红了的先修再交付。

## 9. 现在线上为什么是 0 信号（刚实测，这就是你第 2 条质疑的真身）

| 读数（`backend/reports/health/quota_state.json`，14:32 快照） | 值 |
|---|---|
| 近 15 分钟 LLM 调用 | 32 次 |
| 其中 429（被限流） | **21 次（65.6%）** |
| 通道状态 | `llm_channels_state: error` |
| 待分析队列 | 323 条 |
| 近 30 分钟决策 | **0 条** |
| 最后一条决策 | 13:14:39（已断 ~80 分钟） |

引擎日志同一时刻的原文：

```
[gate-replay] 跳过（通道不可用）：all 1 gate channels unavailable
[AI] ⚠️ 门卫通道只有 1 条、独立 key 1 个 (aliases=['minimax-gate']) → 与主分析共用配额；
     配额打满时门卫会整体 429。可在 .env 配 GATE_ALT_{BASE_URL,API_KEY,MODEL} 接一个独立端点。
```

**因果链**：门卫（判"这条新闻值不值得分析"的那一步）只有 1 条通道，且和主分析**共用同一个 key** →
配额被打满 → 门卫整体 429 → 门卫不可用 → 新闻全部冻结（`gate_unavailable=1`，实测 PENDING 里 324 条）
→ 认领拿不到可分析的行 → 决策 0 条 → 你看到"全网监控却没有交易信号"。

**这不是"没信号可抓"**，是**单点把整条产线掐断了**。同时也是结构性缺陷：
`all 1 gate channels` —— 一条通道挂了就等于全站停摆。

可选的修法（都需要你拍一个）：
1. 在 `.env` 配 `GATE_ALT_BASE_URL / GATE_ALT_API_KEY / GATE_ALT_MODEL`，给门卫一个**独立配额**的端点（系统已经预留了这个口子）；
2. 或者把门卫与主分析的并发/频率错开（代价是判定变慢，但不会再整条停）；
3. 或者换一个配额更宽的同族 key（现状是 15 分钟 32 次调用就 429，说明配额很紧）。

> 另附现场证据两条：`[FATAL] another engine instance is already running (single-instance lock held), exit`
> 与 `[ENGINE-EXIT] 收到 SIGTERM (15) ... 查是谁在调 restart_backend.sh` ——
> 说明这台机器上还有别的会话在反复重启引擎/改 `ai_worker.py`（日志显示 14:27:48 又改过），
> 引擎在"重启—抢锁—退出"之间循环，也会让产出断断续续。这一条我改不了，需要先停掉那一路操作。
