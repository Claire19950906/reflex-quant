## 0. 一页纸

**三句话结论**

1. 系统的工程完成度很高，但**「分析」和「没分析」没有被记成两种不同的事实**：今天 482 条决策里 430 条（89.2%）其实没有形成有效分析，却和「分析之后判断为中性」共用同一个 `HOLD` 和同一个 `analysis_degraded=1` 标记。
2. 所以瓶颈不在模型是否聪明，而在**漏斗上游四个漏点 + 一个必然坍缩的置信度公式**：36.5% 的决策落在系统不交易的品种上；证据就绪率只有 21.6%；27.6% 的输出被截断或只剩总结；模型方向分 92.3% 是 0，而 `置信度 = |方向分| × 5 个乘子`，0 乘任何数还是 0，闸门拿 15 分去拦一堆 0 分。
3. 结构上的病灶是同一件事的另一面：取数、判据、拼 prompt、调用、解析、归一化、降级、写库全在一根 **2,913 行**的主循环里，**「分析发生在哪一步、坏在哪一步」只能靠读代码猜**。重建的目标不是把目录摆整齐，而是让每个阶段成为可单独回放、单独计分、单独替换的函数。

## 1. 诊断

### 1.1 今天的漏斗：每一环损耗多少

```
raw_news 今日 2,934
  ├─ LLM 门卫 2,614 次调用 → FILTERED 2,451 (83.5%)
  └─ 进入主分析 489  （DONE 262 / PENDING 223 / PROCESSING 7）
        ├─ 落决策 482
        │    ├─ 未降级 52
        │    │     └─ 方向性 3（BUY 2 / SELL 1）
        │    └─ 降级 430
        └─ 待分析积压 223（消费速度 < 生产速度，队列在变长）

累计已结算 3 笔（quick_sim_trades=3，非今日）
```

两个被忽略的事实：

- **223 条 `PENDING` 是排队而不是丢弃**：说明主分析的吞吐已经被「176 条越界 + 194 条真实失败的重试」占满，队列在长。
- **每产生 1 条方向性决策，全天大约花 4.8 M input tokens**（14.4 M / 3）。这个换算不是成本指标，是效率指标：99% 的算力花在了产不出方向结论的路径上。

### 1.2 八处损耗（按「损失 × 可修性」排序）

#### L1 范围错配：36.5% 的决策落在系统不交易的品种上

> 本节数字已用 `backend/scripts/analysis_state_audit.py`（只读）按五终态重算校准（2026-11-16 21:50），
> 与初版口径的差异见文末「审计修正」。

- 证据：`analysis_degraded_reason='target_none'` **264 条**，但它们的去向并不一致——**166 条**是品种越界（`target_asset` NONE 145、CN_STOCK 17、NVDA 15、AMZN 8…），**98 条**是核心品种（XAU 46 / WTI 42 / BTC 10）模型没给出目标、由规则补了品种。
- 全库重算：`out_of_scope` **176（36.5%）**、压缩输出 60（12.4%）、真实失败 **194（40.2%）**（模型未返回 96 / 输出结构不达标 98）、完整 52（10.8%）、数据未就绪 0（当前实现从不因数据跳过调用，只在 `hard_data_status` 留痕）。
- 机制：A 股个股/港股/宏观汇总类新闻走完 `_call_llm_sync` 全套（7.5k 字符 system prompt + 7 个注入块 + 25 s 调用），只为得出「不在核心清单，按 HOLD 兜底」。
- 后果：①预算浪费；②**账本污染**——越界与真实失败被同一个 `analysis_degraded=1` 记账，真实失败率因此被讲成 89.2%（实际 40.2%，见第 12 节的口径修正）；③这 98 条核心品种的 `reasoning_path` 里写着「target_asset=NONE 不在核心监控清单」，而同一行 `target_asset=XAU`——**兜底文案自己把可交易品种判成越界**。按小时核对：98 条全部落在 00:00–08:00 与 11:00 一个点，10:00–16:00 零复现 → 文案重写（`rerender_degrade_text_for_asset`，`ai_worker.py:5202`）在今晨已止血，这批是历史行，不用改代码，只需在统计侧按品种口径过滤。

#### L2 证据未就绪就调用模型：`market_confirmation` 99.2% 是 `unknown`

- 证据：`hard_data_status`：`ok` 104（21.6%）、`missing:feed_stale` **185**、`missing:none_target` 143、`missing:unknown_symbol` 27、`missing:no_local_feed` 23；`market_confirmation='unknown'` **478 / 482**。
- 机制：prompt 里要求「结合多周期盘面结构判断」，但快照过期（`feed_stale`）时仍然发请求，模型只能回 `unknown`；而 `unknown` 正是结构评分无法产出、`structure` 因子（权重 0.15）恒零的直接原因。
- 后果：**七段推演里的「盘面结构分析」段在 8 成情况下是空转**，这是「推理看着很长、方向分却是 0」的主要来源之一。

#### L3 输出契约不稳：27.6% 的分析被截断或只剩总结

- 证据：`llm_empty` **71**、`summary_only` **62**（合计 133 / 482）。
- 机制：主分析 `max_tokens=4000`，MiniMax-M3 会先写 `<think>` 再写正文；`_call_llm_sync` 已经用 prefill `{` 做了补丁，但仍有 71 条完全空、62 条只给 `[总结]` 段。
- 后果：这 133 条被记成「降级 HOLD」，与「模型判断中性」不可区分；同日账本里 `reasoning_path` 从 1,039 字到 4,000 字截断并存（`ai_worker.py:11724` 对 `reasoning_path` 做 `[:4000]`）。

#### L4 置信度公式必然坍缩：92.3% 的方向分为 0，闸门在拦 0 分

- 证据：`sentiment_score=0.0` **445 / 482**；`evidence_confidence` 除 3 条外全为 0；`trade_gate_reason` 里「统一置信度 0.0 低于闸门 20.0」337 条、「低于闸门 15.0」63 条。
- 机制：`evidence.unified_confidence()` 是 `base = |score|*100` 再乘 `significance_weight × coverage_factor × risk_factor × corroboration_factor × (1 - 矛盾比例)`。score=0 → 全式为 0。闸门 15 分拦的不是「低质量方向」，而是「没有方向」。
- 后果：**闸门失去了排序能力**（`gate_calibrator.py` 开头就是这么写的），`v342` 引入的 `structure / surprise / confidence_split` 增量在这套公式里没有出口。

#### L5 记账语义混淆：越界、兜底、失败写成同一个「降级」，`no_trade_reason` 100% 为空

- 证据：`no_trade_reason` **482 / 482 全空**；唯一读它做归因的是 `reflection_ontology.py`（HOLD 原因按「数据不可用 / 延迟 / 源降级」分支），**这些分支从不触发**。同一 `analysis_degraded_reason` 字段里挤着六种语义：越界 176、模型未返回 96、结构不达标 98、只剩摘要 60、服务端兜底 33、无标的。
- 机制：`analysis_degraded_reason` 只有一个字段挤五种语义（越界、空输出、只剩总结、服务端兜底、真正失败）；HOLD 的「为什么不下单」没有独立字段承载。
- 后果：任何按 HOLD 原因做统计的看板（`analysis_process.py`、`missed_signal_detector.py`）都恒为空，`reflection_ontology` 的 22 号分支成了死代码。

#### L6 反思分账错位：82.5% 的反思是在给数据层记账

- 证据：`trade_reflections_v2` 605 条：`layer=data` **499**、`analysis` 97、`timing` 8、`filter` 1；`settled=1` 508 条。
- 机制：`data_feed_timeout` 这类数据层故障被写成「反思」，与「模型推理错了」混在同一张表、同一个胜率分母里。
- 后果：反思器看起来「很勤快」，实际推理类样本只有 97 条 —— **反思层的产出量与它真正能改进的对象不匹配**（这也是此前多轮评估里「反思能自证失败、但无可验证边际」的结构原因）。

#### L7 通道与成本：六个别名叫同一个 key，failover 22%

- 证据（`backend/.env` 实测）：`MINIMAX_API_KEY` / `MINIMAX2_API_KEY` / `MINIMAX_MAIN_KEY` / `MINIMAX_GATE_KEY` / `MINIMAX_ANOMALY_KEY` / `MINIMAX_REFLECT_KEY` **六个变量是同一个 key 的同一串字符**；主分析 745 次里 `ai_worker_failover` 167 次（22.4%）；`gate` 通道 2,614 次调用中 220 次 `http_error`（8.4%），`anomaly` 53 次全部失败（429/529）。
- 机制：模型池按 `weight` 复制槽位（`_build_model_pool`），但槽位背后是同一配额 —— 「账户 2 兜底」不存在，权重 2/1 只是把同一账户的并发放大 3 倍，429 集中爆发后再由熔断逐个摘除。
- 后果：`failover` 让单条新闻付两次 input（2.24 M tokens），`gate` 的 8.4% 错误率让约 220 条新闻的过滤结论不可信（默认放行还是丢弃，取决于降级分支，属于隐性口径）。

#### L8 口径漂移：同一份账本里至少四套版本并存

| 项 | 文档/上游说法 | 运行时实际 |
|---|---|---|

| 闸门阈值 | `config.py:888` 默认 10 | `.env` 15；今日账本里出现 20 与 15 两套文案 |

| prompt 版本 | `ai_main_prompts` 表（0 行） | `ai_decisions` 无 prompt 版本列，无法按版本比较效果 |

补充：同日「过度分析惩罚」文案同时出现 `>800 字` 与 `1800 字 + 重复率` 两种口径，说明当天换过代码版本，跨日聚合会失真。

### 1.4 判断

「顶层分层合理、模块层退化」这个既有结论依然成立，但不够用：**真正的问题不是模块没有按领域归位，而是分析链没有按阶段归位**。领域分包解决的是「文件在哪」，阶段切分解决的是「哪一步坏了、坏的成本是多少」。前者是整洁问题，后者是能力问题 —— 本方案把后者排在前。

### 2.1 四层结构（每层都要有契约和失败态）

| 层 | 职责 | 输入 | 输出 | 失败态（必须落库） |
|---|---|---|---|---|
| L0 证据层 | 快照 / 行情 / 宏观 / 情绪 | 品种 + 时点 | 带 `as_of` 的证据包 | `data_unavailable(feed=…)` |
| L1 分析层 | LLM 七段推演 + 16 字段 | 新闻 + 证据包 + prompt 版本 | 结构化结果 + token 账 | `llm_failed` / `parse_failed` |
| L2 决策层 | 闸门 / 仓位 / 成本 | 结构化结果 + 历史命中率 | action + p_hit + 闸门链 | `gate_blocked(reason)` |
| L3 结算反思 | 2h 前向验证 / 归因 | 决策 + 真实成交价 | `is_correct` + 维度 | `settle_invalid(price_sanity)` |

### 2.2 六条不变量（写进代码，不写在文档里就算数）

- **I1 五终态**：每条新闻的分析结果只能是 `complete | out_of_scope | data_unavailable | llm_failed | parse_failed` 之一，`analysis_degraded` 由它派生，不允许再出现「一个布尔装五种原因」。
- **I2 置信度可复算**：`confidence` 必须能由「历史命中率 + 收缩 + 事前确认」重算出来，且与模型自评分（`model_score`）分开存。
- **I3 样本门槛**：已结算 < 60 笔时，任何胜率/均值只允许出现在「样本不足」区块，不得进入闸门阈值标定。
- **I4 未来函数**：证据只取 `move_ts` 之前；复用已有约定（`config.parse_time_to_bj`、`uses_future=0`）。
- **I5 降级≠中性**：`HOLD` 必须带 `no_trade_reason` 枚举（越界/证据不足/方向中性/闸门拦截/超时过时），统计时分母分开。
- **I6 成本预算**：每次调用写 `tokens_in/out` 与阶段标签，单条新闻的分析预算上限可配置，超预算要显式记账而不是静默重试。

## 3. 分析链优化（W1–W6）

> 排序原则：**先减少「不该发生的调用」，再提高「该发生的调用」的成功率，最后才动评分与阈值。**

### W1 前置范围路由（收益最大、改动最小）

**现状**：`target_asset=NONE/CN_STOCK/NVDA…` 的新闻走完整主分析，176 条/日。

**改法**：
1. 在 `_process_single` 之前插入 `route(news) → {core, adjacent, out_of_scope}`，判据用「已抽出的 event_type + 资产别名表（`asset_alias`）+ 新闻源」三件套，纯本地、可单测。
2. `out_of_scope` 不进主分析：写 `event_atom`（供因果链/A 股情绪页复用）+ `analysis_state='out_of_scope'`，成本 ≈ 0。
3. 对外接口不变（`ai_decisions` 仍写一行、`suggested_action=HOLD`），只是 `analysis_degraded` 不再为真。

**落点**：新 `analysis/route.py`；`ai_worker` 主循环调用点；`analysis_process.py` 的统计口径。

**验收**：主分析调用 745 → ≤ 350/日；`out_of_scope` 行数 ≈ 176；核心品种被兜底成 `NONE` 的 98 条 → 0（由 W3 契约修复）；相关单测 ≥ 12 例（美元指数/黄金 ETF/A 股个股/宏观汇总各 3）。

**回放实测（`scripts/analysis_route_shadow.py`，只读，512 条今日新闻）**：

| 路由结论 | 条数 | 占比 |
|---|---|---|
| core | 157 | 30.7% |
| adjacent | 16 | 3.1% |
| unknown（保守进分析） | 255 | 49.8% |
| out_of_scope（不进主分析） | 84 | 16.4% |

- **误杀 0**：被挡的 84 条里，没有一条跑出 BUY/SELL（只看非副品种、未降级的行）。
- 回放过程中修掉两个会真丢核心新闻的缺陷：① `gate_assets` 实际以 JSON 串存库（`'["个股","原油","黄金"]'`），按逗号拆会带上方括号和引号，**50 条**核心新闻被判成桶；② 桶标签判定排在清单扫描之前，`gate_main_asset="个股"` 会直接短路掉清单里的「原油/黄金」。
- 残留 2 条（`news=28318/28358`，BTC 主行）是副品种链生成的 `server_fallback` 行，正文明写「科技股/英伟达股价」——挡掉它是对的，不是误杀。
- 结论：路由可以开，但 `unknown` 仍占一半，说明**光靠门卫字段不够**；下一刀应把 `event_type_code` 与新闻源一并喂给路由，才能把 unknown 压到 20% 以下。

**风险**：误判核心品种 → 用「宁可进分析」的保守规则（adjacent 一律进）；路由结果写 `asset_route` 列（已存在）。

### W2 证据就绪门（决定「分析有没有意义」）

**现状**：`feed_stale` 185 条、`market_confirmation` 478 条 `unknown`，仍然发 LLM。

**改法**：
1. 调用前检查三件事：快照年龄（按品种的 `max_age`）、目标品种是否有本地源（`quote_sources`）、K 线是否覆盖 `expected_horizon` 所需周期。
2. 不就绪 → 不调用，写 `analysis_state='data_unavailable'` + `hard_data_status='missing:feed_stale'` + 触发 `source_status` 修复流程；**不要**用 `server_fallback` 假装分析过。
3. 就绪包随 prompt 一起冻结（`data_anchor_ts` 已有），保证可回放。

**落点**：新 `analysis/readiness.py`；`engine/forward.py` 复用同一套 `max_age`。

**验收**：`ok` 率 21.6% → ≥ 85%；`unknown` 占比 ≤ 15%；`feed_stale` 的 185 条要么修好、要么明确标记不分析；补测「过期快照」必须拒答。

**风险**：先修 feed 会造成短期「分析量下降」——这是预期效果，不是 KPI 恶化；文档要提前写明。

### W3 输出契约与长度预算（把 27.6% 的损耗压到 3%）

**现状**：`llm_empty` 71（`<think>` 吃满 token）、`summary_only` 62（只输出 `[总结]`）；`reasoning_path` 上限 4,000 字，而「过度分析惩罚」阈值 1,800 字。

**改法**：
1. 两段式输出：第一段 `skeleton`（16 字段 JSON + 每段首句），第二段 `reasoning`（七段全文，可截断到 1,200 字）；任一段失败不影响另一段落库。
2. 保留 prefill `{`；对 `<think>` 模型显式 `enable_thinking=false` 或按模型能力路由（`pool.py` 里按 `key_alias` 打标）。
3. 长度预算显式化：`reasoning_path ≤ 1,200 字`，超长只告警不扣分（惩罚改看重复率，`text_quality.overanalysis_penalty` 已经是这个口径，把旧分支删掉）。
4. 失败重试只走 `lean` 模式（已存在），最多 1 次，避免二次付费膨胀。

**落点**：新 `analysis/contract.py`（字段/枚举/长度校验）、`analysis/parse.py`（三级容错）、`analysis/prompt.py`（版本化模板）。

**验收**：`llm_empty+summary_only` 133 → ≤ 15/日；同一条新闻两次回放字段一致率 100%（除时间戳）；`reasoning_path` 长度分布 P50/P95 进看板。

**风险**：两段式增加一次调用的可能；用「先骨架后推理」在同一次调用里用标记切换，避免真的两次付费（先做单次，失败再退两段）。

### W4 置信度概率化（让闸门重新有排序能力）

**现状**：`confidence = |score| × 5 乘子`；score=0 → 0；闸门 15 拦 0，判据失效。

**改法**：
1. 双轨记账：`model_score`（模型自评，仅作特征）+ `p_hit`（可复算概率）。
2. `p_hit` 由 `gate_calibrator` 的方法论给出：按 `(asset, direction, pre_move_confirm)` 分格，贝叶斯收缩（`SHRINK_N=20`），前 70% 训练 / 后 30% 考试；样本不足回落到「资产级 → 全局」两级收缩。
3. 闸门阈值改为 **p_hit 的分位数**（例如通过率 15%–25% 对应的分位点），不再手调绝对分；阈值变更必须写 `calibration_run` 记录。
4. **切换前先 shadow 两周**：`confidence_shadow.py` 已有影子账本，把 `p_hit` 与旧 `confidence` 并列记账，比较通过后的 2h PnL / 命中率，再改闸门。

**落点**：新 `analysis/confidence.py`；`gate_calibrator.py` 抽成可复用库；`evidence.unified_confidence` 保留为 legacy。

**验收**：方向性产出 3 → 8–15/日；通过闸门的样本 shadow PnL 与随机基线差异可检验（p<0.1 才允许上线）；每条方向性决策能导出「p_hit = 命中率 × 收缩 × 确认状态」的计算链。

**风险**：样本少时 p_hit 全被拉到 50% → 通过率暴涨。用「分格样本 < 20 → 不上调、只用做 veto」的保守策略；门槛规则写死在代码常量里，env 只允许调松紧，不允许调方法。

### W5 通道、缓存与成本

**现状**：六别名同 key；failover 22.4%；gate 8.4% 错误；静态块占输入 2/3（**估算**，`cached_tokens` 今日 2.1 M / 14.4 M ≈ 15% 命中）。

**改法**：
1. 通道真实性：要么真多账户（每账户独立配额），要么**合并成一个逻辑通道 + 显式单点降级**，删掉虚假的 weight 池。当前事实是后者，配置就应该诚实地写成 1 个主通道 + 1 个备用（不同厂商）。
2. `gate` 批处理：8 条新闻一次判定，输入从 1.37 M/2,614 次降到约 1/6；错误率目标 ≤ 2%，失败时整批回落到「进分析」。
3. 静态块：system prompt（7,503 字符）+ `calendar`/`dim`/`performance` 等静态块打标缓存，按资产类别裁剪注入（`core` 与 `adjacent` 两套上下文）。
4. `failover` 治理：调用前健康探测（已有 `_probe_openrouter_if_stale` 的形态），熔断后不再进池；把 failover 计入 `analysis_state`，不再静默重试。

**落点**：`analysis/pool.py`、`analysis/call.py`；`config` 里删除误导性的 `MINIMAX2_WEIGHT` 语义。

**验收**：input tokens/次 13.7k → ≤ 6k；`gate` 错误率 ≤ 2%；`failover` 占比 ≤ 5%；单条新闻的总尝试次数 ≤ 2（可查询）。

**风险**：缓存命中依赖 provider 支持；不支持时改「静态块前置、动态块后置」的顺序也能省 KV 复用。

### W6 复盘分账与样本流水线

**现状**：`no_trade_reason` 全空；反思 82.5% 是 `data` 层；`t2_cost_ledger` 空表；结算曾用冻结价（WTI 86.43 事故）。

**改法**：
1. HOLD 必须写 `no_trade_reason`，枚举五类：`out_of_scope / data_unavailable / direction_neutral / gate_blocked / stale_news`；写入点唯一（`persist`）。
2. 反思按层分表/分列：`layer ∈ {data, analysis, decision, execution}`，胜率只在 `analysis` 层算；`data` 层转成「源健康事件」进 `source_status` 而不是 `trade_reflections_v2`。
3. 成本账本：每笔纸面交易写 fee/slippage/borrow，`t2_cost_ledger` 不允许空表（`paper_trading` 结算时强制写）。
4. 结算价 sanity：结算前检查「同价 tick 连续 ≥ N 次 / 距上一笔更新时间 > max_age / 跨源偏差 > 阈值」→ 拒绝结算并标 `settle_invalid`，绝不把异常价当成交价。
5. 样本流水线：每日 `可结算数 × 结算成功率` 进看板；60 笔门槛用「预计达成日」而不是「已完成数」驱动。

**落点**：`analysis/persist.py`、`engine/forward.py`、`reflection_ontology.py`（去掉死分支）、`quick_sim.py`。

**验收**：`no_trade_reason` 填充率 100%；反思 `analysis` 层占比 ≥ 60%；`t2_cost_ledger` 行数 = 结算笔数；异常价结算 = 0；60 笔预计达成日 ≤ 21 天。

**风险**：HOLD 枚举一旦上线，历史 482 条需要一次性回填（只按 `analysis_degraded_reason` 映射，不改事实）。

## 4. 结构重建：三刀，按收益/风险排

> 原则：**搬迁不是优化**。先切「每天在变的那一段」（分析链），再合「运维重复的那一块」（双后端），最后才动「目录本身」（429 模块）。反过来做，风险最高、收益最低。

### 4.1 第一刀：把分析链切成 `analysis/` 包（strangler，不回写原文件）

目标结构（包名 `backend/src_python/analysis/`，与 `engine/` 平级，避免编排与实现耦合）：

| 模块 | 职责 | 行数上限 | 依赖 |
|---|---|---|---|
| `contract.py` | 16 字段契约、枚举、长度预算、校验器 | 350 | 无 |
| `route.py` | 核心/邻近/越界路由 | 250 | `asset_alias` |
| `readiness.py` | 快照年龄、源覆盖、周期覆盖 | 300 | `quote_sources`、`source_status` |
| `context.py` | 注入块分级装配 + token 预算 + 缓存标记 | 500 | `contract` |
| `prompt.py` | 模板注册（版本 id）、按模型能力裁剪 | 400 | `contract` |
| `pool.py` | 通道池、熔断、配额、健康探测 | 400 | `config` |
| `call.py` | 单次调用、prefill、lean/两段式、超时 | 600 | `pool` |
| `parse.py` | 三级容错解析（JSON/包裹/正则兜底） | 400 | `contract` |
| `normalize.py` | sanitize / presanitize / 资产归一 / 时间校验 | 600 | `contract` |
| `confidence.py` | model_score / p_hit / 收缩 / 分位闸门 | 450 | `gate_calibrator` |
| `persist.py` | 五终态落库、降级记账、HOLD 枚举 | 300 | `db` |
| `pipeline.py` | 阶段编排（每阶段纯函数，可单独回放） | 400 | 以上 |

`engine/ai_worker.py` 退化为调度壳：领取/并发/超时/告警/进度，目标 **≤ 1,000 行**。

**迁移手法（关键，避免第二次事故）**
1. 建包 → 写 `pipeline.py` 的阶段签名 → **旁路接入**：主循环先调用 `analysis.pipeline`，其内部仍调旧函数（`_call_llm_sync` 等），行为零变化。
2. 逐阶段「搬实现」：每搬一个阶段，把旧函数改成 3 行薄委托（`return analysis.parse.parse(raw)`），**不删除旧函数**，保留回滚开关（env `ANALYSIS_STAGE_V2=0/1`）。
3. 每阶段上线前跑 **golden set**：30 条真实新闻 + 冻结证据包（用 `data_anchor_ts` 回放），逐字段 diff；只允许「时间戳/随机 id」不同。
4. 全部阶段切完、gate 全绿，再删旧实现（单独一个提交，可 revert）。

**验收**：`ai_worker.py ≤ 1000` 行；`analysis/` 内单函数 ≤ 300 行；每阶段 ≥ 5 个单测；golden set 一致率 100%；线上 `analysis_state` 分布与迁移前逐日对比无系统偏移。

**风险**：`_call_llm_sync` 里内嵌闭包与共享容器（`_asset_insight_hit_ids`）——搬迁时必须显式改成返回值，不能靠闭包副作用；`_presanitize` 与 `_sanitize` 有顺序依赖，拆开要先用 30 条样本证明等价。

### 4.2 第二刀：双后端 → 单后端

**现状**：`api_server`（:8000，348 端点）与 `bridge_server`（:8100，80 端点）并存，重复 22 条；bridge 的出生原因是「源文件已删、内存里还在跑」的事故补丁。

**改法**：
1. 按域合并剩余 22 条重复（crowd 已做 5 条），每批 ≤ 5 条，带契约测试。
2. 8100 **只保留薄转发**（不做业务实现），并在响应头标 `X-Served-By: 8100-proxy`；前端与脚本逐步改到 8000。
3. 最终 8100 退化为反向代理或直接下线；下线前用访问日志证明「零外部依赖 8100」——**用证据判，不靠感觉**（沿用 `docs/零引用端点审计-2026-11-16.md` 的两证据法）。

**验收**：重复端点 22 → 0；8100 上业务实现行数 → 0；端点总数 ≤ 440；`architecture_baseline.py` 进 CI 作护栏。

**风险**：已知 8100 直挂 8000 实现会慢 20–30 s（`90656ac` 有记录）→ 合并时保留薄转发，不做「直接挂载」；`~/.trident/wrappers/*.sh` 里直连 8100 的脚本要同步清单。

### 4.3 第三刀：`src_python` 领域分包（只做四簇）

**现状**：429 个模块平铺；`docs/后端领域分包方案-2026-11-16.md` 已给出六簇映射，但尚未动运行时代码。

**调整建议**（与既有方案相比更保守）：
1. **先立 `common/`**：`config`、`db`、`time_utils`、`http_retry`、`asset_alias`、`dim_tables`、`source_status` —— 被引用最多的 111/37/29/18 次，必须先固定。
2. **只迁四簇**：`feeds/`、`signals/`、`reflection/`、`decision/`。理由：这四簇占日常改动量的大头，且边界相对清晰；其余（`opt_*`、`backfill_*`、oneoff、测试钉住的模块）留在根目录，等 import 垫片跑稳一年再动。
3. **import 垫片**：`src_python/__init__.py` 用 `__getattr__` 把旧扁平名映射到新包（`db` → `common.db`），让 251 个测试文件不改也能过；垫片标注「过渡用，计划 2 个版本后移除」。
4. **wrapper 清单先行**：分包前拉出 `~/.trident/wrappers/*.sh` 里所有 `src_python/<module>.py` 路径，生成 `reports/structure/wrapper_refs.txt`，CI 校验零失效。

**验收**：首层模块 429 → ≤ 120；跨簇 import 数量进基线；3,638 例测试全绿；wrapper 0 失效；`architecture_baseline.py` 同时产出「首层模块数 / 跨簇 import 数」。

**风险**：一次搬迁 100+ 文件会使 `git blame` 断代（用 `git mv` 保历史）；循环导入最容易发生在 `signals ↔ decision`，用「公共层只依赖 common、领域包之间只允许单向依赖」的规则强制。

## 7. 不做什么，以及为什么

## 11. 准确度的分母在哪里（HOLD 反事实结算，2026-11-16 22:10）

「提高准确率」这件事，先要回答「现在能不能算准确率」。答案是：**不能，因为分母只有 3**。

- `forward_pnl` 非空仅 **3 条**（今天 2 笔 BUY + 1 笔 SELL）；**479 条 HOLD 从不结算**。
- 用 `kline_bars` 1 分钟线给 HOLD 补事后价格（`scripts/analysis_hold_counterfactual.py`，只读），
  今天 180 条 HOLD 可结算（BTC 50 / ETH 11 / SOL 1 / XAU 118）：

| HOLD 之后位移 | 30 分钟占比 | 60 分钟占比 |
|---|---|---|
| <0.10%（几乎没动，观望正确） | 45.0% | 28.9% |
| 0.10–0.30% | 33.9% | 39.4% |
| 0.30–0.60% | 16.7% | 17.2% |
| >0.60%（明显漏单） | 4.4% | **14.4%** |

- 关键交叉项：60 分钟位移 ≥0.60% 的 26 条里，**20 条（76.9%）是分析降级行**。
  也就是说漏单的主因不是「闸门太严」，而是**根本没产出方向**（92.3% 的方向分为 0）。

**所以准确度的提升顺序是三层，不是调阈值**：

3. **最后才是排序**：`置信度 = |score| × 5 个乘子` 在 92.3% 的 0 分面前没有排序能力，

## 12. 选择器在做负向选择（2026-11-16 22:40 的实验）

### 12.1 先修一个记账错误：60 条不该算「失败」

### 12.3 于是新选择器「按档位」而不是「按乘积」

`analysis/confidence.py`：A 可建仓 / B 影子单 / C 只观察 / D 观望，判据是

**结论要说清楚：这不是「新选择器更好」的证据。** 28 条样本下，B 档反而比 C 档差，
