## 二、根因链（按发生顺序）

1. **模型池只装配了 MiniMax 主 / #2 两个账户**（`runtime/model_pool.json`）。
2. 两个账户都返回 **HTTP 402 `insufficient_balance_error`**：
   > "当前已达到 Token Plan 用量上限。为避免调用中断，请升级 Token Plan 套餐，或购买积分补充用量并开启积分自动消耗。"
   12:46 起进入熔断（`runtime/llm_call_failures.jsonl` + `runtime/breakers/*`：open / half_open）。
3. **本地日请求保险丝到线**：3860/3200（`runtime/pool_blocked_alert.json`；闸门逻辑 `src_python/llm_budget.py` 的 `check()`），第二道闸门在发请求之前就拦截，一条都不认领。
4. **备用通道全部不可用**（逐项实测，见下表）。
5. 新闻截止线被抬高：`runtime/news_cutoff.json`，原因 `llm_outage_recovery: idle 701min`，floor 12:43:39 —— LLM 宕机约 11.7 小时，宕机前的旧新闻不会再补分析。

## 五、恢复方案（任选其一，先有一条可用通道）

### 方案 A：充值 / 升级 MiniMax（最快，池现成）
1. MiniMax 后台升级 Token Plan 或购买积分，并开启积分自动消耗。
2. 到账后：
   - 清熔断状态 `backend/runtime/breakers/*`（或等 half_open 自愈）；
   - 若本地请求计数仍挡：调大 `.env` 的 `LLM_DAILY_REQUEST_BUDGET`（如 6000），或等次日 0:00 自然重置当日计数；
   - 重启引擎：`launchctl kickstart com.trident.engine`（bridge 一般不必重启）。
3. 验证：`/api/health/models` 通道 `available=true`；`/api/events/today` 的 `analyzed_count` 增长；页面活跃信号出数。

### 方案 B：接入一条第三方有效 key
- 在 `backend/.env` 填 `DEEPSEEK_API_KEY`（及 `DEEPSEEK_BASE_URL`/`DEEPSEEK_MODEL`），或 `ARK_API_KEY` + 正确的 `ARK_MODEL`（火山方舟 endpoint id）。
- 注意：**DeepSeek 只要配了 key 就自动进池**（`src_python/config.py` 第 582 行附近，无独立 ENABLED 开关）。
- 同样清熔断、重启 engine、再验证出数。

### 方案 C：本地免费兜底（不建议跑主分析）
- 磁盘可用约 19G；`ollama` CLI 不在 PATH。
- 代码注释明确：3B 模型跑主分析 prompt（10k+ token）在 Mac CPU 上会超时，且 JSON 质量差、会污染历史高质量信号库。本地通道只适合门卫（短 prompt 二分类）。
- 若仍要做：先 `ollama pull` 一个 7B 及以上模型，再 `LOCAL_LLM_ENABLED=1`；主分析需另开 `LOCAL_LLM_MAIN_ENABLED=1`。

## 六、注意事项（避免二次踩坑）

- **不要清 `ai_call_stats` 账单记录来"重置"闸门**：那是真实用量账本，清掉等于掩盖消耗；预算闸门应靠调配置或跨自然日重置。
- 恢复前确认 `LLM_GLOBAL_KILL_SWITCH=0`（当前为 0）。
- 不要用 3B 弱模型回填历史信号库。
- AIPING / Xinshu 若要复用，需先起本机代理（Clash 等）并确认端点恢复，再开对应 ENABLED。
