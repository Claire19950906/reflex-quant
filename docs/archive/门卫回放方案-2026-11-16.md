# 门卫回放方案（2026-11-16）

> 目标：把 420 条「impact_score 恒为 5.0」的决策里、**门卫从未打分**的那部分，补上一次 L3 门卫判定，
> 让 `impact_score` 的重建来自真实判断而不是兜底值。
> 前置：v397 已把 `impact_score` 改成 `model > gate_impact_1to100 > gate_strength > default` 阶梯，
> 回填脚本 `src_python/backfill_impact_score.py`（默认 dry-run）已就绪。

## 1. 问题量化（真库实测，2026-11-16 17:5x）

`ai_decisions` 里 `impact_score=5.0` 的 420 条，按对应新闻的门卫状态分组：

| 门卫状态 | 决策数 | 不同新闻数 | 含义 |
|---|---|---|---|
| `gate_unavailable=0` 且 `gate_impact_1to100=0` | 366 | 247（其中 252 条 gu=0） | **门卫压根没跑**，`_attach_gate` 未被调用 |
| `gate_unavailable=2`（鉴权失效/额度耗尽，降级放行） | 45 | 23 | 门卫跑了但拿不到结论，明确放行 |
| `gate_verdict='排除'` 但仍产出了决策 | 9 | 5 | 门卫判"排除"，主分析仍跑了（流程不一致） |

新闻来源高度集中：`sina_flash` 195 条、`wscn` 51 条、`jin10` 7 条，其余零散。
新闻年龄 0.4–18.1 小时。

**关键结论：回放成本按"新闻"算只有 275 条，不是按决策数和全库 9935 条空 verdict 算。**
275 次门卫调用 ≈ 一个 LLM 池跑 25 分钟（实测单次 5.0s，`[GATE-L3]` 日志）。

## 2. 为什么现成的两套回放都覆盖不到这 275 条

系统里已经有**两套**门卫回放：

- `scripts/oneoff/replay_deferred_gate.py`（手动脚本，v320）
- `engine/gate_replay_guard.py`（引擎内自愈，v321；启动日志可见
  `[gate-replay] 启动自检通过…每 300s 一轮，每轮最多 50 条`；v397 前已扩到
  `GATE_REPLAY_INCLUDE_UNJUDGED=1`，把 `gate_verdict` 为空/未判定的 PENDING 也纳入）

两者的选取条件都卡在 **`status='PENDING'`**。而本次目标的 275 条新闻
`status='DONE'`、`ai_decisions` 里已经有对应决策 —— 门卫回放对它们来说"已经太晚"：
早已跳过门卫、进入主分析、产出决策并归档。引擎自愈每 300s 跑一轮也永远捞不到它们。

### 2.1 为什么不能直接把 `status` 拉回 `PENDING` 让自愈去捞

`replay_deferred_gate.py` 与 `gate_replay_guard.py` 的回放后处理都会改写
`is_noise` / `status` 让 `ai_worker` 重新认领 → **重复分析、重复产出决策**，
在 420 条已有决策上叠加一倍新决策，等于人为制造重复样本，直接污染 S12/S15 与归因。

### 2.2 为什么原生脚本也选不中

`replay_deferred_gate.py` 只认 `gate_unavailable=1`；这批里 252 条是 `=0`
（根本没调过门卫），23 条是 `=2`（鉴权失效降级放行），一个都不符合。

结论：需要**独立的"只补分、不动流程"**回放器。

该脚本的选取条件是 `COALESCE(gate_unavailable,0)=1 AND status='PENDING'`，回放后**改写**
`is_noise` / `status` 让 `ai_worker` 重新认领分析。这里有三个不成立的前提：

1. 目标行 252 条是 `gate_unavailable=0`，选不中；23 条是 `=2`（鉴权失效分支，不写 1），也选不中。
2. 这批新闻 `status='DONE'`、已经产出决策。脚本会把它拉回 `PENDING` → **重复分析、重复决策**。
3. 脚本按"新闻"回放但不改已产出的决策，`impact_score` 仍是 5.0，等于白跑。

因此需要**独立的只补分、不动流程**的回放器。

## 3. 方案

### 3.1 新建 `backend/scripts/oneoff/replay_gate_for_decided.py`

职责单一：给"已产出决策、但门卫没分"的新闻补一次 L3 判定，**只写 gate_* 字段**。

选取条件（一条 SQL，先 dry-run 打印）：

```sql
SELECT r.id, r.source, r.title, r.content, r.ts
FROM raw_news r
JOIN ai_decisions d ON d.news_id = r.id
WHERE COALESCE(r.gate_impact_1to100, 0) = 0
  AND COALESCE(r.gate_strength, 0) = 0
  AND r.status = 'DONE'
GROUP BY r.id
ORDER BY r.ts DESC
```

写回字段（**只这几列**）：`gate_impact_1to100`、`gate_strength`、`gate_verdict`、
`gate_core_impact`、`gate_main_asset`、`gate_assets`、`gate_kind`、`gate_timing`、
`gate_is_material`、`gate_unavailable=0`，外加新增列 `gate_replay_v397=1`（幂等标记 + 可回滚锚点）。

**绝对不写**：`status`、`is_noise`、`relevance_score`、`ai_decisions` 任何字段。
（不动 status 就不会被 `ai_worker` 重新认领 → 不产生重复决策。这是与 `replay_deferred_gate` 的根本差异。）

调用：`from realtime_filter import _l3_semantic_gate`，`gate = _l3_semantic_gate(title, content)`；
返回 `None` → 记 `gate_unavailable=1` 并跳过，下次可重试。

### 3.2 安全约束（照抄 `replay_deferred_gate.py` 已验证的教训）

- **逐条独立短事务**：每条 `UPDATE` 后立刻 `commit`，绝不攒批。门卫单次 5–8s，攒批会把写锁跨 LLM 调用长期持有，后台 `ingest`/`ai_worker` 抢不到锁 → `database is locked`（该事故已发生过）。
- `sqlite3.connect(..., timeout=30)`：默认 5s 不够。
- 单条失败 `try/except` 跳过并打印，不中断整批。
- **串行**执行，不并发：门卫池已经在被引擎占着，并发只会触发 429。
- 默认 **dry-run**，`--commit` 才写；`--limit N` 支持抽样。
- 写前把命中行的原 gate_* 值落到 `gate_replay_backup_v397` 表（news_id + 旧值 + 时间），回滚有据。

### 3.3 跑完之后的连锁动作

```bash
# 1) 抽样验证（先 30 条，人工看 3 条 gate_core_impact 是否说得通）
python3 scripts/oneoff/replay_gate_for_decided.py --limit 30 --commit

# 2) 全量
python3 scripts/oneoff/replay_gate_for_decided.py --commit

# 3) 让 impact 阶梯吃到门卫分（v397 已写）
python3 src_python/backfill_impact_score.py            # dry-run 看投影
python3 src_python/backfill_impact_score.py --commit   # 写库

# 4) 复算记分卡 S15
python3 src_python/capability_scorecard.py --write
```

## 4. 预期收益（按实测基线推算，非承诺）

基线：494 条决策，`impact_score=5.0` 420 条（85.0%），S15 实质化 15.3%。

- 275 条新闻里，`sina_flash`/`wscn`/`jin10` 这类快讯型占 92%，门卫给分概率高但**判"排除/无信号"的比例也高**（全库 `可交易 4054 / 无信号 3142 / 排除 2019`）。
- 保守（只有"可交易/强信号"才给分，占比约 40%）：救回 ≈ 110 条 → S15 ≈ 15.3% + 22pp ≈ **37%**
- 中性（给分率 60%，含低分档）：≈ 165 条 → **≈ 48%**
- 乐观（给分率 80%）：≈ 220 条 → **≈ 60%**

到 80% 需要同时做另一件事：剩余 145 条新闻是**结构性无门卫分**（历史数据 + 无 L3 通道时段），只能改口径单列，不能编数。

## 5. 需要你拍板的一个口径问题

门卫判"排除"的新闻（这批里 5 条新闻 / 9 条决策）补上分之后，`impact_score` 怎么定？

- **A 采纳分数**（`gate/10`）：`impact_score` 会掉到 1–2，语义是"这条新闻确实没影响力"。
  好处：S15 真实上升；代价：前端出现大量低分卡片，观感变差。
- **B 排除类固定 2 分**，来源标 `gate_excluded`：评分可控，不出现 1.0。
- **C 不采纳**，把"无门卫分"单列成 `unknown` 一档，不计入 S15 分母。

推荐 **B**：既如实体现了"无影响"，又不制造 1 分噪声；A 的极端值留给模型自己给分。

## 6. 风险与边界

| 风险 | 处置 |
|---|---|
| 门卫额度被打满，引擎当前批次拿不到门卫 | 回放串行 + `--limit` 分批；门卫池失败即停，恢复后重跑（幂等） |
| 写锁与引擎抢 | 逐条 commit + timeout=30 + 只读列最小 |
| 重复决策 | 不写 `status`/`is_noise`，逻辑上不可能被重新认领 |
| 回放结论与当日决策矛盾（门卫说排除，决策却说有影响） | **只补分数不推翻决策**；矛盾行单独出报告，不做自动修正 |
| 我改错列 | 白名单 UPDATE + `gate_replay_v397` 标记 + 备份表，一条 `DELETE` 级回滚 |

不做什么：不重跑主分析、不改 `suggested_action`、不重算 `market_confirmation`（那是价格验证的事，另开一单）。

## 7. 验收标准

1. `SELECT count(*) FROM raw_news WHERE gate_replay_v397=1` = 预期回放条数，且 `status` 分布不变（DONE 恒为 DONE）。
2. `ai_decisions` 行数在回放前后**完全不变**（不产生新决策）。
3. `backfill_impact_score.py` 的"可救条数"从 9 条升到 ≥ 100 条。
4. 记分卡 S15 从 15.3% 升到 ≥ 37%（保守线）。
5. 引擎日志在回放时段无新增 `database is locked`。
