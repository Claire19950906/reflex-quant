## 0. 口径警告（先看这一条）

这个仓里"入库量"有三套算法，互相差 30%~170%，**任何覆盖率结论都必须先说明用的是哪一套**：

| 口径 | 定义 | 24h 读数 |
|---|---|---|
| A · 发布时间 | `raw_news.ts`（平台发布时间）落在窗口内 | 3,950 |
| B · 到达时间 | `raw_news.first_seen_ts`（首次入库）落在窗口内 | 2,611（**下限**，见下） |
| C · 决策行 | `ai_decisions.created_at` 落在窗口内 | 349（analysis 201 + routing_miss 148） |

B 为什么是下限：`first_seen_ts` **全部是 TEXT 字段**，里面混着三种值——epoch 字符串（`"1794981885"`）、ISO 串（`"2026-11-17T18:55:41+08:00"`）、**空串**。空串占 **7,370 / 25,607 = 28.8%**，任何"按到达时间"的 SQL 都会静默少算。

更阴的一点：`first_seen_ts >= <整数>` 在 SQLite 里**永远为真**（TEXT 与 INTEGER 比较时 TEXT 一律更大）。我第一版就被这个坑骗过：算出"24h 到达 18,131 条"，实际只有 2,611 条。**上一轮（11-17）的文档已经记录过这个坑，我还是踩了。**

> 结论：**口径不统一本身就是 P0 缺陷，不是统计美化问题。** 面板、复盘、我的判断全都在这个坑上漂移。

## 1. 当前状态（证据强、可直接复核）

| 事实 | 证据 |
|---|---|
| 主分析自 11:13 后**零调用** | `ai_call_stats.purpose='main'`：今日 00–11 点有调用，12/13/14 点均为 0 |
| 门卫自 12:00 后**零成功** | 12 点 58 次全 `http_error`、13 点 57 次、14 点 52 次；11 点还有 124 次成功 |
| 最后一条决策 11:15:01 | `ai_decisions.max(created_at)`；`analysis` 类最后 11:13:41 |
| 引擎在等上游，不在跑批 | `runtime/ai_worker_progress.json` = `pool-blocked`；看门狗判"上游全池熔断，已等 699s，重启无用" |
| **6 个 MiniMax key 是同一把钥匙** | `MINIMAX_API_KEY` / `MINIMAX2_API_KEY` / `MAIN` / `GATE` / `ANOMALY` / `REFLECT` 的 SHA256 前 8 位完全相同（`39082e69`） |
| 本地兜底实际不可用 | 日志反复 `qwen2.5:3b ... ReadTimeout`（12–32s）；`/api/ps` 返回 `{"models":[]}`（模型根本没加载）；我自己的 8 token 请求 30s / 120s 两次均无响应 |
| 翻译也被同一账户拖死 | `[PRE-TRANSLATE] MiniMax-Translator HTTP Error 429`，英文原文直接入库 |

**因果链（这次是对的）：** 一把 key 同时供门卫、主分析、异动、反思、翻译 → 日耗输入 token 约 5.8M → 配额/限流打满 → 门卫 429 判不出 → 新闻走"降级放行" → **主分析用同一把 key，也 429** → 没人认领 → 50 分钟后归档成 `gate_down`。

所以 `gate_down` 不是"归档逻辑写错"，是**同一账户被六个用途一起抽干**的下游后果。

## 2. 被我讲错的三处（修正）

### 2.1 「80% 新闻被门卫丢掉，可回捞 3,000 条」——**错**

- 按到达口径：`gate_down` 1,862 / 2,611 = **71%**；按发布口径是 3,209 / 3,950 = 81%。两个都高，但分母不同，不能混着说。
- "回捞"这部分**不该做**：这类行是 50 分钟前的新鲜新闻，回捞时已过 45 分钟建仓窗口，只能产出 HOLD 并烧 token。而且你之前定过规矩：**采集中断后以恢复时刻为新起点，不处理停机期堆积**。回捞正好违反这条。
- 正确的动作是：**停机期只保新鲜**（恢复后 30 分钟内的新闻优先），而不是把积压全补跑。

### 2.2 「每小时 10 条决策是产能、目标 40 条」——**错**

- 10 条/h 是**门卫和主分析同时 429 时的故障态读数**，不是系统上限。11:00 那一小时主分析还有 20 次成功调用。
- 用故障态读数当基线去定目标，会把"修故障"和"扩产能"两件事混成一件。

### 2.3 「主分析 1/3 token 花在池外标的」——**方向对，但桶认错了**

- 24h 决策 349 = `analysis` 201 + `routing_miss` 148。
- 池外不是 `analysis` 里的 NONE（只有 18 条），而是**整个 `routing_miss` 桶**（148 条全部 NONE）。
- 但这些 `routing_miss` **确实调用了主模型**（`reasoning` 里带 `[MiniMax-M3 (MiniMax)]` 前缀），按 7.7k 输入/次算：148 × 7.7k ≈ **1.14M / 3.80M = 30%**。
- 所以"省 token"的量级成立，但**"预筛能省下来"没验证**：`analysis/prefilter.py` 默认是开的，24h 只丢了 **1 条**（`prefilter_scope:bucket`）。判据依赖门卫标签，门卫一挂就形同虚设。

## 3. 真正的优化清单（按证据强度排）

### P0-a 配额治理：一把钥匙别再供六个用途

| 项 | 内容 |
|---|---|
| 证据 | 6 个 key 指纹一致；日耗 main 3.80M + gate 1.73M + verify 0.20M ≈ 5.8M 输入 token |
| 动作 | ① 门卫**降载**：规则/关键词先判，只有"可能可交易"才进 LLM；命中缓存的直接复用（同一指纹新闻 24h 内重复率可从 `content_fingerprint` 统计）<br>② 翻译改本地/离线词典 + 缓存，别占主配额<br>③ 若确实要多通道，必须**换账户**，不是换 key 名（现在改名没用，指纹一样） |
| 收益 | 门卫 6,892 次调用是 max 的 14 倍，压掉一半就能给主分析腾出额度 |
| 验收 | 门卫 30 分钟成功率 ≥ 80%；主分析 `pool-blocked` < 30 分钟/天 |

### P0-b 口径修复：先把尺子校准

| 项 | 内容 |
|---|---|
| 证据 | `first_seen_ts` 28.8% 为空；TEXT/INTEGER 比较恒真；funnel 235 / analysis 201 / yield 349 三个分母 |
| 动作 | ① 迁移 `first_seen_ts` 为 INTEGER，NULL 明确标未知，**不猜、不回填**<br>② 统一三个口径的定义并写进 `definitions`：`决策 = analysis + routing_miss`、`覆盖率 = 有 ai_decisions 的新鲜到达 / 新鲜到达`<br>③ SQL 里禁止裸比较文本时间字段，加一条 `fix_*` 式自检脚本 |
| 收益 | 后面所有优化都建立在这把尺子上；不修，指标永远是"看起来好/坏" |
| 验收 | 同一时刻三模块的"决策数"差值 ≤ 5%；`typeof(first_seen_ts)` 只有 integer/null |

### P0-c 本地兜底：要么真能用，要么明确不排队

| 项 | 内容 |
|---|---|
| 证据 | 模型未加载（`/api/ps` 空）、`NUM_PARALLEL=1`、`CONTEXT=8192`、ReadTimeout 12–32s |
| 动作 | ① 启动预热 + `keep_alive=-1`，避免每次冷启动<br>② 探针改成"8 token / 5s 内必须出字"，不达标直接跳过本地通道<br>③ 本地超时从 90s 降到 20s（现在 90s 只是把队列拖长）<br>④ 门卫若走本地，只发短 prompt（L2 二分类），不发 L3 全量 |
| 收益 | 门卫有真兜底；不再有"90s 白等 × N 条" |
| 验收 | 连续 24h 本地探针成功率 ≥ 95%，否则自动退出池 |

### P1-a `routing_miss` 前置（省 30% 输入 token）

- 现状：148 条/24h 全是池外，走完主模型才判 NONE。
- 动作：把 `prefilter` 的判据从"依赖门卫标签"改成"门卫缺判时用正文别名 + 个股特征词"做确定性判定；判不准一律保留。
- 验收：抽 100 条人工复核，误杀 ≤ 2 条；`routing_miss` 占决策从 42% 降到 ≤ 15%。

### P1-b 复核/异动通道恢复

- `verify` 432 次 / 215 成功（**49.8% 失败**）；`anomaly` 88 次 / **0 成功**。
- 这两条都在抢同一把 key，建议错峰 + 独立额度，否则主分析永远排在后面。

## 4. 明确不建议做的

| 提案 | 为什么不做 |
|---|---|
| 把 `NEWS_EXPIRE_GATE_DOWN_MIN` 从 50 分钟放宽到 6 小时、回捞积压 | 与"停机期不处理堆积"的口径冲突；回捞的老新闻已过建仓窗口，只会产出 HOLD 并烧 token |
| 用故障态读数（10 条决策/h）定产能目标 | 那是 429 的读数，不是能力上限 |
| 直接换 key 名字增加通道 | 6 个名字是同一把钥匙，改名不增加任何配额 |
| 先改 prompt | prompt 不是今天的瓶颈；通道与口径才是 |

## 5. 自审记录（我错在哪、怎么发现的）

| 我原来说的 | 复查后的真相 | 错因 |
|---|---|---|
| "24h 入库 3,950、分析 235、覆盖 5.9%" | 三套口径分别是 3,950 / 2,611 / 349，5.9% 是 A 口径对 C 口径算的 | 混用分母 |
| "24h 到达 1.8 万条" | 实际 2,611（另有 28.8% 空值） | `TEXT >= INTEGER` 恒真，把 16k 文本行全算进来了 |
| "137 条池外标的占 39%" | `analysis` 里 NONE 只有 18 条；池外是 `routing_miss` 148 条（占 42%） | 桶定义看错 |
| "本地兜底永久卡死" | 是"模型未加载 + 单槽位 + 90s 超时"，表现为 12–32s ReadTimeout | 用一次 curl 超时下永久结论 |
| "restart_count 797 说明今天不稳" | 797 是累计值，无时间分布；今天有 5 次进程更替的日志证据，但可能是并发会话/手动重启 | 把累计数当当日数 |
| "50 分钟归档闸数学上必然丢" | 机制成立，但真正的驱动是"门卫与主分析同 key，一起 429"，归档只是下游结果 | 把结果当根因 |

方法论上的教训（写进流程，避免再犯）：

1. 任何"量"的结论，先打印 `typeof(列)` 和空值率；
2. 任何比例，先写清分子分母各自用哪套口径；
3. 任何"产能/上限"结论，只用**通道全绿时段**的读数；
4. 任何"永久故障"结论，至少 2 种时间尺度的实测（30s + 300s）才下。
