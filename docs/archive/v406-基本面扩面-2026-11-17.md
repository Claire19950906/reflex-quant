# v406 · 基本面扩面：补齐覆盖 + 拆掉单边偏多 + 装定时任务

> 日期：2026-11-17 · 承接 v405（基本面权重 0 → 0.08）
> 触发：能力审计结论——"公司级基本面只有 4 只票、EPS 同比 4/4 全缺、PE 分位只有 NVDA、无定时任务、
> 单边偏多、A股/港股未表态"。这一版把这 6 个短板里能落的全部落地。

## 一句话结论

基本面从"NVDA 一只票 + 一个只会往多了打分的估值映射"，变成**9 只美股 + 2 只 A股/港股可读、
EPS 同比真能算、低估值遇上盈利下修会自动折半、每天 05:10 自动更新**的一层；
"没有基本面"这件事从一句话拆成**四种可区分的原因**（不适用 / 占位 / 无数据 / 该市场未接）。

## 一、四条改动

### 1）覆盖：5 只基线 → 16 只 + 近 30 天决策过的票（`config.py` + `equity_fundamentals.py`）

| 项 | v405 | v406 |
|---|---|---|
| `EQUITY_TICKERS` | NVDA/MSTR/COIN/MARA/RIOT（5） | +AMZN/META/AAPL/TSLA/MSFT/GOOGL/PLTR/SMCI/MU/HUT/CLSK（16） |
| 实际有数 | 4 只（MARA 从来没抓到过） | **9 只 × 8 季 = 72 行**（NVDA/MSTR/COIN/RIOT/AAPL/AMZN/GOOGL/MU/CLSK） |
| 名单来源 | 写死 | 基线 ∪ 近 30 天真实决策过的美股（`ef.universe()`，最多补 20 只） |

配额是这里最硬的约束，所以抓取改成**两条节流**：
- `EQUITY_STALE_HOURS=168`：一周内抓过的不重抓（三表是季报，一天重抓纯烧配额）；
- `EQUITY_MAX_PER_RUN=6`：一轮最多刷 6 只，按「最旧优先」轮转，几天铺满；被顺延的不影响读数（库里那 8 季照样参与打分）。

### 2）EPS 同比：真正的根因是**窗口太窄**，不是代码没写

v405 的 4/4 只票 `yoy.eps_diluted` 全 None，当时归因为"EPS 取不到"。实测真因是
`db_pack` 只回 400 天 → 只装得下 ~5 个季度 → **算同比需要 8 个季度**，永远差一半。

修复三件：
1. `db_pack` 窗口 `400 → 800` 天（8 季度 + 季报滞后的余量）；
2. EPS 的 **TTM 与同比由同一条序列得出**；利润表缺 EPS（AV `INCOME_STATEMENT` 的常态）时用
   一致预期历史的 `reportedEPS` 拼序列，标 `eps_source="earnings_history"`，不静默混源；
3. **负基数守卫**：`eps_prev < 0` 时同比数学上无意义（EPS 从 −2.0 到 +1.0 会算出 −150%，
   把「扭亏为盈」读成「盈利恶化」）→ 不算同比、标 `eps_source` 加 `_neg_base`、退用营收增速代理。

实测（`ef.db_pack`）：NVDA +96.91%、COIN −135.38%、RIOT −503.32%、AAPL +19.41%、AMZN +20.06%、
GOOGL +88.95%、CLSK −248.35%、MU +808.08%；MSTR 仍无 EPS（源里就没有），继续用营收 +4.24% 代理。

### 3）单边偏多：PE 加 PB 两把尺子 + 一致性护栏（`fundamental_factor.py`）

**问题**：`(50−分位)/50` 让所有"估值低于自身一年中位数"的票都记正分，加上盈利修正 ±40% 饱和，
读数只会往 +1 挤（NVDA 直接顶到 +0.93）。低 PE 分位有两种来源——股价跌了（真便宜）和
盈利下修（价值陷阱），后者恰恰该看空，v405 完全不区分。

**改法**（只折半、不翻转，避免同一条证据用两遍）：

| 情形 | 处理 | 标签 |
|---|---|---|
| 估值分 > 0 且 盈利修正 ≤ −0.10 | 估值分量 ×0.5 | `value_trap` |
| 估值分 < 0 且 盈利修正 ≥ +0.30 | 估值分量 ×0.5 | `growth_premium` |

同时补 **PB 分位**当第二把尺子：COIN/RIOT 常年亏损、MSTR 历史 PE 从没取到 → 这三只票的"估值"分量恒为
None，等于只剩盈利修正在打分。有 PE 时 PE/PB 等权取均值，`components["valuation_basis"]` 记用的是哪几把。

### 4）A股/港股：从"装作不用看基本面"到"要么接、要么明说"（`asset_kinds.py` + `cn_fundamentals.py`）

以前 `CN_STOCK`/`US_STOCK`/`INDIVIDUAL_STOCK` 被归进「非公司标的」，等于把"A股这家公司有财报、
只是没接"说成"这类资产本来就不用看基本面"。现在五类路由：

| kind | 含义 | 例子 | 输出 |
|---|---|---|---|
| `non_equity` | 真不适用 | BTC/XAU/WTI/US10Y | `reason=non_equity`，detail 写「N/A，不是缺口」 |
| `placeholder` | 代码没解析出来（**缺口**） | CN_STOCK/HK_STOCK/US_STOCK/INDIVIDUAL_STOCK/NONE | `ticker=None`，detail 明写「勿据此推断其财报」 |
| `us` | 美股 | NVDA、US_HYNIX→MU | 走三表 + PE/PB 分位 |
| `a_share` | A股 | `600519` / `600519.SH` / `SH600519` 三写法都通 | 东财 `RPT_LICO_FN_CPD` |
| `hk` | 港股 | `00700` / `00700.HK` / `HK00700` | 东财 `RPT_HKF10_FN_MAININDICATOR` |
| `other_market` | 代码清楚、市场没接 | SKHYNIX→000660.KS | `reason=market_unsupported` |

A股口径的关键：东财给的是**累计值**（三季报 EPS 51.53 是 9 个月的），直接当 TTM 会少一个季度、
直接四季相加又会重复相加。用「本期累计 + 上年年报 − 去年同类型累计」还原：
茅台的 EPS_TTM 65.66、营收_TTM 1744.34 亿都是这么算出来的。

CN 层与美股层的不对称（已写进模块 docstring）：美股 = cron 落库、决策链路零网络读库（AV 只有 25 次/日）；
CN = 按需抓取（国内源 ~300ms）+ 24h TTL 落库，因为不存在配额问题。

## 三、踩过的坑（都写进代码注释了）

1. **FMP 免费档对 statement 端点返 402**（`Payment Required`），另有一路 SSL `UNEXPECTED_EOF`
   —— 所以美股只能靠 AV 兜底，25 次/日 × 每票 4 次，必须轮转。SEC EDGAR 实测不通（SSL EOF）。
2. **AV 免费档是 25 次/日不是 25 次/分钟**：一只票三表 3 次 + `EARNINGS` 1 次 = 4 次 →
   一天最多 6 只。所以做**日配额账本** `runtime/av_budget_YYYY-MM-DD.json`，超额直接不发请求
   （而不是"发出去再失败"）。
3. **东财 A股排序列名是 `REPORTDATE`（无下划线）**，写成 `REPORT_DATE` 会返回
   "REPORT_DATE排序列不存在"——看着像没数据，其实是参数名错。港股才是 `REPORT_DATE`。
4. 东财必须带 UA + `Referer: https://data.eastmoney.com/`；`push2.eastmoney.com` 直接
   `RemoteDisconnected`，改用 `datacenter-web.eastmoney.com`。
5. `urllib.request.quote` 不存在，要 `from urllib.parse import quote`。
6. **配额是共用资源**：`EQUITY_TICKERS` 5→16 后，美股快照层（`feeds/equity_feed.py`，1 次/票 的
   AV `OVERVIEW`，6h 一轮）如果不记账，一轮 16 次 × 4 轮/日就能把 25 次/日吃干 → 三表 cron
   静默饿死，症状是"三表永远停在上周"却没有任何报错。已让快照层走同一个账本，并在
   剩余 ≤ `AV_SNAPSHOT_RESERVE`（默认 8）时停手 —— 快照缺一轮下轮补，三表缺就是整季缺口。
7. `install_cron.sh` 里 `TRIDENT_CRON_DIR` 写死旧路径 `~/.cline/data/workspaces/chat/trident_v170/backend/cron`
   —— 项目搬到 `~/Desktop/金融1.0` 后所有 job 都 "⚠ not found; 跳过"。改为按脚本位置推导。

## 一点六、第二轮：把"装上了但没生效"的两处补上

### 1) 配额切分（原来装不下，谁先跑谁吃光）

免费 AV 25 次/日，一只票固定 4 次（三表 3 + 一致预期 1）。原先配置是「三表 6 只/轮」＝
24 次，一跑就把配额吃光，快照层只剩 1 次 → 新票永远拿不到估值快照。改成：

| 用途 | 额度 | 说明 |
|---|---|---|
| 三表（05:10 cron） | 3 只/轮 = 12 次/日 | 季报 90 天才变一次，慢几天不丢数据 |
| 快照层（eq.pe/eq.pb） | 13 次/日 | 快照要密，缺一轮下轮能补 |
| `EQUITY_MAX_PER_RUN` | 6 → **3** | 配合上面 |
| `AV_SNAPSHOT_RESERVE` | 8 → **12** | 快照层剩 12 次就停手，把余量留给三表 |
| `fetch_pack` 自适应 | `limit = min(设定值, 剩余配额 // 4)` | 当天只剩 5 次就只刷 1 只，不白撞 |

16 只基线靠 7 天 TTL 轮转，5~6 天一轮；已有 9 只不会被重抓。

### 2) 快照按「样本最少优先」排队

`equity_feed.fetch_snapshot` 原来是一边 FMP 一边 AV 兜底，配额在名单**前几只**上就耗光。
改成两阶段：先全量走 FMP（不耗 AV），落空的票再按「近 7 天 eq.pe 样本条数升序」排队。
实测排序 `['AMZN','AAPL','NVDA','MARA','MSTR']` —— 0 样本的两只排最前。

### 3) PE 分位重写：原来算出来是假的

排查发现两件事：

- **快照分位不可信**：NVDA 一年窗口里其实只有 45 天、2512 条，九成挤在同一价位
  （19.55），算出来的「97 分位」是采样密度凑的，不是真的贵。
- **倒推可行**：季报 EPS（带**真实公布日**）+ 日线收盘都是现成的 → `ef.pe_history`
  按「日线收盘 ÷ 当时已公布的 EPS TTM」还原一年 PE 序列，每天 1 个点，~250 个样本。
  防前视：EPS 只在实际公布日之后才进 TTM，不用未披露季报解释历史价格。
  亏损（四季 EPS 合计 ≤0）直接跳过 —— 负 PE 放分位会变成「便宜=看多」。

重算后（`pe_history` 为 PE 主算法，快照按日去重后作备份）：

| 票 | 当前 PE | 一年区间 | 分位 | 估值分 | 盈利修正 | 最终分 | 护栏 |
|---|---|---|---|---|---|---|---|
| NVDA | 22.27 | 22.3~58.2 | 0% | +0.994 | +0.884 | **0.9388** | — |
| MU | 9.55 | 8.7~55.3 | 1% | +0.982 | +0.880 | **0.9308** | — |
| GOOGL | 14.81 | 14.6~33.9 | 1% | +0.970 | +0.444 | 0.7072 | — |
| AMZN | 30.32 | 27.1~37.9 | 36% | +0.276 | +0.196 | 0.2362 | — |
| AAPL | 39.55 | 30.8~41.1 | 94% | −0.882 | +0.449 | 0.0039 | **growth_premium** |
| MSTR/COIN/RIOT/CLSK | — | — | — | 无 | — | 纯盈利修正 | — |

**护栏第一次在真实数据上触发**（AAPL：估值极端贵 + 盈利强上修 → 折半记 `growth_premium`），
决策侧 explain 里能看到 `估值分位分=-0.44、盈利修正分=+0.45、护栏=growth_premium`。

只剩 4 只（MSTR/COIN/RIOT/CLSK）仍无估值分量：COIN/RIOT/CLSK 是 TTM 亏损（PE 无意义），
MSTR 源里就没有 EPS。它们的分数仍由盈利修正单向驱动 —— 这是数据事实，不是漏做。


### 4) MARA 从 `no_data` 变成"可读"（不用配额）

MARA 三表抓不到（配额/源缺），但 `equity_earnings_events` 里有 **58 期真实公布过的 EPS**。
新增 `_summarize_earnings`：够 8 期就出一份「只有盈利面」的精简 summary，标 `partial=True`：

| 票 | TTM EPS | EPS 同比 | 最近预期差 | 读数 |
|---|---|---|---|---|
| MARA | −2.29 | −214.3% | +13.8% | 得分 −0.4444（纯盈利面，无估值） |

缺三表就只给盈利面，不给估值/毛利率/现金流，`partial=True` 一眼可见 —— 不拿半套数据冒充全套。

### 5) A股/港股：从"接好了但触发率 0"到"新闻点名就能触发"

根因不是没接，是 `target_asset` 只输出类别（`CN_STOCK`），近 7 天 14 个 distinct 值里
没有一个真实代码。补三处：

1. `asset_kinds.NAME_ALIASES`：**74 个公司名 → 代码**（A股 30 / 港股 24 / 美股 20），
   `resolve_from_text(text, placeholder)` **只在同一市场内反解**（`CN_STOCK` 里的"苹果"不认成 AAPL），
   `NONE` 不推翻（模型明确说无可交易标的就别硬找）。
2. `fundamental_factor.build(asset, hint=新闻原文)`：占位标签 + 新闻点名公司 → 反解出代码后正常出读数。
   实测：`CN_STOCK` + "贵州茅台三季度净利+12%" → `600519.SH`，`HK_STOCK` + "腾讯控股回购" → `00700.HK`。
3. `engine/ai_worker`：两处 `build` 调用都带上新闻原文（`_fundamental_hint`），
   prompt 第0步新增 `news_ticker` 字段 —— 模型点名公司时直接给代码，别再只给类别。

### 6) 顺手把"决策链路可能 stall 8 秒"堵掉

CN 代码一旦真被反解出来，`cn_fundamentals.load()` 会在 TTL 过期时**同步抓东财**（超时 8 秒、
还带锁）— 一条新闻卡住，整批决策排队。改成决策链路 `allow_fetch=False`：

| 场景 | 行为 |
|---|---|
| 决策链路（`cf.build`） | **只读库**，绝不联网；读到旧值就标 `读数 N 天未更新` |
| 定时任务（cron） | 负责抓新数据落库 |

读数过期不再"就地补"，而是显式标出 `stale_days`，让人知道这是旧值。

### 9) PB 分位为什么还是没做（结论：不是没努力，是没有料）

### 十三、财报日更：从"装了但跑不起来"到"引擎自带调度真跑通"（2026-11-17 第三轮）

这一节值得单独写，因为它是典型的"状态显示成功、实际一次没跑"。

**第一次装 launchd（05:10）：**

```
state = not running     runs = 0     last exit code = (never exited)
```

看起来只是"还没到点"，实际用 `launchctl kickstart` 手动触发一次就露了：

```
state = not running     runs = 1     last exit code = 126
```

126 = 不可执行。日志写着：

```
shell-init: error retrieving current directory: getcwd: cannot access parent directories: Operation not permitted
/bin/bash: .../cron/run_equity_fundamentals.sh: Operation not permitted
```

**两条假设，逐条验证：**

| 假设 | 验证 | 结论 |
|---|---|---|
| 项目在 `~/Desktop` 下，launchd 读不到桌面 | 同目录有 112 个 `com.trident.*` job 都在正常跑（exit 0），它们的脚本也只是读桌面上的 python 文件 | ❌ 不成立，桌面**文件可读** |
| `WorkingDirectory` 指向桌面目录 | 把 `WorkingDirectory` 从 `.../金融1.0/backend` 改成 `~/.trident`（能跑的 job 都这么配） | ✅ 是问题之一，已改 |
| 改完仍然 126 | 报错从 `getcwd` 变成直接 `Operation not permitted` 打在 .sh 上 | ✅ 第二层原因：launchd **执行**桌面上的脚本被拒（其他 job 只是让 python 去**读**桌面文件，不涉及 execve） |

**结论：launchd 这条路在"项目位于桌面"的前提下不成立**，不是配置写错能救的。已撤销装载。

**改法：让常驻引擎自己按日触发。**

| 组件 | 内容 |
|---|---|
| `config.py` | `EQUITY_DAILY_AUTO_ENABLED`（默认开）、`EQUITY_DAILY_HOUR=5`、`EQUITY_DAILY_MINUTE=10`、`EQUITY_DAILY_CHECK_S=600` |
| `api_server.py` | `_equity_daily_due()`（纯函数，可测）、`_equity_daily_run_sync()`（子进程 + 1800s 超时）、`equity_fundamentals_daily_watcher()`（已注册进 lifespan） |
| 互斥 | 成功才写 `~/.trident/log/equity_fundamentals.last_run`（日期）；失败不写 → 10 分钟后重试。launchd 与引擎两份调度共用这个文件，谁先跑谁写 |
| 脚本侧 | `run_equity_fundamentals.sh` 开头检查同一状态文件，当天跑过直接退出，避免双份调度各烧一遍 25 次 AV 配额 |

**真实运行证据（不是"代码写好了"）：**

```
bridge.out.log: [EQUITY-DAILY] 日更完成: ... 002594.SZ 比亚迪 净利同比=-4.24 PE=23.16 | [A股港股] 已入库 12 条
状态文件: 2026-11-17
```

中间还出现过一次 `[EQUITY-DAILY] 本轮失败(不记日期，稍后重试)`，10 分钟后自动重跑成功 —— 重试链也是真的在工作。

**顺带补的闸门**：`cron/install_cron.sh` 现在会在安装时检测"项目是否在 `~/Desktop` 下"，
命中就当场打印 TCC 警告和两条可选路径，不再出现"✅ 安装成功"然后一次都跑不起来。
