> 状态：**已完成第 1、2 批（删副本）+ 第 3 批（crowd 域整域切片）**，剩余 22 条待定口径。
> 生成日期：2026-11-16 · 数据来源 `backend/scripts/route_merge_audit.py`（可随时重跑）

## 1. 为什么有重复

`api_server.py`（:8000）与 `bridge_server.py`（:8100）是两个独立 FastAPI app。bridge 在文件末尾会
`import api_server` 并把它的路由**挂进本进程**，挂载时有一条关键规则：

```python
# bridge_server.py 挂载段
if (_path, _methods) in _existing:
    continue        # 已有同名同方法路由则跳过, 保留本文件自身的实现优先
```

于是：**bridge 自己写了实现的路径，api_server 的那份就被遮蔽**。同一 URL 在磁盘上存在两份代码，
8000 对外服务用 A，8100 对外服务用 B —— 这是双实现并存的真实来源，不是"复挂"。

bridge 的出生原因写在它自己的 docstring 里：*"8000 端口 api_server.py 磁盘源文件已删, 内存里 200+ 模块仍在跑"*。
一个事故补丁长成了正式服务，`v367 单后端合并` 只把 lifespan 接了过去，路由层没合并。

按 `routers/meta.py` 的四条切片规矩，把 api_server 里连续的 9 条 crowd 端点整体搬到

**这一步踩到一个必须记下来的坑**：FastAPI 0.163 的 `app.include_router()` **不再把子路由
摊平进 `app.routes`**，而是包一个 `_IncludedRouter`（`path` 为空，真路由藏在 `.original_router`）。
uvicorn 自己不受影响，但 `bridge_server.py` 末尾那段「手工把 api_server 路由挂进 8100」的循环
只认带 `.path/.methods` 的 `APIRoute` —— 被包起来的路由在 8100 上**静默消失**（不报错，
直接落到 catch-all 返回"暂未实现"）。当场表现是 `test_catch_all_is_registered_after_our_endpoints`
失败、`bridge` 日志仍是"挂载 345 个"而 crowd 一条都没有。

处置：在 api_server 里加 `_include_flat()`，按老语义 `app.router.routes.append(r)`，
并同时把 meta 域的 `include_router` 一并换掉。**后续任何域切片都必须用它**，否则
8000 正常、8100 缺端点，且不会有任何报错提示。

## 3.5 对拍证据（比读代码可靠）

`backend/scripts/contract_diff.py` 同时请求 8000 与 8100 的同名路径，比结构不比数值。
2026-11-16 实测：

| 路径 | 8000 | 8100 | 结论 |
|---|---|---|---|
| `/api/market/movers` | 200 / 3 KB / `partial:true` | 200 / 465 KB / 完整 | **同一 URL 两份数据**；8000 默认 timeframe 是 `3m` 且硬映射，8100 是 `24h` |
| `/api/market/prices` | 200 / **13.5 s** / 外网多源 | 200 / 1 s / 本地 K 线 | 慢 13 倍，数据源也不同 |
| `/api/health` | 200 / 91 B / `status` | 200 / 3.5 KB / `db,tables,code_version…` | 两套刻意契约（安全版 vs 部署探针版） |
| `/api/trading/signals` | 200 / 7 KB / **list** | 200 / 145 KB / **dict** | 顶层类型不同，前端写任一侧都会踩另一侧 |
| `/api/events/today` | 200 / 204 B | 200 / 204 B | 结构完全一致 → 可合并 |
| `/api/review/snapshot` | 200 / 768 B | 200 / 768 B | 结构完全一致 → 可合并 |
| `/api/crowd/ranking` | 200 / 28.8 KB | 200 / 28.8 KB | 结构完全一致（前两批收敛的成果） |

据此定下的第一条口径：**前端实际打的是 8100，所以 8100 的行为就是对外契约**。
凡是 8000 与 8100 同 URL 不同内容的，一律改 8000 去对齐 8100，而不是反过来。

**已按此修掉一条**：`/api/market/movers` 的 8000 代理原来只传 `timeframe`、且把非 `10m`
一律映射成 `3m`，于是 8000 永远返回 3 KB 的 partial 轻量版。改为**参数原样透传**
（timeframe/limit/full）、默认值对齐 24h、缓存键带上全部入参。改后 8000 默认返回
423 KB 完整版，`?timeframe=3m` 仍走轻量版 —— 与 8100 逐字节一致。

## 5. 处置原则（不要机械删）

1. **影子副本 / 纯委托**：直接删一份，另一份自动接管。这类最安全（前两批都是这一类）。
2. **同源已分叉（0.5~0.9）**：先 diff 出差异点，判断差异是"修正"还是"口径漂移"。带 `v317/v320 fix`
   注释的多为后续修正，原则上**保留修正版**并搬进 `routers/`。
3. **两套逻辑（<0.5）**：**禁止直接删**。必须先定"对外唯一口径"，再让另一侧改为委托
   （bridge 已有先例：`/api/events/today` 委托 api_server 权威实现）。删错的后果是前端某卡片悄悄换数。
4. 每次合并都要让 `architecture_baseline.py` 的**端点总数守恒**：搬走不改数，删重复才减数。
   总数突变 = 有人把路由搬丢了。

### 踩坑：挂载会把「另一个进程的 DB 连接参数」带过来（2026-11-16）

删掉 8100 侧 `review/snapshot` 后由挂载的 8000 实现接管，**每次 20~30 秒**（删之前 21ms）。
根因：8000 那份用 `sqlite3.connect(DB_PATH, timeout=20)`，在 8100 进程里跟 8100 自己的
写库抢锁，每次都踩满 20s 超时。挂在同一个 FastAPI app 里 ≠ 跑在同一个进程里 ——
连接参数、busy_timeout、线程池都是进程级的，A 进程的实现搬到 B 进程可能完全不可用。

结论：判断「两条能不能合成一条」不能只看返回是否一致，还要看**它的 DB 访问方式是否适配
目标进程**。8000 与 8100 的 DB 访问风格不同（前者大量 `aiosqlite`/裸 sqlite3，后者
统一 `db_cursor()` + 线程池），跨进程合并要优先选「薄转发 + 本地兜底」而不是直接挂载。

### 结论

- **能合的已经合完了**（表格前 6 行）。
- 剩下的多数是「同一份数据的两种包装」：要么缓存新旧不同（events），要么 8100 侧多了兼容参数/信封字段，要么 8100 侧有**注册顺序**或列名修复这类不能丢的细节。
- 真正还需要动的只剩**表格最后 5 行**（causal-graph、filter-stream、stream、v201/impact、v189/calendar、v189/causal），且都卡在同一个前提上：**它们的重查询 20 秒量不出来**，得先给对拍脚本加长超时并单独跑，否则只能猜。
- 下一批建议顺序：① 给 `contract_diff.py` 加 `--timeout` 参数；② 逐个量那 5 条；③ 只对确认「一方是桩」的做转发，其余写进文档标 `兼容` 收尾。
