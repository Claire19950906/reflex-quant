# 能力记分卡（两层验收）

> 一句话：**结构层必须全绿，统计层永远有区间。** 把"有没有"和"准不准"分开验，是这套系统不再天天红的前提。

## 1. 为什么原来的验收入口会反复红

`capability_acceptance.py`（26 项）验的是链路、表、调度、端点、枚举——这类判据是**有限**的，可以修到全绿（2026-10-28 是 21 PASS/4 FAIL，11-09 是 25 PASS/0 FAIL）。

但它同时把"准确率"塞进了同一张 PASS/FAIL 表，于是必然出现三个结构性问题：

| 问题 | 表现 | 后果 |
|---|---|---|
| 样本量当能力 | 75 笔开仓 54.7%，判 FAIL | 样本不足被说成能力不行，改代码也变不绿 |
| 口径漂移 | 事件方向命中率"日格平均"33.5%，"事件加权"48.8% | 同一件事三个数，谁都能得出"绝大多数不达标" |
| 分母重置 | 归因窗口一改，765 条历史归因作废 | 每次修完都像"从零开始" |

## 2. 两层怎么分

```
结构层 STRUCT（capability_acceptance.py 复用）
  └─ PASS / FAIL：链路、表、调度、端点、枚举、只读断言
  └─ 退出码由它决定；有 FAIL 才算"不能用"

统计层 STAT（capability_scorecard.py）
  └─ 达标 / 接近达标 / 未达线 / 样本不足 —— 没有 FAIL
  └─ 每项固定：分子、分母、样本门槛 gate、毕业线 target、基准 baseline
  └─ 比例类给 Wilson 95% 区间；样本不足只报区间，不下结论
```

判定规则（`judge_status`）：

- `n < gate` 或值缺失 → **样本不足**（不是失败）
- 点估计 ≥ target **且** 95% 区间下界 > baseline → **达标**
- 点估计 ≥ target 但区间下界没过 baseline → **接近达标**（方向对了，证据不够）
- 其余 → **未达线**

## 3. 三条防"假进步/假退步"机制

1. **口径指纹**（`definition_hash`）：每个指标对"分子/分母/窗口/门槛"做哈希。口径一改，报告显示「口径变更」，旧对比自动作废，不允许拿新口径和旧数值比。
2. **快照增量**：每次运行追加 `backend/runtime/capability_scorecard/history.jsonl`，报告显示 Δ值 与 Δn。进步用"区间 + 样本增量"证明，不用颜色。
3. **毕业线**：target / gate / baseline 写死在 `METRICS` 注册表里，改口径必须改定义字符串 → 指纹变化 → 历史对比作废。想"改分母让它变绿"会立刻被发现。

## 5. 用法

```bash
cd backend/src_python

python3 capability_scorecard.py                 # 两层总览（结构层会自动跑，约 2 分钟）
python3 capability_scorecard.py --no-structure  # 只算统计层（秒级）
python3 capability_scorecard.py --history 10    # 附最近 10 次快照趋势
python3 capability_scorecard.py --json          # 机读
python3 capability_scorecard.py --no-snapshot    # 试跑，不落快照
python3 capability_scorecard.py --reset-history  # 清空快照（慎用）
```

退出码：`0` = 结构层无 FAIL；`1` = 结构层有 FAIL。统计层**不影响退出码**——它不该把 CI 卡红。

## 6. 工作纪律（避免再次陷入"改不完"）

1. **一次只改一个指标**，改完先看 `--no-structure` 的 Δn 和 Δ值，确认是这个改动带来的。
2. **不动口径就不动快照**：只改实现、不改分子分母，指纹不变，历史可比。
3. **样本不足的指标不许下结论**：S2 在 n≥100 之前，报告里永远只是区间。
4. **结构层全绿是上线门槛**；统计层用于排优先级，不用于判生死。
