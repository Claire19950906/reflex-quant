# v419 · 门卫未判定行不再静默归档（2026-11-17）

> 一句话：**「门卫没判定」不等于「这条新闻不该看」。放行之后没人认领，超龄就被归档 ——
> 这条链 7 天吞掉 4683 条，一条决策都没产出。**

## 1. 问题（先有数字，再动手）

从产能体检的入口漏斗里捞出来的（`analysis_yield.py::gate_funnel`）：

| 日期 | `FILTERED + gate_unavailable=2` | 有决策的 |
|---|---|---|
| 11-10 | 177 | 0 |
| 11-11 | 159 | 0 |
| 11-12 | 309 | 0 |
| **11-13** | **1538** | 0 |
| 11-14 | 1031 | 0 |
| 11-15 | 566 | 0 |

| 合计 | **4683** | 3 |

其中 **4405 条 `retry_count=0`**（从没失败过，基本等于从没被分析过）。
对比同一周真正进分析的只有 786 条 —— 蒸发的比分析的多 6 倍。

## 2. 根因（读代码，不是猜）

```
门卫通道不可用
  → realtime_filter 写 gate_unavailable=1（冻结待回放）
  → 30 分钟后 _GATE_FREEZE_TTL_S 到点，主循环把标记改成 2（降级放行）
  → 但「放行」只改了标记：行仍然待在 PENDING 队尾
  → 认领 SQL 是 ts DESC（最新优先），积压时永远排不到它
  → ts 过了 NEWS_ANALYZE_MAX_AGE_HOURS（6h）
  → _expire_stale_news 归档成 FILTERED，reason 只写 stale_expired
  → 语义上被记成「超龄」，没人知道它「门卫没判过、也从没分析过」
```

v408 已经给「门卫判可交易」的行开了豁免（`NEWS_EXPIRE_KEEP_TRADEABLE`），
但 `gate_unavailable=2` 这一档没开 —— 这就是剩下的口子。

## 3. 改了什么（两处，都在 `engine/ai_worker.py`）

### 3.1 认领顺序加一档（`_BATCH_CLAIM_FRESH_SQL`）

```
窗口内可交易(0) → 过期可交易(1) → 门卫未判定(2) → 其余(3)
```

档内仍按 `ts DESC, id DESC`，v323（最新优先）/ v413 / v418 的实时性语义不变。
**参数个数不变（仍是 4 个）**，调用方 `_build_claim_sql` 无需改。

为什么这类要插队：它们已经白等了 30 分钟冻结期，再让他们排在全量队列的队尾，
6 小时门槛一到就必死 —— 插队是让它们**在死之前**被看一眼。

### 3.2 归档分两段（`_expire_sql` / 新增 `_expire_gate_down_sql`）

| 段 | 对象 | 门槛 | filter_reason |
|---|---|---|---|
| 第一段 | 普通超龄行（门卫有判定的） | 6h（`NEWS_ANALYZE_MAX_AGE_HOURS`） | `stale_expired` |
| 第二段 | 门卫未判定行（`gate_unavailable=2`） | 24h（新开关） | **`expired_gate_down`** |

- 分开写两条 SQL 而不是一条带 OR：**宽限不同**（一条 UPDATE 只能有一个时间条件），
  **留痕也要不同** —— `stale_expired` 是「超龄」，`expired_gate_down` 才是
  「门卫没判过、也没人分析过」，事后要回放时能精确捞。
- 第一段用 `keep_gate_down=True` 把 =2 的行排除在外，交给第二段。

### 3.3 开关（默认全开，可回退）

| 环境变量 | 默认 | 关掉的效果 |
|---|---|---|
| `NEWS_EXPIRE_KEEP_GATE_DOWN` | `1` | 退回 v408 行为：=2 的行 6h 就归档 |
| `NEWS_EXPIRE_GATE_DOWN_GRACE_H` | `24` | 缩到 ≤6h 等于不生效（代码里有保护：宽限必须大于常规门槛） |

`.env` 未改，用代码默认值。要压积压再临时关。

## 4. 看板同步（不然改完也不知道有没有用）

`analysis_yield.py::gate_funnel` 新增 `expired_gate_down`：
过宽限才归档的条数，单列一项，不再混进「门卫不可用被否」。
前端产能体检页的漏斗表加了一行「过 24h 宽限才归档」。

**上线后怎么验证**：重启当天起，`expired_gate_down` 应该接近 0
（因为 24h 宽限内基本都会被插队认领），而 `analyzed_gate_down` 会上升。

## 5. 测试

`tests/test_v408_archive_and_scope.py` 扩到 21 条（+4）：

- 门卫未判定行 10h 不该被第一段归档（守在宽限里）
- 30h 才归档，且 `filter_reason='expired_gate_down'`（不能和 stale_expired 混）
- 两段 SQL 的 WHERE 各自正确
- 认领 SQL 有 `gate_unavailable=2` 档且参数个数仍是 4

v408 原有的 3 条用例显式把新开关关掉，继续守 v408 语义（两版行为都可回归）。

## 6. 边界

1. **只改归档与认领顺序**，没有改门卫判定、没有改分析契约、没有改评分。
2. **24h 之后仍会归档**（不是无限保留）：长期故障下队列不会无上限膨胀，
   代价是极端情况下仍会丢，但那时是「已知丢了 24 小时」而不是「悄悄丢了」。
3. 历史 4683 条**没回放**。它们 status 已是 FILTERED、reason 是 stale_expired，
   要不要捞回来是另一个决策（涉及额度成本与时效），本次不做。
4. 改完需**重启引擎**才生效（进程 08:27 起，代码之后改的）。
