# 决策停写 3.4 小时：根因、为什么"代码干净却还报错"、修复与验证

时间：2026-11-16 16:55 → 20:20（恢复写入）

## 一、症状

| 指标 | 停写时 |
|---|---|
| `ai_decisions` | 478 条，`MAX(created_at)=16:55:49`，之后 3 小时 25 分钟零新增 |
| `raw_news.DONE` | 4346，不增长 |
| `raw_news.PROCESSING` | 8 条长期不落地（19:28 认领的 30497…30566） |
| engine | 每 ~3 分钟认领 8 条，日志里 `[AI] Claimed ...` 照打，但一条都不入库 |
| 队列 | PENDING 509 / FAILED 599 / FILTERED 14316 |

engine 进程是活的、在认领、在调模型，唯独"落库"这一步每批都抛异常。

## 二、根因

```
[19:22:35] [AI] Batch persist 失败，跳过本批: NameError: name 'analysis_degraded_reason' is not defined
[19:25:48] [AI] Batch persist 失败，跳过本批: 同上
[19:28:34] [AI] Batch persist 失败，跳过本批: 同上
```

`_batch_persist()` 里有一个未定义的裸名 `analysis_degraded_reason`（正确应该用
`_ad_why`，即 `classify_analysis_degraded()` 的返回值）。

后果被一个**"全批作废"**的结构放大了：`_batch_persist` 是**一个事务里循环写 8 条**，
任何一条抛异常 → 整个事务回滚 → `except` 打印"跳过本批" → 把 8 条 PROCESSING 全部退回
PENDING。于是队列队头被同一批 8 条反复占位、反复重分析、反复作废：

- 每次作废 = 8 条的分析成本（模型调用、评审、门卫）全部白烧
- DONE 不涨、决策不涨、PENDING 也不降
- 前端"待分析"看起来永远卡着

## 三、为什么"磁盘代码已经干净，运行态还在报"

这是本轮最费时间的一段。现象：

- AST 扫全文件：`bare Name 引用行号: []`（一个都没有）
- grep：只命中 12572 行 INSERT 的 SQL 列名字符串
- 但 `engine.err.log` 里同名 `NameError` 持续冒出来，且 traceback 显示的行内容
  在当前文件里**根本不存在**（显示的是一句注释）

找到的解释（有明确时间戳支撑，不是猜）：

```
engine/__pycache__/ai_worker.cpython-314.pyc   写入时间 20:01
engine/ai_worker.py                            文件修改时间 20:07
```

也就是说：**20:01 进程启动时载入的是 20:01 那版字节码，而源码是 20:07 才被换成干净版本**。
Python 只在 import 时读一次源码，进程不会因为源文件变了就重新加载 → 运行态继续按旧代码执行。

所以"代码看起来干净，日志还在报"不是玄学，而是**旧字节码 + 长驻进程**。
之前几次 `kickstart -k` 也没解决，因为 pyc 时间戳仍指向旧版。

### 修复动作（三步，缺一步都不生效）

1. `rm -f engine/__pycache__/ai_worker.cpython-314.pyc`（删掉旧字节码，逼它重新编译）
2. `launchctl bootout` + `bootstrap com.trident.engine`（真正换进程）
3. 验证：新 pid 起来后，`err.log` 不再新增该 `NameError`

## 四、顺手治理掉的第二个"烧钱点"

修复后仍慢，日志里两类 schema 失败在**每条 NONE 类新闻**上都出现，每次都要再烧一遍全量模型调用：

```
[market_category] '' is not one of ['CRYPTO','GOLD','OIL','STOCK','MACRO','COMMODITY']
[hard_data_evidence] 'N/A' is too short
```

这两条都不是"内容错"，而是"如实的没有"：

- `market_category=""`：`target_asset=NONE`（非核心监控品种）时，分类客观上不存在。
  代码在 `_sanitize` 里本来就把它写成"待复核"标记并进 `unclassified_events`。
- `hard_data_evidence="N/A"`：模型明确说"没有硬数据"，3 个字撞了 `minLength:4`。

改法（`llm_schema.py`）：

1. `market_category` 的 enum 增加 `""`（附注释说明为什么空串合法）
2. 新增 `_EMPTY_EQUIVALENTS`（`N/A` / `不适用` / `无` / `-` …）与 `_is_empty_equivalent()`，
   在 `validate_ai_decision` 包装层里把它们**当空值摘除后校验、校验后原样还原**
   —— 还原是为了让 `missing_fields` / `completeness_score` 依然如实记着缺口，不掩盖。

测试：`tests/test_llm_schema_optional_v396.py` 从 8 例扩到 **11 例**，全绿
（新增：空分类合法 / N-A 占位放行且原样还原 / 真填了但不合格照样拒）。

## 六、剩下的真问题（数据在此，不粉饰）

1. **吞吐仍低**：一批 8 条，实际落库只有 1–3 条。原因不是落库代码，而是
   ① 模型侧 429 / TimeoutError（尾 3000 行里 37 次超时）
   ② 每条分析要多轮（主分析 → schema 补全 → 两步抢救 → 同行评审 → 门卫回放）
   ③ `_batch_persist` 仍是"全有或全无"，一条坏就丢 7 条
2. **新决策 3 条全是 `target_none`**：这条新闻本身是"英伟达/亚马逊/OpenAI 热议"、
   "CFTC 命令争议"、"美联储 50bp 讨论"——对 BTC/XAU/WTI 没有可交易标的，
   判 NONE 是**正确**的，不是降级噪声。但这说明：HOLD 率高的一个结构性原因是
   **新闻池里宏观/个股评论类占大头**，而它们照样走全量 8 次模型调用。
3. **HOLD 率仍不可观测**：基线 478 条 + 现在 3 条，样本量远不够判断
   "R11 + schema 放行后 89.5% 是否下降"。

## 七、建议的下一步（按收益排序）

1. **`_batch_persist` 改逐条隔离**：一条失败只丢那一条，不再整批回滚。
   这是吞吐的第一杠杆（当前等于每批最多 87.5% 的分析成本被浪费）。
2. **无标的宏观新闻走规则级拦截**（不进 LLM）：`target_asset` 可判为 NONE 的新闻
   直接写"规则 HOLD + target_none"，省掉 8 次调用。代价是失去"宏观→间接影响 BTC"
   的推演，需要产品口径确认。
3. 429 侧：把"瞬时限速"的 45s 退避改成按批次指数退避，减少同批内互相踩踏。

## 八、第二轮加固（21:00 之后）

### 8.1 又抓到一个"一条坏值炸整批"

```
[20:56:13] [AI] Batch persist 失败，跳过本批:
           ProgrammingError: Error binding parameter 11: type 'list' is not supported
```

模型把 `reasoning_path` 返回成了**数组**。sqlite3 绑参只接受标量，于是整批 8 条回滚。
现象是队列里同一批 id 反复被认领（20:57 / 20:59 / 21:02 三次同一批）。

修法：新增 `_db_safe()`，INSERT 前把参数逐项归一 ——
list/dict → JSON 文本（内容不丢）、bool → int、其余非标量 → str。
测试 `tests/test_db_safe_params_v396.py` 5 例全绿（含"一批参数混进 list/dict 仍可绑定"）。

### 8.2 尝试给"非核心新闻"开快速通道，实测 **0 命中**

设计：模型判 NONE + 无分类 + 全文无池内关键词 → 跳过 schema 补全 / 两步抢救。
`tests/test_noncore_fastpath_v396.py` 8 例全绿。

但上线后 `非核心新闻（无池内标的）` 打印次数 = **0**。原因查清了：
`POOL_KEYWORDS` 里含"美联储 / 通胀 / CPI / 降息"，而当前队列大头正是宏观新闻，
它们必然命中关键词 → 按保守口径必须照常分析。

**这条优化对当前新闻结构基本无效。** 我没有据此放宽关键词表 ——
放宽就等于放弃"宏观新闻→间接影响 BTC"的推演，那是产品口径，不该我单方面改。

### 8.3 当前吞吐（实测，不粉饰）

- 21:05 落库一条 BTC 决策（`summary_only`），21:16 新批次认领
- 近一小时新增 4 条（11904–11907），其中 3 条 NONE、1 条 BTC
- 门卫侧仍在 20–34 秒/次的超时重试；两步抢救预算 3/10 分钟经常打满后跳过

真正的提速只剩两条路：
1. **提高并发**（多条新闻同时过模型），受模型侧 429 限制；
2. **降低门卫/评审的重试次数**，用"单次判定 + 失败即放行"换吞吐（会牺牲一点判断精度）。
