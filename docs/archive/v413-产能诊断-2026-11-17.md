## 二、四个根因，按影响排序

### R1（主因）`pool-blocked` 是"死等"，且看门狗必杀

`engine/ai_worker.py:11483-11509`：

```python
_pool_ok, _pool_reason = main_pool_ready()
if not _pool_ok:
    _log_progress("pool-blocked")     # ← step 名一直不变
    ...
    await asyncio.sleep(5.0)
    continue                          # ← 不认领、不降级，纯等待
```

- `_log_progress` 每轮都写，但 **step 名恒为 `pool-blocked`**；看门狗 `engine_watchdog.py:284-292` 只认"step 有没有换"，`hang_after = 3×threshold = 1800s` → 30 分钟必判挂死。

## 三、修法（三档，按"改动量 / 收益"排）

### P0-A 让 `pool-blocked` 不再触发"强杀"，并且真的在探活（改 2 处，最小）

1. `_log_progress("pool-blocked")` 带上轮次与已等待时长（例如 `pool-blocked#12/600s`），让 step 名随等待变化；
2. 更彻底的做法：主循环在 pool-blocked 时**主动做一次半开探测**（挑一个通道发 1 条最小请求），探通即刻恢复，而不是只依赖 `main_pool_ready` 的熔断器状态。
3. 看门狗侧对 `pool-blocked` 单独放宽（例如 2 小时），或**只在 step 为 `analyze/batch/persist` 时才判死**——那三种才是真卡死，`pool-blocked` 属于外部依赖不可用，重启无意义。

**预期收益**：今天这种 3.2 小时空等 + 反复强杀的组合直接消失；在办批次不再白跑。

### P0-B 把本地 3B 放进"闸门兜底"，不进"方向决策"（改 1 个 env + 1 处池构造）

- 不建议直接把 `LOCAL_LLM_MAIN_ENABLED=1` 全开：3B 模型出 BUY/SELL 会污染决策表与反思语料。
- 建议新增一个**只给 gate 用**的开关（例如 `LOCAL_LLM_GATE_FALLBACK=1`），把 `local/qwen2.5:3b-fast` 加入 `purpose=['gate']` 的池；主分析在远端全灭时**明确报"降级不建仓"**，而不是产出垃圾方向。
- 这样在 MiniMax 全挂时：新闻照常被剪枝/打标（不丢、不积压），主分析挂 HOLD 且留痕，恢复后自动补。

**预期收益**：`gate_unavailable=1` 的 912 条从"未判定堆积"变成"本地模型已判定"，队列不再被占。

### 本轮新查出来的两件硬事实

**① 引擎今早是「反复被拉起」的节奏，不是「跑不完就慢」**

`[SOURCE-ALERT] watcher 启动` 这个只在启动时打一次的横幅，今早出现 12 次：

| 08:01 | 08:04 | 08:08 | 08:12 | 08:15 | 08:18 | 08:20 | 08:25 | 08:27 | 08:31 | 08:35 | 08:40 |
|---|---|---|---|---|---|---|---|---|---|---|---|

也就是**每 2–5 分钟重启一次**，每次重启都会把在办的 8 条 PROCESSING 退回 PENDING（`ai_worker.py:10941` 启动即重置），所以批次永远跑不完。
崩溃栈指向 `ai_worker.py:11519` `_now_sticky - _MAIN_STICKY["since"]` 的 `TypeError: str - str`，累计 63 次；当前源码该处已是 `time.time()`（v404 修过），最后一次崩溃记录停在 06:42。08:49 之后观察到引擎稳定（同一 PID 持续 >10 分钟）。

**② 能落库 ≠ 能交易：今天 0 笔成交，卡在「信号过期」**

```
[AI] 信号过期，跳过建仓: news=#32145 已 100 分钟（> 45 分钟 / 2700s），仍入库统计不交易
```

今日出现 20 次。含义是：新闻排在队列里等到被分析出来时，已经超过 45 分钟交易阈值 → **只入库、不下单**。
今日 30 条决策的「入库→分析」等待：平均 19.9 分钟、最长 44 分钟；成交 0 笔（昨日 3 笔、-1.319 USDT）。

这就把漏斗闭成了环：**产能不足 → 排队 → 到点时已过期 → 不成交 → 看着"分析了很多"但账上不动**。
修产能（本文件第二节）对成交的意义，就是把这 20 次过期压下去。

### 第四层根因：落库阶段被「逐条两步抢救」拖成十几分钟

前三个根因都在讲"为什么批次开不起来"，这一层讲**为什么批次开起来了也出不了货**。

`_batch_persist()` 是整批一个事务，但它在**事务内**逐条跑"落库前抢救"（v346 那道：真降级 + 真品种 → 精简两步再补一次）。每条要额外 2 次 LLM 调用，约 +45~90 秒。一批 8 条如果全部命中，落库 wall 就 >15 分钟。

实测证据链（2026-11-17）：

| 观测点 | 数据 | 含义 |
|---|---|---|
| `[BATCH-RESULT] 成功 8 / 失败 0` | 08:58 那次 8 条全分析成功 | 分析环节没问题 |
| 落库后实际写成决策的 | 只有 2 条（#32145 XAU、#32152 NONE） | **8 条里 6 条没落成** |
| 那 6 条状态 | 长期 `PROCESSING`、`retry_count=0`、决策数 0 | 卡在落库阶段，直到下次重启被退回 PENDING |
| progress | `step` 停在 `analyze-done`、`step_ts` 09:05:02 长期不动 | 典型「卡在落库」信号 |
| 同一批 id 反复被认领 | 08:16 / 08:19 / 08:21 / 08:34 / 08:41 / 08:46 / 08:51 都是 32145 这一族 | 批次永远跑不完 |
| 今日 `Batch persist 失败` | 白天 0 次；`数据库锁定，第 N 次重试` 0 次 | **不是被锁挡住，是被慢拖住** |
| 代价 | `信号过期，跳过建仓` 今日 20 次 | 分析做完了但过期 → 不下单 |

也就是说：**慢不是问题，过期才是问题**。一条新闻从入库到落库如果走 100 分钟，它产生的信号在法律意义上已经作废（阈值 45 分钟 / 2700s）。

### 改动 4：给「落库前抢救」加单批条数上限

```python
_RESCUE_MAX_PER_BATCH = int(
    os.getenv("TRIDENT_TWO_STEP_RESCUE_MAX_PER_BATCH", "3") or 3)
```

原因：现有的滑动窗口（`rescue_budget_ok`，每 10 分钟 10 条）只限"一个时间段里救几条"，**不限"一批里救几条"**。一批 8 条全命中，8×2 次调用照样放行 → 整批落库被拖到过期。现在每批最多救 `N`（默认 3）条，其余跳过并在 `rescue_log.jsonl` 里记 `skip="batch_cap"`，留到下一批再救（它们还在队列里，不会丢）。设 `0` 可关闭限制、恢复旧行为做对比。

改了三处：

| 位置 | 改动 |
|---|---|
| `_RESCUE_SF_STATE` 定义之后（约 4723 行） | 新增 `_RESCUE_MAX_PER_BATCH` 常量 + 注释 |
| `_batch_persist()` 内 `done_news_ids` 之后 | 新增 `_rescue_used_in_batch = 0` 批次计数器 |
| 抢救判断条件 | 加 `_RESCUE_MAX_PER_BATCH <= 0 or _rescue_used_in_batch < _RESCUE_MAX_PER_BATCH`；命中则 `+= 1`；跳过原因区分 `batch_cap` / `budget_exhausted` |

`py_compile` 通过，16 条测试全绿（`test_v413_*` 7 + `test_engine_watchdog` 9）。

### 改动 5：重启不再把已经落库的成果作废（v415）

改动 4 之后又发现一个更贵的问题。原来的启动复位是一刀切：

```sql
UPDATE raw_news SET status='PENDING', processing_at=NULL WHERE status='PROCESSING'
```

引擎每重启一次就把在办批次全退回队列。但一批 8 条里，决策是**边算边 INSERT**的，被杀时常常已经写进去几条了。这些已经落库的行被退回 PENDING，后果是：

| 后果 | 说明 |
|---|---|
| 白烧额度 | 会被重新认领、重新分析一遍（每条 8~19 次模型调用） |
| 产出重复决策 | 同一份新闻写两条决策，把复盘分母虚高 |
| 「待分析」计数虚高 | 明明分析完了，前端仍显示积压 |

实测：09:23 有 **10 条「决策已落库但状态是 PENDING」**的行在排队等重跑，其中 `32097 WTI`、`32099 XAU` 是真可交易。

现在启动复位拆成三条，各管一段：

| SQL | 作用 |
|---|---|
| `_STARTUP_RECOVER_DONE_SQL` | `PROCESSING` 且有决策 → 直接标 `DONE`（成果已在，没理由重跑） |
| `_STARTUP_RESET_PENDING_SQL` | `PROCESSING` 且没有决策 → 退回 `PENDING`（真没落成，得重来） |
| `_STARTUP_FIX_PENDING_WITH_DECISION_SQL` | `PENDING` 且有决策 → 扶正为 `DONE`（前几轮重启留下的僵尸） |

第三条带保护：`TRIDENT_ALLOW_REANALYZE=1`（回归重放模式）时不执行，否则会把有意重放的数据锁死。

三条 SQL 互斥且穷尽：任一 `PROCESSING` 行有且只有一个归宿，重启后不会滞留。

**线上验证（09:27 重启，PID 90590）**：

```

```

| 指标 | 改前 | 改后 |
|---|---|---|
| PENDING 且有决策（白跑队列） | 10 | **0** |
| 今日 DONE | 8 | **18** |
| 今日已落库的可交易 | 1 | **6** |
| 今日 PENDING | 203 | 208（8 条新的退回 + 扣掉扶正的 10） |

测试：新增 5 条（3 条启动复位 + 2 条 PENDING 扶正），合计 **21 条全绿**。

### 改动 6：schema 补全调用为什么"每条都要来一次"——枚举字段被写成对象/长句（v416）

上面成本一节留了个问题：为什么 `schema_fill_lean` 会比主调用还多。查日志看到真因：

```
[V174-SCHEMA] JSON Schema 校验失败 (3 错) |
  [asset_classification] {'primary':'贵金属','instrument':'XAU','currency':'美元计价',
                          'income_character':'非生息资产','key_drivers':[...]} is not of type 'string'
  [consensus_vs_us] '与既定 SELL 判断一致；偏鹰通胀风险表态强化了实际利率上行压制黄金的逻辑…'
                    is not one of ['一致','反共识']
```

`llm_schema.py` 里这两个字段是**严格枚举**：

| 字段 | 约束 | 模型实际给的 |
|---|---|---|
| `asset_classification` | `enum: 避险/抗通胀 \| 供给驱动 \| 高Beta \| 宏观锚 \| 政策敏感` | 一个 JSON 对象（把分类拆成 primary/instrument/key_drivers） |
| `consensus_vs_us` | `enum: 一致 \| 反共识` | 一整句话（里面其实含"一致"） |

类型不对 → 整条校验失败 → 触发「schema 精简补全」再调一次模型。今日 `schema_fill_lean` **105 次 > 主调用 102 次**，等于每条分析都在多付一次调用。

修法：在**校验前**加一层归一（`coerce_enum_fields`），把已有信息塞回枚举，不改语义：

| 情况 | 处理 |
|---|---|
| `asset_classification` 是对象/数组 | 拼成文本 → 先匹配枚举原词，再走同义词表（避险/非生息/实际利率→避险/抗通胀；OPEC/库存→供给驱动；等） |
| `consensus_vs_us` 是长句 | 先判"反共识/不一致/背离"，再判"一致/相符"，避免"不一致"被"一致"抢先命中 |
| 本来合法 | 不动（返回 0） |
| 归一不了 | 不动，交给补全流程 —— **宁可不猜，也别把分类改错** |

测试：新增 6 条 `tests/test_v416_schema_enum_coerce.py`，全绿。

预期收益：如果它确实命中了大部分误返，`schema_fill_lean` 应该明显下降，单条分析的调用数从 ~2 次降到 ~1.2 次，同时整批变快 → 过期更少 → 才谈得上成交。

### 改动 7：落库卡死 7 分钟的真凶 —— WAL 顶到 64MB 上限（v417）

**时间线（10:00 现场）**

```
09:46:47  Claimed 8 items [32163,32177,32180,32181,32182,32183,32184,32185]
09:51:34  step=analyze-done（分析完成：成功 6 / 失败 2，529、429）
09:51     → 日志彻底停住 7 分钟以上，CPU 0%
```

采样引擎线程栈，卡在这里：

```
sqlite3VdbeExec → btreeBeginTrans → sqliteDefaultBusyCallback → nanosleep
```

也就是**拿不到写锁**，在 SQLite 的 busy handler 里睡。

**真凶不是一个进程，是 WAL 满了**

| 证据 | 数值 |
|---|---|
| `trident_event_bus.db-wal` 大小 | **正好 67,108,864 字节 = 64MB，恰等于 `journal_size_limit`** |
| 手动 `PRAGMA wal_checkpoint(TRUNCATE)` | 返回 **`busy=1`**，64MB → 64MB（**一帧都没截掉**） |
| 每小时的 checkpoint 任务（10:00:54 那次） | 日志写的是 `WAL 64.0MB -> 64.0MB \| 结果=(1, 551, 551)` —— 同样 `busy=1` |
| 写锁可用率实测 | 90 秒探 444 次，**只拿到 94 次（21.2%）**，最长连续抢不到 **60 秒** |
| 同时打开这个库的进程 | **20–24 个**（18 个采集脚本 + engine/api/bridge/sim_equity…） |
| 17 个采集任务的调度间隔 | 全部 `StartInterval=600`（每 10 分钟），**同一秒起跑** |

**这是个自我锁死的闭环**：

```
WAL 涨到 64MB 上限
  → 每次 checkpoint 都要先抢写锁
  → 写锁被 20+ 个并发写者占着（21% 可用率）
  → checkpoint 返回 busy=1，一帧都截不掉
  → WAL 继续满着
  → 写者继续排队，锁更抢不到
  → 引擎落库卡死 → 批次跑不完 → 新闻过期 → 不成交
```

**修法（两条，正交）**

1. **WAL 软上限 64MB → 256MB**（`db.py:266`）
   不是"允许它涨到 256MB"，而是**给 checkpoint 留出可推进的余量**：WAL 不到天花板时 checkpoint 能在锁的间隙里部分完成，不会顶死。实测 WAL 常态 < 60MB，256MB 只是天花板不是常态。
2. **checkpoint 频率 3600s → 300s**（`com.trident.wal-checkpoint-cron.plist`）
   原来一小时才截一次，一小时足够把 WAL 涨满并卡住整段。改成 5 分钟，单次推进量小、更容易在锁间隙成功。

> 恢复验证：手动跑一次 checkpoint 后，引擎立刻恢复写库（`INSIGHTS-HIT-WRITE decision#11962/#11963` 连续落盘），确认机制成立。

### 改动 9：快路径为什么一次都没走通 —— 关键词表把"宏观词"当成"品种词"（v420）

诊断到这一层时，手上有个从早到现在都没解释的怪数：**`_noncore_fast` 日志命中 0 次**。

这条路本来是专门用来省调用的：模型判了 `NONE`（没有可交易标的）的新闻，如果
它自己也说"没有具体品种"、正文里也没提到任何监控品种，那就不该再去做 schema 补全、
两步抢救、落库前抢救（合计 3–5 次额外模型调用，单条多花 1–2 分钟，一批 8 条能拖 20 分钟）。
检查发现它有两个条件卡死了自己，而且**两个都是逻辑写反**：

| # | 原条件 | 实测数据 | 后果 |
|---|---|---|---|
| 1 | `market_category` **必须为空** | 今日 21 条 NONE 决策里 **MACRO 18 条 / 空 3 条** | 86% 直接被挡 |
| 2 | 正文不含 `news_router.POOL_KEYWORDS` 任何词 | 该表 49 个词里混着"美联储/通胀/CPI/非农/关税/中东/制裁" | 宏观新闻**必然命中**，100% 被挡 |

两条件叠加 = 快路径对宏观新闻**在结构上就不可能命中**。可宏观新闻恰恰是 NONE 的大头。

**条件 1 为什么是反的**：`MACRO`（宏观）是**合法且正确**的非品种分类。模型填 `MACRO`
恰恰是在说"这是宏观新闻，没有单一品种"——这跟 `target_asset=NONE` 完全自洽。
拿它当'模型在偷懒'的证据，方向搞反了。真正该警惕的是反向情形：
**给了品种级分类（XAU/BTC/WTI）却又不填 `target_asset`**，那才说明可能漏锁标的。

**条件 2 为什么是反的**：`POOL_KEYWORDS` 是给"新闻→品种路由"用的，里面必然要放驱动词
（不然"美联储降息"这条新闻路由不到黄金）。但"是否提到某个可交易品种"要用另一张表：
提到"美联储"不等于提到了黄金，只是**可能影响**黄金。

修法（`ai_worker.py`，两处）：
1. `declares_non_core_news()`：`market_category` 判空 → 改为判"是否**具体品种级**"，
   新增 `_SPECIFIC_ASSET_CATEGORY_HINTS` + `_is_specific_asset_category()`。
2. `news_mentions_pool_asset()`：`POOL_KEYWORDS` → 换用新增的 `_ASSET_ONLY_KEYWORDS`
   （**只含品种名**，刻意剔除全部宏观驱动词）。

**用今天真实数据回放的效果**（21 条 NONE 决策，不是造的数据）：

| 口径 | 走快路径 | 占比 |
|---|---|---|
| 改前 | 0 条 | **0%** |
| 改后 | **19 条** | **90%** |

剩下 2 条被拦是对的：正文里真出现了黄金/BTC 一类的品种词，这种必须照常抢救（可能漏了标的）。

新增 `tests/test_v420_noncore_fastpath.py` **7 条**，覆盖：
MACRO 放行 / 空分类放行 / 品种级分类拦截 / 正文含品种拦截 /
非 NONE 永不快路径 / 推演过短拦截 / 分类器本身。

> ⚠️ 这条改动的价值不是"今天能成交几笔"——它省的是**调用次数**。今日成本已到

> 正确的修法是**增量落库**（每条分析完立刻写库，重启只损失正在分析的那条），
> 那需要把 `_batch_persist` 从"批末一次性事务"改成"逐条提交"。
> 这是本轮**没有做**的改动 —— 它动的是落库主路径，改坏了会丢数据，
> 需要单独一轮改 + 压测。等外部重启停下来之后，`AI_BATCH_SIZE` 应该调回 8。

| anomaly | 10 | |

**门卫 : 分析 = 8.6 : 1**。今日入库 673 条，等于每条新闻平均付 4 次门卫调用、
0.46 次分析调用。配额还没轮到分析就被门卫烧光了 → 全池熔断 →
`跳过认领：全部通道熔断` → 新闻在队列里等到过期 → 不成交。

**门卫为什么要跑这么多？**日志里有个数字当时看不懂：

```
[gate-replay] 自动回放 33 条，剩余 11141（ok=33 frozen=1 err=0 remaining=11141）
[gate-replay] 自动回放 2 条，剩余 11140
```

一直报「还剩 11141 条待回放」，那它当然每 300 秒都要跑一轮。可同一时刻真查库：

| 口径 | 条数 |
|---|---|
| `gate_unavailable=1 AND status='PENDING'` | **1** |
| `(gate_unavailable=1 OR 未判定) AND status='PENDING'`（正确口径） | **3** |
| 脚本报的 `remaining` | **11,141** |

虚高 **3,714 倍**。根因在 `gate_replay_guard.py` 的 `count_backlog()`，一个少了括号的 WHERE：

```sql
-- 错（原代码）
WHERE COALESCE(gate_unavailable,0)=1 OR (gate_verdict IS NULL OR gate_verdict IN ('','未判定'))
```

SQL 里 `AND` 优先级高于 `OR`，所以这行的实际语义是
「gate_unavailable=1 **或者** 全库所有 gate_verdict 未判定的行」——
**`AND status='PENDING'` 被整个 OR 掉了**，历史 FILTERED / DONE 行全被算进"待回放"。

于是 `run_gate_replay_background` 入口的短路 `if not pending: return stat`
**永远不触发**，引擎每 5 分钟无意义烧一轮门卫调用（50 条/轮 × 6–13s/条），
一直烧到配额熔断。今日门卫 2,688 次调用的很大一块就是这么来的。

而回放本身几乎全白干：今日回放 145 条，结果是 **排除 134 / 可交易 11**，命中率 **7.6%**。

修法（`gate_replay_guard.py:count_backlog`）：把 OR 那一组用括号包起来，
`AND status='PENDING'` 留在**组外面**。

```sql
-- 对
WHERE (COALESCE(gate_unavailable,0)=1 OR (gate_verdict IS NULL OR ...)) AND status='PENDING'
```

⚠️ 坑：第一版我把括号写在最外面写成
`(COALESCE(gate_unavailable,0)=1 AND status='PENDING' OR (...))`，
**照样错** —— 里面仍按 AND>OR 解析成 `((A AND status) OR B)`，status 又丢了。
测试当场抓出来（期望 3、实得 8），才改成现在这个写法。

**线上验证**（读真实库跑修复后的 `count_backlog`）：

```
修复后 = total 11141 / pending 3
改前报的 remaining = 11141
```

`pending` 从 11,141 降到 **3** —— 这 3 条清完，短路立刻触发，回放自动停，
配额回到主分析手里。新增 `tests/test_v422_gate_replay_precedence.py` **3 条**。

## 这条发现对「落地实用性」意味着什么

前十一层改动解决的都是「**跑不动**」；这一层暴露的是「**跑得动，但不做决定**」。

- 产能层：已修到能出结果（今天可交易落库 11 → 16 条）
- 决策层：**HOLD 率 99%**，等于每分钟处理再多新闻，也几乎不产生交易
- 商业层：3 笔样本、累计亏损、99% HOLD —— 「拿它去交易」这件事目前**不成立**

所以产能不是瓶颈的终点，**它只是把瓶颈从「跑不动」挪到了「不敢下单」**。
要改善，得动的是 prompt / 阈值 / 决策口径（`buy_min_score=0.1725` 这类），
而不是继续加速度 —— 这一点和先前那份《落地实用性评估》里「产品落地 C、交易商业 D」的判断是一致的，
只是现在有了更硬的证据：不是跑不起来，是**跑起来也不下单**。
