# 禁止假数据：清理 1393 行 + 建守卫（v403）

> 用户指令："假的全删了，假数据全删了。以后在这个系统里不能出现任何假的数据。"

这句话不能只当一次清理执行完 —— 清理是一次性的，**产生假数据的机制还在**。这一版做两件事：
把已经存在的假数据清掉（1393 行），并让"再造假"在第二天早上就被抓住（每日守卫 + 0 号铁律）。

## 一、判据：什么算假数据

只认一条：**这个值能不能追溯到真实观测**（真实 tick、真实新闻原文、真实 LLM 原文）。

不能追溯的，就是假的 —— 哪怕它看起来很正常。典型是三种：

- **占位**：`0` / `0.0` 被当成"算出来很低"，实际语义是"没算过"；
- **默认值**：`impact_score=5.0` 被当成"影响力中等"，实际是门卫没打分时的兜底；
- **借来的身份**：一条成交/样本引用了一个降级决策 —— 那笔"方向"不是判断，是模板拼的。

处置只允许两种：**置 NULL**（表示"不知道"）或**删行**（表示"这条本来就不该存在"）。
第三条路——编一个合理值填平——是本项目最严重的违规，写在 AGENTS.md 0 号铁律里。

### 清完 20 分钟后 F3 又长出 11 行：根因不是"漏扫"，是 upsert 把 NULL 写回 0

第一轮清理后复扫为 0，但 20 分钟后守卫报警：F3 又出现 11 行 `confidence_at_time=0`。
这些行的 `created_at` 是当天早些时候（04:07 / 08:32 / 13:03），说明不是新样本，而是**旧行被重写**。

真凶在 `missed_signal_reflection.py` 的 upsert：

```sql
ON CONFLICT(decision_id) DO UPDATE SET
    confidence_at_time = excluded.confidence_at_time   -- 用 0 覆盖了刚置的 NULL
```

漏检反思每 10 分钟跑一次（由 `reflection_scheduler` step7 驱动），每次都把同一批 decision
重新 upsert 一遍，于是"清理"变成了一次性的表面工作。

修了两处（这是本版最关键的一处改动 —— 只清不修，第二天一定复发）：

1. **写库前把 0 映射成 NULL**：`confidence_at_time=0` 的语义是"没算过"，写 NULL；
2. **upsert 不许用未知覆盖已知**：`COALESCE(excluded.confidence_at_time, trade_reflections_v2.confidence_at_time)`，
   同一个写法在 `paper_reflection_worker.py` 里也补了一份（它是结算反思的主写入方）。
3. 重启 api 让常驻线程加载新代码，再复扫 → 0。

### 第二波：F2 又长出 6 行 —— 阶梯的"默认 5.0"本身就是假数据工厂

清完 F3 后，新决策又落了 6 条 `impact_score=5.0`（无门卫证据）。根因在
`impact_score_ladder.resolve_impact_score`：模型没给、门卫也没分时，它返回 `5.0` 并标 `default`。
标签只解决了"事后能不能分辨"，没解决"这个值根本不该存在"。

改成返回 `None` + `"unavailable"`：**没算出来的影响力就该是 NULL**，不是"中等影响力 5"。
下游 `decision_guard._clamp10(None, 5.0)` 内部按中性处理（这是计算过程，不落库），
`backfill_impact_score.plan()` 也同步把 unavailable 计为"无法回填"而不是"回填成 5.0"。

### 第三波：为什么改完代码还在写 0 —— 常驻进程拿的是旧模块

第一次修完 F3 仍复发，原因是**进程里跑的是旧代码**：

- 8000 端口上的 api 是另一个会话手动起的进程（不在 launchd 里），`kickstart` 起的新实例
  抢不到端口直接退出，旧进程继续每 10 分钟把 NULL 覆盖回 0；
- 真正的后台调度线程在 **bridge（8100）**里（api 在 bridge 在线时明确跳过所有后台线程）；
- engine（决策写入方）也是重启前启动的，阶梯改动不生效。

处置：杀掉占 8000 的游离进程 → `kickstart` api → `kickstart` bridge → `kickstart` engine，
逐个确认 `curl /health`，然后复扫一次、等一个调度周期（10 分钟）再扫 —— 两轮都为 0 才算收敛。

## 三、为什么没有物理删除 430 条降级决策

F1/F2 只清数值不删行，是有意为之：降级决策本身**是真实发生过的系统行为**（LLM 空返回、
服务端兜底都留了 `analysis_degraded` 与 `degraded_reason`），它是"故障记录"，不是假数据。
删了行，`quality_rejections`、`signal_chain_archive`、`decision_evidence` 等 16 张表的
引用会一起断，故障也无法复盘。

真正要保证的是**它们不许产生任何绩效**：R11 拒绝建仓、统计口径把 `analysis_degraded=1`
剔除、前端标注"降级"而非"观望"。这三条现在都成立。

如果要把这 430 条从库里彻底抹掉，属于另一个决定（会破坏审计链），需要单独拍板。

## 五、运行方式

```bash
cd backend/src_python
PYTHONPATH=. python3 fake_data.py                 # 审计（只读）
PYTHONPATH=. python3 fake_data.py --commit        # 清理（先备份库）
PYTHONPATH=. python3 fake_data.py --guard         # CI/cron：有假数据退出码 1
PYTHONPATH=. python3 fake_data.py --json-out x.json
```

写库时按主键 80 行一批 + 每批 commit + 写锁退避重试：生产库里引擎在持续写，
单条长事务会把 SQLite 写锁攥住几十秒，实测直接 `database is locked`。
