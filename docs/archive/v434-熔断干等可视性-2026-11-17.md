## 一、为什么还要改：修完「不杀」之后，仍然看不出在等什么

v413 修完后，看门狗对 `pool-blocked` 有一条 6 小时独立宽线（`POOL_BLOCKED_HANG_AFTER_S`），
不会再拿 30 分钟去砍。但现场信息依然是空的：

| 现场 | 修之前 | 现在（v413 之后） | 缺什么 |
|---|---|---|---|
| `runtime/ai_worker_progress.json` | `step` 恒为 `pool-blocked` | 仍然恒为 `pool-blocked` | 第几轮、等了多久、还要等多久 |
| 引擎日志 | `跳过认领：全部通道熔断: mm1[熔断中],mm2[熔断中]` | 同左 | 该等（quota 30min）还是该换 key（auth 24h） |

v409.2 那次更典型：熔断器停 `half_open`、探测名额被占死、日志只有「熔断中」四个字，
**没有倒计时**，于是「通道 30 分钟内自愈」和「30 分钟纹丝不动」在日志里长得一模一样。

## 二、改法（两处，都在 `engine/ai_worker.py`）

### 1. `pool_recovery_eta(pool=None)` —— 只读，算「最近可恢复」

按每条通道的 quota / net / auth 三个熔断器算：

- `state == "open"` → 剩余 = `_wait_until - now`；
- `state == "half_open"` 且 `_probe_in_flight` → 剩余 = `probe_timeout - (now - _probe_at)`（探测名额被占死的最坏情况）；
- 单条通道取三类里**最大**的剩余（三类都通才算这条通道能用）；
- 池层取**最小**（最快的通道恢复就该立刻认领）。

返回值：`None` 算不出（池空 / 熔断器取不到）、`0.0` 已有通道可放行、`>0` 剩余秒数。

**红线**：只读属性，**不调用** `allow()`。`allow()` 有副作用（open 冷却到期会顺手推
`half_open` 并占掉唯一探测名额），v409.2 就是被这个副作用卡了 30 分钟。

### 2. `_log_progress(step, **extra)` + 熔断分支落现场

`step` 名**不变**（仍是 `pool-blocked`，看门狗是精确匹配，改名会让 6 小时宽线失效），
额外落五个字段：

```json
{
  "step": "pool-blocked",
  "pool_blocked_round": 720,
  "pool_blocked_since": 1794910527.5,
  "pool_blocked_elapsed_s": 3600.2,
  "pool_blocked_reason": "全部通道熔断: mm1[quota(1780s)],mm2[quota(1780s)]",
  "pool_next_recovery_s": 1780.0
}
```

日志同步改成：

```
[AI] 跳过认领：全部通道熔断: …（熔断冷却中，零额度消耗｜第 720 轮，已等 3600s｜最近可恢复 20:14（还要 1780s））
```

通道恢复后 `_pool_blocked_since` / `_pool_blocked_round` 清零，下一轮 `_log_progress`
整份覆盖，旧字段不会残留。

## 六、追加：`processing_at IS NULL` 的僵尸回收（19:35）

> 重启让 v434 生效后顺手发现的问题，一并修在本轮。

**现象（生产实测，不是推演）**

2026-11-17 18:00–18:12 入库的 6 条新闻（33918 / 33981 / 34008 / 34011 / 34017 /
34025）挂在 `status='PROCESSING'`、`processing_at` 为空，一直挂到 19:14 重启才消失。
看门狗每 120 秒跑一轮、每轮都判定「无需动作」——因为它根本没把这 6 行纳入回收范围。

**根因**

```sql
-- 旧
WHERE status='PROCESSING' AND processing_at IS NOT NULL
  AND processing_at < datetime('now','localtime','-15 minutes')
```

`processing_at IS NOT NULL` 这条本意是「没写认领时间的行不算卡死」，实际效果是
**它们永远判不了死**：唯一能清掉它们的路径只剩重启时的启动复位
（`_STARTUP_RESET_PENDING_SQL`）。代价是——它们占着「待分析」计数、占着
`_CLAIM_DEDUP`（有决策的行不再进队列），而在对账口径里它们既不是 PENDING 也不是
DONE，属于"看不见的死行"。

**为什么 NULL 只可能来自异常路径**

认领 SQL（`_BATCH_CLAIM_FRESH_SQL` / `_BATCH_CLAIM_SQL`）是**同一个 UPDATE** 同时写
`status='PROCESSING'` 和 `processing_at=datetime('now','localtime')`，不可能只写一半。
所以 NULL ⇒ 批中途被杀 / 落库回写异常，按「新闻入库时间」判年龄是安全的，
不会误伤刚认领的行。

**改法**

```sql
-- 新
WHERE status='PROCESSING'
  AND COALESCE(processing_at, datetime(COALESCE(ts,0),'unixepoch','localtime'))
      < datetime('now','localtime','-15 minutes')
```

`ts` 是 epoch 整数（全表无时区歧义，v433 刚统一过），`ts` 也缺失时按 1970 处理
（异常行直接进回收流程，`retry_count` 仍会把它推到 `FAILED`）。

**测试**

```bash
cd backend && python3 -m pytest tests/test_v434_processing_null_reclaim.py -q        # 8 passed
cd backend && python3 -m pytest tests/test_v322_watchdog_active_batch.py tests/test_v434_processing_null_reclaim.py -q
# → 39 passed（含把 test_v322 里锁死旧判据的两条改为新语义，并补 ts 列）
```

**生效状态**

引擎 19:21 启动的新进程（pid 40039）已加载本改动；此前 6 条僵尸是启动复位清掉的，
下一次出现 NULL 僵尸将由看门狗在 15 分钟内自动回收，不再需要重启。

## 七、同一时段发现的另一件事：外部 kickstart 风暴

`~/.trident/log/engine.out.log` 里近 1 小时有 9 条
`[ENGINE-EXIT] 收到 SIGTERM (15)`（17:38 / 17:42 / 17:44 / 17:45 / 17:51 / 18:00 /
18:08 / 18:17 / 18:26 / 18:52 / 19:14 / 19:21，间隔 2–26 分钟不等）。
`ops-audit` 同一天的告警原文是：

> [严重] 引擎被反复重启：近 1 小时 SIGTERM × 9
> → 批次落库在批末一次性提交，重启会整批作废；先停掉外部 kickstart

`~/.trident/wrappers/run_engine.sh` 的注释里也早就写着「实测今天引擎每 3–5 分钟被
外部会话 kickstart -k 一次」。落库是批末一次性提交，每被杀一次就作废一批（约 6 条），
也就是说**零产出小时不只来自熔断干等，也来自这个外部重启源**。

这条不在本仓库代码里（`master_api.py` 无重启接口，仓库内无任何 `kickstart` 调用点，
`~/.trident/log/restart_calls.log` 也没有记录），需要先定位调用方再决定怎么处置。
