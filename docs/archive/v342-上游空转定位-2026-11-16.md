# v342 · "不给方向"到底卡在哪（2026-11-16）

## 一、先排除掉两个嫌疑

用 `ai_call_stats`（真实调用日志，403,164 行）核对近 3 天：

| 状态 | 次数 |
|---|---|
| `ok` | 682 |
| `http_error`（其中 **429 = 737**） | 913 |
| `network_error`（其中 **ReadTimeout = 325**） | 336 |

再看 `purpose='main'`（主分析，即生成决策的那一路）：

| 项 | 结果 |
|---|---|
| 调用次数 | **195，全部 `ok`** |
| `tokens_out` 分布 | 800–2000：**193** · ≥2000：1 · 300–800：1 |
| `tokens_out = 0`（真空回） | **0** |

**结论：主分析调用是成功的、输出也不短（800–2000 token）。**
所以不是 `max_tokens=4000` 截断（平均 519、最大 2260，离 4000 很远），
也不是主链路超时。429 和 ReadTimeout 打的是 `gate` / `anomaly` / `advisor` 这些旁路，
不是出决策的那一路。

## 二、真正的断点：模型给了内容，但没给"标的 + 八段"

272 条决策的实际分布（`report_llm_degrade.py`）：

| 类型 | 条数 | 占比 |
|---|---|---|
| 真实八段 | 29 | 10.7% |
| 只有 reasoning 摘要 | 51 | 18.8% |
| 完整降级（`target_asset=NONE` 起步） | **191** | **70.2%** |

对照字段长度：降级行 `asset_reasoning` 平均 **24.6 字**（基本空），
真实八段行 39.4 字；`reasoning_path` 降级 435 字（模板本身就是这么长）/ 真实 645 字。

也就是说：**模型返回了 800–2000 token 的 JSON，但里面缺 `target_asset`，
也没写八段 → 下游只能按 NONE 记账 → 整条决策变成"品种不存在 + 无方向"。**

这解释了那个矛盾现象：调用日志一片绿，决策日志一片 HOLD。

## 三、真凶：未闭合 `<think>` 把 JSON 一起删了

重启后现场日志给出决定性一行：

```
[PARSE-DEBUG] 原文 1455 字 → 剥 think 后只剩 0 字
              | 原文头: '<think>We need output JSON only ... WTI bullish due Russia refini'
```

模型（MiniMax-M3 / M2.7）在 thinking **未闭合**的情况下直接接 JSON，
而旧代码对未闭合 `<think>` 的处理是 `re.sub(r"<think>.*$", "", ...)` ——
**从标签删到文末**，把 1455 字里 think 之后的完整 JSON 一起删掉。

于是：调用成功（tokens 800–2000）→ 文本被削成 0 → `json.loads('')` → 空结果 →
schema 5 错 → 降级 NONE。这就是"调用了、也返回了，但决策永远是兜底"的完整链路。

### 修复：抢救式剥离

`strip_think_blocks()`：配对 `<think>…</think>` 照旧剥；未闭合时**从标签之后找回
第一个 `{` / `[` 起的 JSON**，只有找不到 JSON 才真的清空。附带 `has_unclosed_think()`
用于计数，日志打 `[THINK-RESCUE] 原文 N 字 → 保留 M 字`。

回归用例（`test_v342_empty_output_retry.py`）：未闭合 think + JSON → 能 `json.loads`
且 `target_asset=WTI`；配对 think 仍正常剥；纯 think 无 JSON → 判空。

## 四、另外两处补强（都不改判定）

### 1. 空输出补一次（`is_empty_llm_output` + 一次重试）

历史上**空响应根本不重试**：`_parse_result` 拿到空串 → 关键词兜底 → 降级，
记录里只剩"没分析"，而调用日志显示成功。现在：

- 只在**真没内容**（去 think/代码围栏后 < 10 字）时补一次
- 正常 HOLD 的短 JSON（>10 字）不触发，不会重复烧额度
- 重试再空 → 记 `note_retry_failed`，保留兜底

### 2. `target_asset` 进"必填缺口"，让既有 schema retry 真正触发

原来 schema 补全 retry 的必填清单是 `data_anchor_ts / hard_data_evidence /
elasticity_window / verification / asset_classification / fund_driver / consensus_vs_us`，
**唯独没有 `target_asset`** —— 而它缺失正是 70% 降级的起点。

现在 `target_asset` 缺失或等于 `NONE/OTHER` 也算缺口，会带上 hint 重试一次；
判据仍是"缺 ≥2 个必填字段"，不会让每条新闻都多打一次。

## 九、第二个根因：重试从未执行（慢通道死开关）

`_is_slow_channel()` 的判定是 `"MiniMax" in label or "minimax" in api_base` ——
而生产模型池正是 MiniMax-M3 / MiniMax-M2.7。于是：

| 重试类型 | 线上是否执行 |
|---|---|
| format-fix retry | ✗ 被慢通道跳过 |
| **schema 必填补全 retry** | ✗ 被慢通道跳过 |
| summary retry | ✗ 被慢通道跳过 |

重启后的日志证实：出现了 `缺 P0-2 必填字段` 之前应有的行，但一次都没打
`retrying...`。也就是说这些"根因修复"从上线起就没生效过。

### 修复：只放行"再不放行就必然废数据"的情形

新增 `should_schema_retry(is_slow, missing, allow_slow_retry)`：

- 快通道 → 照旧重试
- 慢通道 → **仅当** `target_asset` 缺失 **或** 必填缺口 ≥ 3 时放行一次
- 其余照旧跳过（避免每条新闻都多烧一次 23s 的调用）
- 开关：`TRIDENT_ALLOW_SLOW_SCHEMA_RETRY=0` 可一键关掉

日志会标 `retrying（慢通道抢救）...`，便于统计放行了几次。


## 十、第三步：两步抢救（先锁标的，再要八段）

修复上面两个 bug 后仍有约 70% 落降级 —— 因为模型**重试也照样交回 skeleton**
（`asset_nature ''` / `factor_ranking []` / `reasoning ''`）。
一次调用要求它同时做三件事（选标的 + 写八段 + 填 8 个证据字段），它就会只填骨架。

于是拆成两次：

| 步 | 要求 | 预期输出 |
|---|---|---|
| ① | 只给 4 个键：`target_asset` / `suggested_action` / `sentiment_score` / `market_category` | 极短，几乎不会空 |
| ② | 锁定标的后，只补 `reasoning_path`（八段）+ 6 个证据字段 | 有明确标的作锚，八段不再空 |

合并规则写成纯函数 `merge_two_step()`：

- **①锁不住标的（NONE/OTHER）→ 整段放弃**，不拿②的半成品覆盖
- 空串 / 空数组 / <4 字的字段一律不覆盖原值
- 合并成功后用 `rerender_degrade_text_for_asset()` 修正降级文案里的"NONE/不在清单"

开关：`TRIDENT_TWO_STEP_RESCUE=0` 可关闭（关闭后回到单次 schema 重试）。
代价：每条需要抢救的新闻多 2 次调用（约 +45s），日志标 `两步抢救①/②`。

回归用例：`test_two_step_merges_target_and_sections` /
`test_two_step_aborts_when_target_locked_fails` /
`test_two_step_does_not_overwrite_with_empty`。

## 十二、所谓"gate 独立配额"其实是假的（已核实）

## 十五、把"独立配额"做成一个空位 + 一个自检

### 空位（你填 key 就生效，不用改代码）

`.env` 里加三行即可生成一条 `purpose='gate'` 的独立通道：

## 十七、针对最大块（target_none 66%）的 prompt 改造

### 观察

208 条 `target_none` 里，很多新闻其实有明确品种（俄炼厂遇袭→WTI、日本国债→XAU/BTC 传导），
模型却写了 NONE。原因不是"不会判"，而是 prompt 把"资产归类"放在第 3 节，
且允许"拿不准就 NONE"——于是 NONE 变成了"我不确定"的挡箭牌。

### 改法（只改 prompt 结构与措辞，不动任何阈值/权重）

在主 prompt 最前面插入 **第 0 步：先判标的**：

- 必须从核心清单挑一个：XAU/WTI/BTC/ETH/SOL/CN_STOCK/US_STOCK/HK_STOCK/SKHYNIX
- **禁止**把 NONE 当"不确定"用；拿不准时选"被冲击最大"的那个，在 [自检] 写明不确定点
- 只有确实无可交易标的才允许 NONE，**且必须写出具体理由**
- 连锁冲击时谁最大写谁，其余放 [因素定位] 的传导说明
- JSON 里 `target_asset` 放**第一个键**，先定调

这条与既有的"资产归类（第 3 节）"不冲突，是把它的优先级提到最前。
存量 208 条 NONE 不回改（改历史文案=改证据），只看新数据。


## 十八、又抓到一个"空转的观测"：探针表根本没建

`llm_degrade_probe` 里明明有 `record()`（把降级分 5 类落表），
但 `init_schema()` **从来没被调用**，`record()` 又把 `sqlite3.Error` 静默吞掉 ——
于是"记录降级"这件事一直在空转，表里一行都没有。查的时候直接
`no such table: llm_degrade_probe`。

修法：`record()` 首次调用时自愈建表（一个 `_SCHEMA_READY` 标志），
不依赖哪条启动路径"记得调它"。

**教训**：观测代码只要吞异常，就会比没有观测更糟 —— 你以为在看数据，其实在看空气。
所以任何"只读不写"的探针，都要有一个**确定会跑的建表点**（或启动自检打印行数）。

## 二十、更正一处误判：不是"三次调用各交空"，是**一次调用交出三行空壳**

按 `news_id` 分组后真相变了：

| 新闻 | 行 | 说明 |
|---|---|---|
| 28507 | CN_STOCK(主) + XAU/WTI(副) | 主行成功，副品种两行空 |
| 28508 | BTC(主) + XAU/WTI(副) | 三行全空 |
| 28511 | BTC(主) + ETH/SOL(副) | 三行皆服务端兜底 |
| 28512 | WTI(主) + XAU/BTC(副) | 三行全空 |

副品种与主品种**共享同一次分析的 reasoning_path**（`_expand_multi_asset_results`）。
所以"三行全空"= **一次调用交出空壳**，然后三行一起降级。
之前说"分品种三次调用易交空"是错的 —— 调用次数没变，是**一次就空**。

### 真正的漏洞：空壳判不出来

`is_empty_llm_output()` 只判**原文长度**（去 think/空白后 < 10 字）。
但失败调用的原文并不短 —— tokens_out=33 时模型交的是
`{"target_asset":"XAU","suggested_action":"HOLD"}` 这种**合法但无正文**的 JSON。
于是：

1. 空输出重试**从不触发**（判为空的条件不成立）
2. 一路走 sanitize → 补 default → 骨架八段 → 记成"LLM 未返回可用分析"

换句话说：**我们有重试机制，但触发条件看错了地方。**

### 修法

新增纯函数 `is_skeleton_result()`：四个正文键
（`reasoning` / `reasoning_path` / `asset_nature` / `asset_reasoning`）
正文合计 < 30 字即判骨架。把空输出重试的条件扩成 `空 || 骨架`，
重试成功也要求"非空 且 非骨架"。

正常 HOLD 的短 JSON 光 reasoning 就 40+ 字，不会误伤（有用例守着）。
用例：`tests/test_v342_skeleton_result.py`（4 条）。


## 二十一、实测 "<think> 吃掉全部额度" —— 并找到唯一有效的解法

### 现象（直连探测，绕开所有业务代码）

对同一个端点发最小请求，模型返回的 content **全是 `<think>`**，
`finish_reason=stop`，正文一个字没有：

| max_tokens | finish | 输出 tokens | 有正文吗 |
|---|---|---|---|
| 200 | length | 200 | 否（全是 think） |
| 800 | stop | 117 | 否（全是 think） |
| 2000 | stop | 83 | 否（全是 think，但已经"想完"了） |

同一模型换个问法（"一句话：黄金第一驱动"）在 max_tokens=300 时**又能答**。
结论：**思考段长度不稳定，短预算时它把预算吃光，答案根本没机会输出。**

### 无效的尝试

- 传 `thinking:{type:disabled}` / `enable_thinking:false` / `reasoning_split:false` —— 全部无效，
  模型照样先写 think
- assistant 预填一段 think + "继续给JSON" —— 无效，它继续思考
- 单纯加大 max_tokens —— 只能提高概率，不能保证（且成本翻倍）

### 唯一有效：assistant 预填 `{`

```
messages = [user(prompt), assistant("{")]
```
模型从 "{" 直接往下写 JSON，**完全跳过思考段**，一次命中：

```
{"target_asset":"俄罗斯炼油厂","verdict":"值得深入分析","reason":"炼油厂遇袭可能影响原油加工…"}
```

已实现为 `_do_api_call(prefill="{")`：
- 预填时**不发送** `response_format=json_object`（两者互斥，部分网关 400）
- 返回时把 prefill 拼回原文，保证 JSON 完整
- 接在"空/骨架重试"之后作为最后一道：普通重试仍空 → 预填抢救

### 顺带发现：引擎其实**停着**

09:45 日志：`[FATAL] another engine instance is already running (single-instance lock held), exit`
—— 之前几次 `kickstart -k` 都在抢锁失败，**新代码根本没生效**。
更糟的是 `/tmp/trident_engine.lock` 被一个已退出的进程留下，
导致后续每次启动都直接 exit。清掉 stale lock 后重启，
09:49 起门卫恢复调用（19 次/10 分钟），积压的 72 条 PENDING 开始消化。

**教训**：`launchctl kickstart -k` 不等于"重启成功"。
必须回读 `[FATAL]` 与 `[BUILD]` 两行 —— 前者说明没起来，后者说明起来的是哪版代码。


## 二十二、恢复后的实测：管道通了，但模型仍"只思考不回答"

### 已恢复

- 清 stale lock 后单实例运行（pid 15266 起）
- `[BATCH-RESULT] 成功 8 / 失败 0` —— 认领与分析循环正常
- `ai_decisions` 从 314 涨到 327，新行开始出现

### 但降级仍在

| 新的决策 | 品种 | 结论 | 降级 |
|---|---|---|---|
| #11747 | INDIVIDUAL_STOCK | HOLD | 否（真分析） |
| #11748 | XAU | HOLD | llm_empty |
| #11749 | WTI | HOLD | llm_empty |
| #11750 | NONE | HOLD | target_none |
| #11751 | CN_STOCK | HOLD | server_fallback |

### 预填 `{` 在生产里**不成立**

日志：`预填 '{' 仍无正文，保留兜底` ×2。

复测发现关键差异：**预填只在该模型"没有 system 消息"时有效**。
一旦有 system（生产里主 prompt 就是 system），模型无视预填、照样先写 think：

| 场景 | 结果 |
|---|---|
| 无 system + 预填 `{` | 第一次成功，再测又失败 |
| 有 system + 预填 `{` | 失败（直接进 think） |
| system 强令"禁止思考" + 预填 | 失败 |

结论：**同输入两次结果不同 —— 这是模型侧的非确定性缺陷，不是 prompt 能修的。**
顺带验了 MiniMax 原生端点 `/v1/text/chatcompletion_v2`：HTTP 529（过载），不可用。

### 结论与出路

本地能做的手段已经用尽：关思考参数、预填、加预算、重试，全部只能提高概率，
不能保证。**根治只有换端点。**

为此新增了与门卫对称的口子（填 env 即生效，不改代码）：

```env
MAIN_ALT_BASE_URL=https://api.deepseek.com/v1
MAIN_ALT_API_KEY=sk-xxxx
MAIN_ALT_MODEL=deepseek-chat
```

权重 6（高于原 main 通道），max_tokens 4000，超时 65s。

### 主通道本身是健康的

| 指标 | 实测 |
|---|---|
| 输入 tokens | 12.2K–12.8K |
| 输出 tokens | 921–1358 |
| 延迟 | 20–41 秒 |
| 状态 | 全部 `ok` |

也就是说：**模型在正常出 1000 token 的八段**，但同一批里仍有调用返回空内容。
所以 `llm_empty` 不是"模型不会答"，而是**部分调用返回空响应**（超时/端侧抖动）。

### 结构性瓶颈已明确

`两步抢救` 有窗口限流（`TRIDENT_TWO_STEP_RESCUE_LIMIT`，默认 **6 条 / 10 分钟**）。
实测日志多次出现「窗口已用 5/6」「6/6」→ **抢救额度先于模型能力用尽**。
每条新闻要 2 次额外调用，一个 8 条的批次就要 16 次 → 窗口只给 6 次，剩下全靠兜底。

这就是"降级率降不下来"的直接原因，而且它是**配置量**，不是模型量。
