# v480 · 两处修复（跨资产量纲 / gate 超时）

日期：2026-11-19 · 项目：金融1.0（Reflex Quant / Trident）

## 一、`/api/discovery/cross-asset-rankings` 量纲混用（已修）

### 现象

涨幅榜出现 `NDX +2,448,212%`、`TENCENT +173,733%`。`latest=3.79e13` 对 `earliest=1.55e9`。

### 根因

`external_indicators` 表把同一资产的**价格 / 成交额 / 成交量 / 涨跌%** 存成不同 `indicator`
（如 `tencent_price`、`tencent_amount`、`tencent_volume`、`tencent_change_pct`）。
`discovery.cross_asset_rankings_handler` 按 `asset` 分组，于是把成交额和价格混成一条序列算涨跌。

同理，BTC 下面 50+ 个派生指标（资金费率、多空比、持仓量、链上手续费…）也被当成"资产"参与涨跌排行，
这些指标的"变化百分比"没有交易含义。

### 改法（`backend/src_python/discovery.py`，备份 `.bak-v480`）

1. 分组键从 `asset` 改为 `(asset, indicator)`；
2. 只允许价格类指标入榜：名字含 `price/close/last/median`，且不含
   `amount/volume/change_pct/ratio/funding/open_interest/supply/fee/mempool/hashrate/dominance/basis/skew/iv/dvol/taker/count/usd/_mb/_tx`；
3. 每个资产只保留一条序列：优先 `tencent_price`，其次条数最多的；
4. 量纲上限：1h ±25%、24h ±60%、7d ±200%、30d ±500%，超限的写入 `anomalies`，**不进涨幅榜**；
5. 返回体新增 `anomalies` 与每条的 `indicator` 字段（其余字段不变）。

### 验证（8100 实测）

| | 修复前 | 修复后 |
|---|---|---|
| 涨幅榜首位 | NDX +2,448,212% | NG +5.92% |
| NDX | +2,448,212% | +0.42%（`tencent_price`，27,116.26 对 27,001.78） |
| `anomalies` | 无此字段 | `[]`（当前窗口内无量纲异常） |
| `total_count` | 数百条（含派生指标） | 15（只有真正的价格序列） |

## 二、gate 通道成功率（已调参，未改判定语义）

### 现象与纠正

`/api/llm-stats/summary` 显示 `gate` 5,241 次调用、ok 仅 2,469 次（47%）。
**但失败记录的 `tokens_in=0`** —— 失败不烧 token，烧的是时间。

### 实测分布（近 24h，5,864 次 gate 调用）

| 指标 | 数值 |
|---|---|
| 成功中位耗时 | 5.9s（P90 13.7s） |
| 失败中位耗时 | 12.9s |
| 单次最长 | 157s |
| 失败错误 | `read timeout`（`realtime_filter._post_openai_compat` 归类为 network） |
| 高峰 | 每分钟 50–68 单时失败率 30–45% |

单条直连手测 1.0–1.3s 正常 → 不是模型或 key 的问题，是高频调用下延迟升高撞超时。

### 改法

| 位置 | 改动 |
|---|---|
| `backend/.env` | `REALTIME_GATE_TIMEOUT_S` 12 → **10**（备份 `.env.bak-v480`） |
| `backend/src_python/realtime_filter.py` | `_GATE_TIMEOUT_S` 默认 25.0 → **10.0**（.env 覆盖时以 .env 为准） |

重试次数保持 2（`_post_openai_compat` 是 L2/L3 共用函数，主分析一次成功更值钱）。
最坏单条等待从 12s×2+1s ≈ 25s 降到 10s×2+1s ≈ 21s；此前实测出现 56s/157s 的长尾不再由超时造成。

### 验证（改后 2.5 分钟窗口）

| | 改前（近 24h） | 改后 |
|---|---|---|
| 成功/失败 | 2,918 / 1,936（约 60/40） | 6 成功 / 1 失败（7 次） |
| 最大耗时 | 157s | 14.6s |
| 失败最大耗时 | 157s | 12.4s |

样本仍小，需继续观察满 24h 再评估。

## 三、仍未改（需单独决策）

- **gate 主备通道同时发请求**：每条新闻向 gate 主通道与备用通道并行发出，谁先回用谁。
  这会把通道负载翻倍、推高延迟，也会让成功的调用计费两次。改动涉及"冗余保障 vs 成本"，
  不能顺手改，需要单独评估。

  是否改为规则层兜底（`gate_fallback=rule`）属于判定口径变更，未做。


## 四、请求预算「被失败请求吃光」（已修）

### 现象

`LLM_DAILY_REQUEST_BUDGET=9000`，今日（11-19）已用 7,285 次 = **81%**，
但 token 只用了 7.38M / 40M = **18%**。也就是说：钱还没花多少，请求额度先见底。

### 根因

`llm_budget.usage()` 的请求口径是 `COUNT(*)`，**把失败也数进去**。
而 gate 的失败（`read timeout`、429）记录里 `tokens_in=0` —— 实际不花钱。
于是：
1. gate 失败把请求预算提前吃掉；
2. 预算到线后闸门拦 gate；
3. 新闻不再过门卫，全部直送主分析（单条 ~13k token，是门卫 ~280 的 16 倍）；
4. token 反而更快打穿 40M → 整条链路停摆。

这就是 `.env` 里 2026-11-17 那段事故注释描述的机制，只是当时归因到"用量涨了"，没发现是口径把失败算成了消费。

### 改法（`backend/src_python/llm_budget.py`，备份 `.bak-v480`）

`usage()` 与 `usage_by_purpose()` 的 SQL 都加了条件：

```sql
AND (status = 'ok' OR (tokens_in + tokens_out) > 0)
```

含义：**只数真的会计费的请求**。计费的失败（有 token）仍然算；零 token 的
网络失败 / 429 不再占预算。本地通道仍排除。

### 验证（今日实时）

| 口径 | 请求数 | 预算占用 | token |
|---|---|---|---|
| 旧（含失败） | 7,285 | 81% | 7.38M |
| 新（只数计费） | 4,608 | **51%** | 7.38M |

释放出约 2,700 次请求额度，且 token 口径完全不变（没有放松花钱的闸门）。

`llm_budget.usage(refresh=True)` 实测：`{'tokens': 7385033, 'requests': 4608, 'news': 380}`。

## 五、结论：gate 本身没有"双通道重复烧钱"

核查 `config.AI_MODEL_ROSTER`：`purpose=['gate']` 的通道**只有一条**
`minimax-gate/MiniMax-M3.1-Flash`（备用 `minimax-gate2` 因 key 与主 gate 相同而没有创建）。
且 `GATE_REMOTE_STAIR_STEP=1` 已经生效：第 1 级只打 weight 最高的单条通道，
其余通道仅在它失败后才并行兜底。

所以此前「主备同时发、成功也计费两次」的判断是**错的**，已更正；不需要再改并发逻辑。

gate 还有两层去重：
- `GATE_CACHE_TTL_S=21600`（6 小时）整段 prompt 级缓存；
- `_gate_title_fp()` 标题指纹缓存（抹平 hash 前缀/标点/空白/大小写）。

## 六、真正的省钱空间（未动，需决策）

近 7 天 token 分布：

| 调用点 | 次数 | 入 | 出 | 缓存命中 | 单次入 |
|---|---|---|---|---|---|
| ai_worker_main | 2,260 | 29.83M | 2.74M | **8.5%** | **13,197** |
| realtime_filter | 20,851 | 5.84M | 3.11M | 0% | 280 |
| ai_worker_failover | 271 | 3.61M | 0.31M | 18.9% | 13,332 |
| ai_worker_verify | 2,022 | 1.56M | 0.39M | 28.5% | 771 |

主分析占全部输入 token 的 **70%**，单次 13,197 token，而系统提示词本身 17,164 字符
（日志 `[CACHE-DBG] syslen=17164` 长期不变），缓存命中只有 8.5%。

可动的三处，按性价比排序：
1. **提高前缀缓存命中**：system 段已稳定（`sysfp=73d690df69` 不变），但命中率仅 8.5%，
   说明 MiniMax 侧缓存没按预期生效，或动态段（绩效/复盘经验）混进了前缀。
   把动态段全部移到 user 消息尾部，理论上可让 17k 字符 system 段每次都命中。
2. **failover 复用主 prompt**：271 次 × 13.3k ≈ 0.24M/天，都是整段重发。
3. **system 提示词收敛**：17,164 字符里存在重复条款，压缩 30% ≈ 省 4k token/次。
   —— 这条会改分析口径，必须单独评审。
