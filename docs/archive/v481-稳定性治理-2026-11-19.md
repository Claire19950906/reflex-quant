# v481 稳定性治理（2026-11-19）

## 一、结论：不是服务本身脆，是四件事叠在一起

| # | 机制 | 干了什么 | 后果 |
|---|------|----------|------|
| 1 | `com.trident.frontend-prod` | 第二份 Next 服务，占 3031 | 白吃内存，和 3030 抢资源 |
| 2 | `com.trident.frontend-rebuild-cron` | 每小时 `next build` + `kickstart -k` 前端 | 8G 机器上每小时一次构建尖峰，前端每小时换进程 |
| 3 | `restart_backend.sh` | `bootout` engine/watchdog 后 `bootstrap ... \|\| true` | launchd 偶发 `5: Input/output error` → 引擎/看门狗**永久消失**，此后没人管引擎 |
| 4 | 外部并发操作（另一路会话 / swap_plist_pause） | 把 116 个 `com.trident.*.plist` 移出 `~/Library/LaunchAgents` | 整套定时任务与核心服务从 launchd 消失，8100 与引擎全无 |

## 二、处置

1. 停用 `com.trident.frontend-prod`、`com.trident.frontend-rebuild-cron`（bootout + disable，plist 改名 `.disabled-v481`）。
2. 加固 `restart_backend.sh`：新增 `ensure_job()`——先 `launchctl print` 查在不在，`enable` 后重试 5 次 bootstrap，再校验；engine / watchdog / bridge 都用它，不再静默丢服务。备份 `.bak-v481`。
3. 新增 `~/.trident/wrappers/ensure_core_jobs.sh` + `com.trident.ensure-core-jobs`（30 秒一轮）：
   - job 不在 launchd → `enable` + `bootstrap`（重试 3 次）；
   - job 在但没进程 → `kickstart`。
   只挂回、不杀进程，日志 `~/.trident/log/ensure_core_jobs.log`。
4. 归还被移走的 plist：`~/.trident/swap_plist_pause/*.plist` → `~/Library/LaunchAgents/`，逐个 bootstrap 110 个，0 失败。

## 三、验证（16:31）

- `launchctl list | grep -c com.trident` = 119；
- 8100 `/api/health` = 200，3030 首页 = 200；
- 页面关键接口全 200：`/api/trident2/features`、`/api/input-layer/snapshot`、`/api/decision-thresholds/recent`、`/api/market/es`、`/api/ledger/overview`；
- 只剩 1 个 next-server（pid 22477），3031 已关闭；
- load 从 198 回落到 87（15 分钟均线仍在衰减）。

## 四、仍存在的风险

- 机器 8G，DoubaoWork 渲染进程常驻 1.3–1.5G、Chrome 500M+，可用内存长期在 1G 以下；内存守卫只告警不回收。
- 外部会话仍可能再次调 `restart_backend.sh` 或移走 plist；现在有 30 秒兜底，但**兜底不是根治**，需要约定「同一时间只有一个会话做重启/安装」。
- `.next-prod-old-*` 备份约 1.3GB 未清理。
