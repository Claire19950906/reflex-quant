# v412 · 行情快照「0/9 OK → down → 降级 HOLD」修复

**一句话结果**：快照从 `DOWN (0/9 OK) in 18.8s` 变成 `PARTIAL (9/9 有价) in 4.6–7.5s`；外盘依旧连不通（环境级），9 个标的改用**国内可直连的真实报价**，mtf 的 1d/4h/1h 也从"本地隔夜线"换成**真实交易所 K 线**（加密 Gate、商品 1d 新浪 + 4h/1h 东财），且每个周期都带可追溯来源；快照链路的每一段都有总预算，慢源再也不会把整段结果拖没。

**引擎侧已闭合**：`国内源补齐 8/9` + `K线补齐 15 个周期（sina_daily_k 2 / em_klines 4 / gate_klines 9）`，整份快照 **5.893s**（打底 0.5 / 远端 3.0 / 国内 2.4 / 装配 0.0）。

这条路走得很绕：先后三次判断都被实测推翻（"进程级 TLS 坏" → 其实是**引擎压根没重启**；"fork 子进程能绕开" → fork 后网络 IO 会挂到 timeout；"加预算就行" → 加到 8s 仍然卡在限制点）。最终解法是**文件邮箱**：抓取交给独立进程，引擎只读文件 —— 见 §8.8。

## 一、症状

引擎日志反复出现：

```
[SNAPSHOT] DOWN (0/9 OK) in 18.824s
[SNAPSHOT] 获取失败: RuntimeError: snapshot down/empty
```

随后整批新闻按降级路径产出 HOLD。11-16 当日 504 条决策里 443 条降级（87.9%），主因分布 target_none 264 / llm_empty 71 / summary_only 62 / server_fallback 33。

## 二、根因（三层，缺一层都不会全断）

| 层 | 事实 | 后果 |
|---|---|---|
| 环境级 | `www.okx.com` DNS 无解析（NO-DNS）；`fapi.binance.com` TCP 通但 TLS 被重置；`query1.finance.yahoo.com` 429 + SSL 失败；系统无代理（`scutil --proxy` 全 0）；`www.google.com` 302 正常 | 9 个资产的远端报价全部拿不到 |
| 代码级 | `_collect_asset` 里的**本地兜底写在远端调用之后**；`asyncio.wait_for(to_thread(...), 8.0)` 超时把线程整个丢弃 | 本地兜底永不执行 → `ticker=None` → 0/9 |
| 口径级 | `ok_count==0`（只数 `status=="ok"`）直接判 `down`；`_build_summary` 在 down 分支硬编码"所有标的拉取失败" | 即便本地有真实价也进不了 ok 计数，汇总仍说"全部失败" |

补充实测：`_okx_get` 在 DNS 不通时 `getaddrinfo` 能卡几十秒，线程挂在 socket 上不走超时返回，所以单靠"缩短超时"救不回来。

## 三、改了什么（`backend/src_python/market_snapshot.py`）

1. **本地优先打底**：`get_snapshot()` 开跑先用 `_rebuild_asset_from_local()` 把 9 个资产从 `market_ticks` + `ohlcv_daily/intraday`（`_local_mtf`）建出来，毫秒级；之后才给远端预算。
2. **远端硬预算**：`SNAPSHOT_REMOTE_BUDGET_S`（默认 3s）用 `asyncio.wait` 等远端，超时即 cancel，不再让挂死线程拖满整段。整次快照稳定在 5–6s，远低于引擎 `wait_for(get_snapshot(), 15.0)`。
3. **远端熔断**：`_trip_remote_breaker()` —— 远端 0 个资产可用时，接下来 120s（`SNAPSHOT_REMOTE_BREAKER_S`）直接走本地，不再每批去撞墙。
4. **状态口径修正**：新增 `usable_count`（`status in (ok, partial)` 且 `price>0`），`down` 只在 9 个全无价时成立；`partial` 不再被写成"所有标的拉取失败"。`get_snapshot_sync()` 同步为同一口径。
5. **日志可复核**：`[SNAPSHOT] PARTIAL (0/9 直连 OK, 9/9 有价)` —— 直连数与本地产出数分开记，不再用单一 "OK" 掩盖本地兜底。

纪律没动：本地兜底只用库里真实存在的 tick/bar，取不到就 `None`，不补价、不跨源拼价；本地来源一律标 `partial` + "本地行情兜底（外网直连失败）"，不冒充外网直连。

**口径规矩（这层最容易出错的地方）**

1. **说明跟来源走，不跟资产走**。`_note_for(asset, source)`：同一个 BTC 走 Gate 说"Gate.io 现货成交价"，
   走新浪说"新浪外盘 hf_BTC"，走腾讯说"腾讯外盘 hf_GC（COMEX 期货代理，非现货）"。
   之前按资产映射，导致 BTC 落到新浪备份时仍写着"Gate.io 现货成交价"——**同样的数字、不同的来源，说成一样就是失真**。
2. **熔断按"源+品种"**。`gate:BTC` / `gate:ETH` / `gate:SOL` 各自独立，ETH 超时不连坐 BTC。
3. **不重试**。Gate/CoinPaprika `retries=1`：重试一次会把 3s 变 6s，整段预算被吃光（实测 `_domestic_tickers` 从 6.46s 降到 3.16s）。
4. **独立线程池**。`_DOM_EXECUTOR`（2 workers）：默认池会被 `_collect_asset` 里挂死的远端线程占满
   （DNS 卡住的请求 cancel 不掉），国内源排在后面直接饿死——这是"代码对但引擎里没生效"的真实原因。
5. **并行不串行**。`_dom_task` 在远端之前创建，总耗时 ≈ max(远端 3s, 国内 3–6s)，不是 3+6。
6. **`usBTC` 禁用**。腾讯 `usBTC` 是灰度迷你 ETF（≈28.74），不是 BTC 现价，列入 `_FORBIDDEN`。

## 七、mtf 多周期改用 Gate 真实 K 线（v412-B）

原来 mtf 的 1d/4h/1h 只有两个来源：远端（全断）和本地库。本地库的问题是**隔夜**——
实测 `[KLINE-LOCAL] WTI 1d 最新 23.6h 前 / 4h 3.6h 前`，拿它算"当前趋势"等于用昨天的方向
指导今天的决策。加密品种有便宜的替代：Gate 现货 K 线。

- **一次请求拿全三个周期**：Gate 拉 `1h` × 200 根（≈8.3 天），本地聚合成
  `4h`（42 根）/ `1d`（8 根）/ `1h`（48 根）。口径自洽（同一份 1h 序列），
  也避开了"分周期各打一枪"的并发拖慢（实测 9 个并发请求 4s 只回来 3 个周期）。
- **优先级**：远端直连 K 线 > Gate K 线 > 本地隔夜线。只覆盖 `source=local_kline`
  或缺失的周期，**不跨源拼**——远端已有该周期就不动。
- **来源可追溯**：每条 mtf 带 `source=gate_klines` / `source=local_kline`。
- **覆盖范围**：BTC/ETH/SOL 拿全 1d/4h/1h；XAU/WTI 见下面的补齐（v412-D）。
- **容错**：Gate 失败是间歇性 `SSLError`（实测约 1/3，与数据量无关），K 线改
  `retries=2 / timeout=2s`；实测单次 1–2s，最坏 4s，仍在 6s 国内预算内。
- **与报价并行**：`_dom_mtf_task` 与报价任务同时发起、同一个 `asyncio.wait` 等，
  不串行叠加预算（串行会变成 6s+6s，顶到引擎 15s 上限）。

[SNAPSHOT] 国内源补齐 9/9（Gate/新浪/腾讯；其余走本地）
[SNAPSHOT] K线补齐 9 个周期（Gate 现货 1d/4h/1h，替代本地隔夜线）

**故障可见性（08:02 那一轮的真实教训）**：引擎某次快照整波 `ConnectionReset` + `Timeout`
（gate/sina/coinpaprika 全灭），日志里"没有国内源那一行"，很容易被读成"代码没生效"。
现在**0 补齐也显式打一行**：

```
[SNAPSHOT] 国内源本轮 0 补齐（源全部失败或任务超预算）→ 保持远端/本地
[SNAPSHOT] K线本轮 0 补齐（Gate K 线抓取失败或超预算）→ mtf 仍用本地线
```

同时把国内源失败熔断窗口从 120s 收到 60s：源失败常是整波网络抖动，120s 会让"一次抖动"
变成"两批都没国内源"。

**总时限（v412-C）**：引擎外层是 `wait_for(get_snapshot(), 15.0)`，一旦超时整份快照被判 down。
实测单次耗时方差极大：`5.3s / 7.8s / 10.9s / 12.1s / 13.5s / 14.4s / 18.7s / 22.4s / 30.4s`——
根因**不在国内源**，逐层查出来是：

| 拖慢点 | 实测证据 | 改法 |
|---|---|---|
| 本地打底逐个库查询 | 库被引擎自己写锁住时，单次只读等满 3s；9 个资产 × 2 次查询 → 22.4s | 只读超时收 1.5s；打底阶段加 3s 总预算，超了给空壳 |
| 技术读数（`_technical_state`）串在装配里 | 库锁时单次从 0.25s 涨到 2s+，9 个串行 = 十几秒 | **改为与取价并行预取**（独立 3 线程池），装配只做 O(1) 合并 |
| 前段等待吃满预算 | 远端 3s + 国内 4s 之后没有装配余量 | 加总时限，各段按"剩余−预留"动态限量 |
| **宏观读数抢写锁 + 慢 SQL** | `_fred_macro_latest()` 原用 `db.get_connection()`（**可写连接 + timeout=5s**）；改只读后单查 0.9s，但引擎写库时实测 3.8–4.4s（每批都在关键路径上） | 三层：①只读 `mode=ro`+`timeout=1.5`；②进程内缓存（宏观是日度）；③**改为与取价并行预取**，装配只接收结果。缓存 TTL 曾设 300s，正好等于引擎快照冷却 300s → 每次必过期（等于没缓存），改 3600s |

总时限参数（`SNAPSHOT_TOTAL_BUDGET_S` 默认 11s；远端 3s、国内 4s 都被它约束）：

```
[SNAPSHOT] PARTIAL (1/9 直连 OK, 9/9 有价) in 7.506s
          （打底 0.3s / 远端 3.0s / 国内 4.0s / 装配 0.2s）
```

阶段耗时直接打进汇总行——下次再出问题，一眼就知道是哪一段。引擎侧实测（09:5x）：

```
11.585s（打底 1.0 / 远端 3.0 / 国内 3.7 / 装配 0.0 + 宏观 3.8）   ← 宏观还在关键路径
 7.458s（打底 0.3 / 远端 3.1 / 国内 4.0 / 装配 0.0 + 宏观 0.0）   ← 宏观改并行后
```

对外层 15s 来说，余量从 3.4s 涨到 7.5s。装配内部还加了逐资产慢日志
（单个资产 >0.5s 才打，`装配慢 XXX 1.20s（light=False tech=预取）`），避免"装配 4.8s"
这种笼统数字找不到出处。
装配阶段还剩一层兜底：预取没覆盖到的资产，第一次读数若 >1.2s 就**熔断**、
其余资产直接标 `available=False`（并写明"库锁导致读数变慢"），绝不逐个去等。
这比让整份快照被 15s 外层取消、整批降级 HOLD 划算得多。

- **limit 无效**：`lmt=200/500/1000`、`beg=0/20260101` 全部只回 **118 根 1h**（≈5 个交易日）。
  够 4h/1h（聚出 31 个 4h 桶），**不够 8 根日线** —— 所以商品 1d 仍由新浪日线负责，不能拿东财顶。

  「收」在「高」前面。照抄 Gate 的开高低收会把最高价和收盘价写反，趋势/ATR 全错且快照上看不出来。
  单测 `test_em_klines_column_order` 钉死这个顺序。

### 8.2 东财的可靠性矩阵（本轮最有价值的结论）

| 实验（同机同时段） | 结果 | 含义 |
|---|---|---|
| 每请求新建 Session，同一 secid 连测 10 次 | 5/10（50%） | 失败是 `RemoteDisconnected`，0.2–1s 就断，不是超时挂住 |
| 复用同一 Session keep-alive，同一 secid 连测 12 次 | 11/12（92%） | 同连接连续打**同一个** secid 很稳 |
| 复用同一 Session **交替请求两个 secid**，各 10 次 | **0/10 全失败** | 同连接换 secid 会被服务端重置 |
| 每请求**独立** Session，`101.GC00Y` 8 次 | **8/8** | 独立连接 + 间隔 0.3s 最稳 |
| 每请求独立 Session，`102.CL00Y` 8 次 | 0/8，间隔 1s 后 3/3 | 短时间内连发会被按秒限流 |

由此定的实现（`em_klines_many`）：**每品种独立连接 + 品种间 `sleep(0.3)` + 重试递退 0.4/0.8/1.2s**，
不是共享 Session 串行。

### 8.3 来源标记必须按周期分开（两处踩坑）

1. 同一个资产的 1d 和 4h/1h 是**不同源**（商品：新浪 + 东财），
   写成一个 `_source` 必污染口径 → 拆成 `_source_1d` / `_source_intraday`。
2. **只在"确实拿到数据"时才设来源**。原实现末尾无条件 `setdefault(_source_intraday,"gate_klines")`，
   会让"没补上"被上层读成"已补" → 改成 `if "1d" in per` / `if "1h" or "4h" in per` 才 setdefault。
   单测 `test_sina_daily_only_feeds_1d` 锁这条。

还有一处更隐蔽的：本地兜底（`_fetch_asset_klines` 内部退回 `kline_bars`）**返回值看不出区别**，
WTI 的 mtf 曾因此 `source=None` —— 既不是真实交易所线，也没标成本地线。
现在用 `_LOCAL_FALLBACK_MARKS[(asset,interval)]` 打时间戳，回退的周期显式标 `local_kline`，
真实外网 K 线标 `remote_kline`，**任何周期都不允许 source 为空**。

### 8.4 熔断键必须按源分开

东财失败原写 `mtf_d:{asset}`，会把新浪日线的熔断一起打开（WTI 明明日线能取，却被连坐停 60s）。
新增 `_cooldown_key(kind, asset)` → `mtf:{a}`（Gate）/ `mtf_d:{a}`（新浪日线）/ `mtf_em:{a}`（东财）。

### 8.5 总预算是这一层最容易被忽略的地方（v412-E）

引擎给国内段 4–5s，但三个源的**超时是叠加的**：

- `fetch_all`（报价）原来是「每个源各等 4s」+ `with ThreadPoolExecutor`（退出默认 `wait=True`），
  新浪单请求 3s、重试 2 次≈6s → 整组被拖到 6–10s，`gate`/腾讯**已经拿到**的结果也被超预算丢掉。
  引擎侧连续多次「国内源补齐 0」正是这个形态，而同一时刻独立进程能取到 8–9/9。
- 修法：一次性总预算 `_cf.wait(jobs, timeout=_QUOTE_BUDGET_S=2.5)`，CoinPaprika 兜底再给 0.8s，
  池子 `shutdown(wait=False)` 不等慢线程。上限 ≈3.3s。
- `fetch_mtf` 同理：`_cf.wait(..., timeout=_MTF_BUDGET_S=3.0)`，东财再等 `min(EM_WAIT_S=2.0, 剩余)`，
  池子不 wait=True。实测稳定 3.0–3.2s。
- 东财不能放在 gate 之前阻塞等待：原来主线程先 `em_fut.result()` 再收 gate 结果，
  东财一退避就把预算吃光，连带已经拿到的 gate/新浪一起丢 → 改成**先收 gate/新浪，再给东财有限等待**。

### 8.7 仍然不是 100%

东财是**机会源**：单进程连跑会出现「run0 只成 XAU / run1 两个都成」的波动（速率限制 + 连接重置）。
定位是「有则用、无则回落本地线并标注 `local_kline`」，不是「保证每个小时都有真实 4h 线」。
若后续要 100%，需要换更稳的源（英为财情 `HistoricalDataAjax`、同花顺未实测），
或接受用东财 `klt=101`（日线，8 根）替代新浪日线 —— 目前不做，因为新浪日线已验证更稳。

### 8.8 引擎侧 0 补齐：三个被实测推翻的判断，和解法

这一节是整轮最贵的部分——**连续三次"看起来有据"的结论都是错的**，写下来是为了以后不再重走。

#### 判断一（错）：引擎进程对这批域名的 TLS 整体不可用

依据：同一时刻终端 `curl push2his` 200、`curl qt.gtimg.cn` 正常，而引擎日志里 `tencent 熔断：预算内未返回` / `gate:BTC ConnectionReset(54)` / `sina TimeoutError`，`engine.err.log` 里 `yfinance SSLError` 累计 3,384 行；代理已排除（`backend/.env` 的 Network Proxy 段全部注释、`MARKET_USE_PROXY=false`）。

**推翻方式**：查进程。`[FATAL] another engine instance is already running (single-instance lock held), exit` —— 每次 `launchctl kickstart -k` 后新实例都被单例锁拦退，**旧进程一直活着**（`ps -o etime` 显示已跑 8 分 26 秒）。也就是说那几轮"重启后验证"，验证的是**旧代码**，日志里读到的自然是旧行为。不是引擎网络坏，是我没确认进程真的换了。

> 教训：`kickstart -k` 不等于"起来了"。必须 `pgrep` + `ps -o etime` 确认为新 pid，且 `tail` 日志里不能有 `single-instance lock`。

#### 判断二（错）：把抓取 fork 到子进程就能绕开

依据：同一个 `domestic_runner.py` 在终端跑 **4.8s** 返回真实周期（run2 拿到 BTC+SOL 三周期、run3 拿到 XAU 1d + ETH 三周期）。

**推翻方式**：在引擎里，子进程**每次都恰好在 timeout 点被杀**——限 3.5s 是 3.5s、限 6.0s 是 6.1s、限 6.5s 是 6.6s、限 8.0s 是 8.1s。这不是"差一点"，是**挂死到被打死**。这是 macOS 上多线程进程 fork 之后做网络 IO 的经典死锁形态：父进程的 resolver/连接状态被复制过去，子进程卡在里面。

#### 判断三（错）：预算不够，加就行

一路从 2.5s → 5.0s → 7.5s → 8.5s 加上去，子进程始终"刚好超一点"。8s 都不够，说明**它不是慢，是卡住**。死锁加预算等于白送时间。

#### 解法：文件邮箱（抓取与引擎彻底分进程）

```
launchd（每 45s，独立进程）
   └─ feeds/domestic_refresh.py
        ├─ fetch_all   → ~/.trident/cache/domestic_quotes.json  {"ts","mode","data"}
        └─ fetch_mtf   → ~/.trident/cache/domestic_mtf.json
引擎（不碰网络、不 fork）
   └─ market_snapshot._domestic_from_cache(mode)
        ├─ ts 新鲜（TTL 180s）→ 直接用
        └─ 过期/缺失        → 回落进程内 fetch（仍如实标 source）
```

| 设计点 | 为什么这么做 |
|---|---|
| 独立进程抓取 | 刷新器是全新进程，没有引擎那堆线程/连接状态，实测 4.86s / 4.52s 稳定返回 |
| 原子写 `os.replace` | 引擎读不到半个文件 |
| `ts` + TTL 180s | 缓存再快也不能当"实时"；过期就回落，宁可没数据也不给旧价 |
| 刷新器取不到就**保留旧缓存** | 旧数据好过没有，但引擎侧靠 TTL 判断它是否已过期 |
| 引擎不再 fork | 彻底避开 fork-after-fork 死锁 |
| `_domestic_via_subproc` 保留原名 | 调用点不动，只换实现，减少回归面 |

launchd：`~/Library/LaunchAgents/com.trident.domestic-refresh.plist`（`StartInterval=45`、`RunAtLoad=true`），日志 `~/.trident/log/domestic_refresh.err.log`。

#### 实测结果（真正重启后的引擎，pid 31057）

```
[SNAPSHOT] 远端补齐 1/9（预算 3.0s，本地打底 9）
[SNAPSHOT] 国内源补齐 8/9（Gate/新浪/腾讯；其余走本地）
[SNAPSHOT] K线补齐 15 个周期（sina_daily_k 2 个、em_klines 4 个、gate_klines 9 个，替代本地隔夜线）
[SNAPSHOT] PARTIAL (2/9 直连 OK, 9/9 有价) in 5.893s
          （打底 0.5s / 远端 3.0s / 国内 2.4s / 装配 0.0s+宏观 0.0s）
```

#### 顺手挖出的第四个真 bug：`_t0` 未定义

装配硬保护（超过 `_deadline+1.5` 就放弃精装、保住价格）写成了 `(_t0 + 14.0)`，但 `get_snapshot` 里的变量叫 `t0`。结果那几轮快照前面明明已经拿到 `国内源补齐 7/9`、`K线补齐 7 个周期`，最后一行却是：

```
[SNAPSHOT] 获取失败: NameError: name '_t0' is not defined
```

一份快照因为一个变量名从"8/9 有价"变成"整份失败"。改完之后立刻是 8/9 + 15 周期 + 5.893s。

> 教训：新增分支必须跑一次真实调用再交付。`ast.parse` 只证明语法对，不证明变量存在。

#### 装配 9.8s 的真相（已证实）

`装配慢 ETH 7.71s（light=True tech=无 内部=7.71s 事后=0.00s）` —— 时间全在 `_assemble_asset` 函数体内，而 light 分支没有任何 DB 调用，所以这 **7.71s 是被抢占的等待**（引擎满载时线程拿不到 GIL），不是真实工作量。真实重启后装配回到 **0.0s**，也反证了这一点。

## 九、「改代码 ≠ 改行为」的边界

- 本次改的是**快照能不能算出价**，不是"能不能赚钱"。9/9 有价只保证模型看得见价格，方向对不对仍取决于新闻与分析质量。
- `partial` 的含义是"**国内源代理价或本地兜底价**"，不是"外盘实时价"。腾讯 `hf_GC` 是 COMEX 黄金期货、不是 XAU 现货，存在期现价差；美股/韩股给的是**收盘价**，非盘口实时。任何用这份快照做的复盘，都不能说成"基于外盘实时行情"。
- `ok` 只给 Gate 现货与真正的交易所直连；**不要把 `partial` 当成 `ok` 统计直连率**。
- 本地兜底价的新鲜度取决于 `market_ticks` 与 `ohlcv_*` 的写入：本轮 `[KLINE-LOCAL] WTI 1d 最新 23.2h 前` 说明部分品种日线已隔夜，需与"实时"区分表述。
