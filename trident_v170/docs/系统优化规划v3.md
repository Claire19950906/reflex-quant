计算输出：
```
盘面结构（XAU 1h）：

  趋势阶段: 中期（结构完整，未到末段衰竭）

  关键位: 支撑 4550（前低）/ 阻力 4620（前高）

  建议: 顺势做多为主，回踩 4550 附近是入场参考，跌破 4520 结构转弱
```

### 结合 AI 的方式
1. **决策上下文注入**：AI 分析新闻时，decision_context 附带盘面结构层（现有快照扩展）→ AI 结合盘面判断：顺势/逆势、入场节点、止损位
2. **新闻 × 盘面匹配**：
   - 利多新闻 + 盘面上升趋势 → 高置信 BUY（顺势）
   - 利多新闻 + 盘面下降趋势 → 降置信（逆势，可能只是反弹）
   - 冲突类突发 + 盘面关键位 → 判断突破概率
3. **止损位参考**：盘面关键位（支撑/阻力）+ ATR → 量化止损建议

## v170 P0+ 增量（trade_uuid 全链路 + 应急对账）

### 背景
v170 Phase 1-7 修复后仍存在一个**数据完整性盲区**：`ai_decisions` 与 `trade_reflections_v2` 之间没有显式主键串联，所有交叉查询都依赖 `decision_id` 隐式关联。一旦 `decision_id` 因重构、删除或跨表重命名失效，paper ↔ reflection 链路就静默断开，且无任何告警。v3 文档的 XLSX 导出也未暴露 trade_uuid，排障时只能靠用户逐行对 `id`。

### 三字段对账模型
| 字段 | 角色 | 来源 |
|---|---|---|
| `trade_uuid` | 全链路**身份 ID**（跨 5 表唯一） | `ai_decisions.id` → UUID v5 namespace |
| `decision_id` | ai_decisions ↔ reflection 内部 FK（脆弱） | 各自 `id` |
| `alert_id` | 单次对账事件的指纹（去重 / 幂等写） | UUID v4 random |

### P0 应急对账（已上线）
- **Schema 迁移**（`id_reconcile.ensure_schema`）：
  - 新增 `id_reconcile_alerts` 表（id / alert_id UUID / alert_type / severity / trade_uuid / reflection_id / decision_id / source_table / payload / 解决时间戳）
  - 给 5 链路表加 `trade_uuid TEXT` + `quarantined_at TEXT` + 5 个 unique/index
  - **幂等**：重复运行 `migrate` 只写新索引（`added_columns: []`）
- **Backfill**（`id_reconcile.backfill`）：1321 ai_decisions / 55 reflections / 534 structured / 99 errors / 56 quick_sim 已写 trade_uuid；残留 orphan / missing_uuid 一次性落 alerts 表
- **三类型错配检测**（`check_mismatches`）：
  - `missing_uuid`：链路表中 trade_uuid 为空（影响 history 完整性）
  - `orphan_reflection`：reflection 的 decision_id 在 ai_decisions 已不存在（schema 重构痕迹）
  - `mismatch`：UUID 串联后 entry_price / entry_time 字段不一致（**最高严重级 critical**）
- **自动 quarantine**：错配 ≥ 0.5% 阈值自动打 `quarantined_at` 时间戳，dashboard / XLSX 默认排除
- **双保险机制**：
  - 保险 #1：`api_server.py` lifespan `_migrate_schema()` 钩子（冷启动）
  - 保险 #2：`com.trident.id-reconcile.plist`（launchd，StartInterval=300 每 5 分钟）
  - 保险 #3：手动 5 个 admin 端点（见下）

### 端点 404 修复教训
最初 5 个 admin 端点 + status 都返 404。**根因**：`api_server.py` 文件末尾的 `if __name__ == "__main__":` 块位置**在 admin 端点之前**——`uvicorn.run(app, ...)` 是同步阻塞调用，会让后续模块顶层代码（含 `@app.post` 装饰器）**永远不执行**，路由不会被注册到运行中的 app。
- **诊断技巧**：在 `__main__` 块里 `print(len(app.routes))` + `grep id-reconcile` 一抓一个准
- **修复方案**：把 `__main__` 块整段挪到文件**末尾**（admin 端点装饰器之后），保证所有路由先注册再启动 uvicorn
- **验证**：inline `python3 -c "import uvicorn; uvicorn.run(api_server.app, ...)"` 能跑（因为 import 阶段所有装饰器已执行），但 `python3 api_server.py` 走 `__main__` 路径触发 bug
