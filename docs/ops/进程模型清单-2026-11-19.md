## 六、后续收敛方向（P2，不在本次改动范围）

1. **统一生命周期**：常驻 / cron / 守护三类用同一套启动器与健康检查；cron 脚本不得自带 `while True`。
2. **重复作业合并**：先解决日志轮转双份；再排查间隔触发里功能重叠的采集/反思作业。
3. **退出码纳入监控（已落地只读扫描）**：`runtime_metrics._launchd_jobs()` 只读解析 `launchctl list`，把每个 `com.trident.*` 作业的上次退出状态归类为运行中 / 正常退出 / 信号终止（-15 SIGTERM、-9 SIGKILL 等）/ 非零退出码，异常项进 `metrics.jobs.abnormal`，随 `/api/health/metrics` 暴露。当前实测异常：`master` 退出码 3、`bridge` SIGTERM(-15)。后续若要持久化退出历史（按时间累计重启次数），再落事件表；当前为实时只读快照。
4. **一次性脚本不进 daemon 循环**：backfill/回填类脚本确认是「跑完即退」，不要被包成常驻线程。
5. **写者收口（联动并发锁排队）**：SQLite 单写者，多进程/多线程并发抢写会排队等锁。并发长事务根治的一部分就在这里——收敛并发写进程/线程、必要时单写者队列串行化；与 P1-1 分域、短批量事务一起在低峰窗口推进。先开 `TRIDENT_WRITE_PROFILE=1` 采集 commit 本身耗时，区分"持锁执行慢"与"排队等锁慢"。
