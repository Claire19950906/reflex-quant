# v414 · 分析产能体检（2026-11-17）

> 一句话：**把「降级 87%」拆成五个能动手的桶，并且把每个比例的分母写进字段名。**
> 只读功能：不写库、不改分析链、不自动重试。

## 1. 为什么做这个

日报里的「降级 461 / 528」是一个数字，但它装着五种完全不同的事实：

| 事实 | 该不该算失败 | 该做什么 |
|---|---|---|
| 品种不在服务范围（A股个股、桶标签） | 不算 | 从分母剔除 |
| 证据没就绪（feed_stale / 无本地源） | 算 | 修数据源 |
| 模型没返回（空输出/超时/服务端兜底） | 算 | 重试 |
| 输出结构不达标（只剩摘要/缺字段） | 算 | 改 prompt/契约 |
| 有方向但只给了摘要（compressed） | 不算 | 只观察 |

一个数字治不了五种病，于是「89% 降级」成了谁也不动的指标。
口径本身在 `analysis/contract.py` 里已经写死了（六终态），缺的只是**按终态聚合的出口**。

## 2. 本来要做的是「标的词典闭环」，为什么改了

先跑了现成的只读审计（`python3 -m feeds.news_asset_router --audit --days 7`）：

```
近 7 天 NONE 行 176 条
  direct 6 / transmit 2 / weak 3 / noise 1 / none 164
  可救回（能定主品种） 8 条 = 4.5%
```

93% 的 NONE 是**真的无关**（俄罗斯暴利税、议长行程），不是漏判。
词典闭环一周最多救回 8 条新闻，投入产出不成立，**所以本轮不做**（不是否决，是排到后面）。

同一窗口的降级构成（`ai_decisions.analysis_degraded_reason`）：

| reason | 条数 |
|---|---|
| target_none | 172 |
| asset_late_bound | 122 |
| llm_empty | 73 |
| summary_only | 70 |
| server_fallback | 33 |
| 未降级 | 69 |

模型侧失败（llm_empty + server_fallback）一周 106 条，是**可以重跑**的量；
结构侧（summary_only + asset_late_bound）192 条，是改契约的量。两者都不是加功能能解决的，
但必须先能分开看 —— 这就是本功能。

## 3.1 顺着「真实失败」往下查，抓到一条通道（同窗口实测）

看板上「模型未返回 98 条」之后，先问一句：是调用挂了，还是调用成功但输出不够？

- 近 7 天主分析调用 **2868 次**，其中 `ok` 2863、`http_error 429` 只有 **5 次** → **调用层几乎没失败**。
- 但 `tokens_out` 分布：<200 **309 次（11%）**、200–600 **168 次（6%）**、600–1500 2287 次、≥1500 99 次。
  也就是说，约 **17% 的「成功」调用写不满八段**，它们落库后就是 `llm_empty / summary_only / parse_failed`。

按 `model_id` 拆开，问题立刻指向一个通道：

| model_id | 调用 | 平均输出 tokens | 短输出率（<600） | 判定 |
|---|---|---|---|---|
| minimax/MiniMax-M3 | 2155 | 968 | 18.2% | 正常 |
| MiniMax-M3 | 405 | 1100 | 6.2% | 正常 |
| minimax2/MiniMax-M3 | 265 | 982 | 11.7% | 正常 |
| **minimax-peer/MiniMax-M2.7** | 43 | 526 | **69.8%** | 不建议用于主分析 |

### 3.1.1 这条结论后来被自己推翻（重要，别照抄上面的判断）

按 `call_site` 查这 43 次 M2.7 到底是**哪条链路**在用：

| call_site | purpose | 次数 | 时间 |
|---|---|---|---|
| `lean_recover_a/b` | main | 20 + 9 | 2026-11-16 12:37–17:11 |
| `two_step_a/b` | main | 10 + 4 | 2026-11-16 14:16–22:43 |
| `ai_worker_main` | main | 769 | **到 2026-11-03 就停了** |
| `ai_worker_verify` | verify | 2582 | 最新 11-17 11:02（正常在跑） |

也就是说：**43 次全部落在 11-16 故障日的「空输出救回」路径上**，不是稳态主链。
而 `config.py` 里 peer 通道是 `purpose=["verify"]`、`_build_model_pool()` 只收 `purpose` 含 `main`
的通道 —— peer 本来就不进主池。所以：

- ❌「备用通道在拿 70% 的短输出兜底」→ **站不住**。
- ❌「把 M2.7 从主分析摘掉」→ **没有配置抓手**，改 `.env` 权重是空操作，还会破坏 verify 跨族共识。
- ✅ 站得住的只有一句：**这条通道在「空输出后精简两步救回」里短输出率 70%**，
  救回路径拿它当主力是可疑的；但它是从哪条分支拿到 peer 的 `model_cfg`，本轮**没定位到**
  （purpose 过滤、`_build_model_pool`、`fallback_cfgs`、`_resolve_model_cfg`、`_pick_main_model_cfg`、
  `.env`、`scripts/` 全部排除）。

所以本轮**没有改任何模型配置**，只把「短输出率」做成看板指标（抓异常用）。
「自动重试」仍然不做：同一通道重跑大概率还是短输出（账本里已有同一条新闻连续 3–4 次同样失败）。

## 3.2 队列水位：进出是否平衡、还要多久排空

只读查询（2026-11-17 11 时许）：

```
PENDING 合计 263（其中可分析 51 / 噪音滞留 212）/ PROCESSING 1
进 128.6 条·h⁻¹ → 出 117.6 条·h⁻¹ → 可分析部分排空约 0.4h → 正常消化
最老可分析 PENDING 5.5 小时
```

**这里踩了第二个坑，也记下来**：第一版把 `is_noise=0` 当过滤条件，算出 PENDING 52，
而额度看板 `quota_state.json` 同时报 `queue_pending=262` —— 两个数打架。
真相是 PENDING 里混着 212 条 `is_noise=1` 的噪音滞留行；而认领 SQL
（`ai_worker._BATCH_CLAIM_SQL`）明确写 `AND is_noise=0`，这些行**永远不会被分析**，
只会等清理脚本归档。
所以现在三个数分开报：`pending`（合计，与额度看板对齐）、`pending_actionable`（会被认领的）、
`noise_pending`（滞留噪音）。用一个数说话，无论取哪边都会误导。

**第一版口径写错过一次，记下来**：一开始用「近 N 小时有决策的 news_id 数」当消费速率，
算出来 6 条/h，于是面板报「积压在涨：进 89 > 消费 6」—— 但同一时刻 PENDING 正从 1437 掉到 260。
错因很简单：**门卫否掉的新闻也算处理完**，它们不进 `ai_decisions`，24 小时里就有 1992 条。
所以「出」必须按 `raw_news.status ∈ (DONE, FILTERED, FAILED)` 计，
「真正出决策」单独用 `decided_news_per_h` 报，两个数不混。

`raw_news` 没有完成时间戳（`processing_at` 只对 FAILED 行有值），所以出队速率是**代理值**，
字段名和文档里都标注了；PENDING=0 或出队速率为 0 → ETA 返回 `None`，不猜。

## 3.3 入口漏斗：产能其实卡在门外，不在模型

把入口拉进来一算，前面的「模型写不完八段」就不再是主因：

| 层 | 条数（近 7 天） | 占比 |
|---|---|---|
| 进来（is_noise=0） | 10370 | 100% |
| 被否掉（FILTERED） | 9481 | **91.4%** |
| 进分析（DONE + PROCESSING） | 786 | 7.6% |
| 出决策新闻（news_id 去重） | 356 | 3.4% |
| 方向性决策 | 6 | 0.06% |

再按「谁否的」拆，才看见真正的问题：

| 分层 | 条数 | 含义 |
|---|---|---|
| 门卫有判定后否（`gate_unavailable=0`） | 4794 | 真正的过滤，属设计内 |
| **门卫不可用·降级放行后仍被否（=2）** | **4687** | 门卫没判定，降级放行走了但照样被否，等于白丢 |
| **门卫不可用·仍出了决策（=2）** | **439** | 决策缺 `gate_context`，质量要打问号 |
| 冻结待回放（=1） | 1 | 等 `replay_deferred_gate.py` 补判 |
| 门卫判「可交易」却被否 | 134 | 最可疑，优先抽样 |
| 被否但门卫给了标的 | 778 | 有明确对象却整条丢弃 |

`gate_unavailable` 的语义在 `db.py` 写得很清楚：0 正常判定 / 1 冻结待回放 / 2 鉴权失效·额度耗尽→降级放行。

### 3.3.1 抽样复核结果（这一节把上面的说法打掉一半，别只看结论）

**（1）「门卫判可交易却被否」134 条 = 旧行为，已经不再发生**

按天看：11-11 有 14 条、11-16 有 86 条、11-17 有 33 条，**最后一条是 11-17 05:47:01**。
而引擎进程是 **11-17 08:27:22** 起的。也就是说 v408 的修复
（`_expire_sql` 里 `keep_tradeable` —— 门卫判「可交易」的行不归档）**从重启起生效，
重启后 5 小时零新增**。这条漏点算关掉了，134 条属历史。

**（2）「近一半流量没有门卫判定」= 11-16 事故遗留，不是当前现象**

按小时看今天的 `gate_unavailable=2`：00–04 时全 0，05–11 时各 0~1 条。
真正集中的只有 **11-16 23 点那一档（40 条里 29 条）**。
所以 4683 条是那几天门卫通道打满时的存量，今天门卫基本是好的。
上一版把它写成「近一半流量没判定」，是把历史存量当成了持续现象 —— 修正。

**（3）但这 4683 条确实是彻底丢失，而且不是小数目**

按天拆（全部 `status='FILTERED' AND gate_unavailable=2`，且查 `ai_decisions` 确认**无一有决策**）：

| 日期 | 蒸发条数 | 有决策的 |
|---|---|---|
| 11-10 | 177 | 0 |
| 11-11 | 159 | 0 |
| 11-12 | 309 | 0 |
| **11-13** | **1538** | 0 |
| 11-14 | 1031 | 0 |
| 11-15 | 566 | 0 |
| 11-16 | 902 | 3 |
| 11-17 | 1 | 0 |
| 合计 | **4683** | 3 |

其中 **4405 条 `retry_count=0`** —— 从没失败过，也基本等于从没被分析过。

**根因（读代码得到，非推测）**：门卫不可用 → 写 `gate_unavailable=1` 冻结 →
30 分钟后 `_GATE_FREEZE_TTL_S` 到点自动「放行」→ 标记被改成 **2** →
但放行只是改了标记，行还在 PENDING 队尾；积压时排不到它 →
`ts` 超过时效门槛 → `_expire_stale_news` 归档成 FILTERED →
**`filter_reason` 写的是 `stale_expired`，语义上等于「超龄」，而不是「门卫没判过、也没人分析过」**。

对比当前指标：近 7 天真正进分析的只有 786 条，而这批悄悄蒸发了 4683 条 ——
**产能最大的漏洞不在模型，在「冻结→放行→没人认领→超龄归档」这条链上。**

本轮**仍然只报数**：修它要么改归档判定（未分析的 `gate_unavailable=2` 不归档、退回队列），
要么改认领优先级（这类行插队），两者都动写链路，且当前仓库正在做目录整改（P0/P1/P2，
最新提交 `e8c4400`，`git status` 有几十个待提交文件），此时改 `ai_worker.py` 会和整改撞车。
先把数字摆在看板上，动手排在整改之后。

## 5. 口径（写死在代码里，不在前端抄第二份）

- 终态判定唯一来源：`analysis/contract.py::derive_state`（本模块不另立规则）。
- `in_scope = 全部 - out_of_scope`；所有比例字段名带分母（`complete_over_in_scope`）。
- 分母为 0 → 返回 `None`，不写 `0.0`。
- `hard_data_status` 为空 → 单列 `hard_status_unknown`，不冒充「证据不就绪」。
- 重试清单只收 `llm_failed`，且按 `news_id` 去重、排除之后已分析成功的新闻。
- `news_events` 对同一条新闻是一对多（实测 4 行），join 前先按 `news_id` 收敛，
  否则决策行会被放大 4 倍（实测 539 → 1012）。

## 6. 边界 / 未做

1. **不自动重试**。清单只是清单 —— 重跑要接 `ai_worker` 的认领队列、退避和配额，
   属写链路改动，另开版本（先量化「重跑成本 vs 救回率」）。
2. **不读绩效表**。胜率/盈亏口径只属于 `quick_sim_trades`，本页不掺。
3. **不追溯改历史**。`out_of_scope` 的 207 条不会被删也不会被改标签，只是不进分母。
4. `data_unavailable` 当前是 0：`derive_state` 只有「证据缺失且不是模型失败」才归这一类，
   现在链路在缺证据时仍会调用模型，所以失败都落到 model/parse 两桶 —— 这是链路事实，
   不是本页漏算。
