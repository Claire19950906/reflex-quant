# 门卫流量减量方案 · 2026-11-20

> 目标：门卫（gate）只做"筛垃圾"的粗过滤，不每条都上精细化 LLM 复核，把当前占调用 95%、输出 88% 的门卫流量压下来。
> 依据：`ai_call_stats` 今日实测 + `realtime_filter.py` 分层代码。所有改动分档可灰度、可回滚；未在运行中服务上直接改配置。

## 一、现状（最近 24h 实测，`ai_call_stats` + `raw_news` 漏斗）

### 1.1 token 账本：是"条数多"还是"单条文字重"？

| 用途 | 调用次数 | ok 次数 | 输入总量 | 输出总量 | 单条输入 | 单条输出 |
|---|---|---|---|---|---|---|
| **gate 门卫** | **8055** | 7994 | 2.51M | **1.78M** | 314 | 232 |
| main 主分析 | 122 | 121 | 671K | 101K | 5547 | 837 |
| verify 复核 | 130 | 105 | 107K | 31K | 1016 | 292 |
| anomaly | 450 | 0 | 0 | 0 | — | — |

- 门卫占全部调用 **92.0%**、占全部输出 **93.1%**、占全部输入 **76.4%**；调用次数是主分析的 **66 倍**。
- **单条门卫输入只有 314，比主分析（5547）轻得多**——所以流量不是"门卫把长文章读进来"烧掉的。

**门卫输出分档（看单条偏不偏长）**：

| 输出档位 | 次数 | 输出 token | 说明 |
|---|---|---|---|
| ≤100 | 3019 | 170K | 短判决 |
| 101–232 | 1516 | 247K | 中等 |
| 233–500 | 2234 | 756K | 偏长 |
| >500 | 906（11%） | **609K（34%）** | 最长一档 |
| 失败 0 token | 381 | 0 | 不计 |

- 输出 >232 的调用占 **39%，却烧掉 77% 的门卫输出**；>500 的 906 条就占 34%。

### 1.2 核心原因（定量归因）

1. **主因 · 调用条数过多（约 2/3）**：触发面是 `all`，所有非噪音新闻都上门卫；前置规则层没拦住，边界件全堆给 L3。
2. **次因 · 单条输出偏长（约 1/3）**：输出上限 800、prompt 要求四步推导，近四成调用展开成 233+ 的长回复。
3. **放大项 · 重复调用**：多源转载、熔断恢复后 replay 补判、失败重试会重复烧；标题/内容指纹只去重 43 条，缓存命中率很低。

### 1.3 是不是门卫承担了全部责任？——实质上是的

名义四层，实际武装度（24h `raw_news` 漏斗，入库 2605 条）：

| 层 | 名义职责 | 实际表现 |
|---|---|---|
| L0 池外/时效 | 本地分流、过期丢弃 | 时效过期 488、池外 1，在跑但只挡两类 |
| L1 关键词 | 垃圾/命中品种本地判 | **只拦 53 条垃圾**，词表窄 |
| L2 小模型 | 粗判信号/噪声 | **`DEEPSEEK_API_KEY` 为空 → 全部 `L2_PASSTHROUGH` 放行**，stats 无独立 L2 调用，这层基本空转 |
| L3 语义门卫 | 最后复核 | **成了第一道、也是唯一一道真做相关性/噪声判断的环节** |

- 门卫 24h 已判决 635 条：**判"排除"仅 138 条（21.7%）**，可交易 435、无信号 53。它不是在高效杀垃圾，而是对规则没拦住的海量新闻逐条精细研判。
- 其余 1938 条"未判定"是 402 熔断期冻结、待回放的件。

**一句话**：门卫被当成"主筛子"在用，而不是"最后一道复核"；L1/L2 两层架子在，但没武装，重担全压给了 L3。

### 1.4 现有分层（已在跑，先不重复造）
- L0-POOL：池外个股公告本地分流（`feeds.news_router`）。
- L0：时效检查，过期直接丢。
- L1：关键词命中 JUNK 丢 / CORE 进池。
- L2：小模型批量分类（`l2_batcher`，`_L2_BATCH_MAX_TOKENS=320`）。
- L3：语义门卫 LLM（本方案要减量的对象）。
- 已有省钱机制：标题指纹缓存、失败 180s 备忘、远程阶梯降级（单通道先上、失败才并行）、熔断跳过、预算/速率闸门。

**问题**：L1 已命中 CORE、L2 已判 SIGNAL 的新闻，仍要再走一遍 L3 精细化门卫；门卫 prompt 要求"四步挖核心影响"、输出给到 800，对一个筛垃圾的判定过重。

## 二、减量措施（按落地难度与风险分三档）

### 第一档：纯配置（改 `.env` + 重启即生效，可随时回滚）

1. **收紧门卫触发面**：`GATE_CALL_SCOPE=pool`
   - 已有代码分支（`realtime_filter.py:2452 _gate_scope_should_skip`）：只对含池内资产 / 宏观锚点的新闻上门卫；无锚点的按 `gate_unavailable=2` 放行给主分析，不伪装成门卫判过。
   - 砍掉"既无品种名、又无宏观驱动词"那批新闻的门卫调用。

2. **门卫输出压短**：`REALTIME_GATE_MAX_TOKENS=128`（保守 96）
   - 门卫只回 verdict + 品种 + 强度一句话，不再展开四步推导；直接砍输出 token 大头。

3. **缓存提效**：调大门卫标题指纹 / 内容哈希缓存的 TTL 与容量上限，多源转载、gate-replay 回放、批量补跑都零请求复用判定（当前缓存命中率仅约 1.3%）。

### 第二档：小改源码（停机窗口落地，配单测）

4. **L1-CORE 免门卫复核**
   - L1 关键词已明确命中池内品种（`verdict=CORE`），说明相关性已成立，直接 PENDING 进主分析，跳过 L3 门卫。
   - 落点：`evaluate_news` 2649 行的 L3 入口，对 `layer=="L1" && verdict=="CORE"` 直接跳过。

5. **L2-SIGNAL 高置信免复核**
   - L2 批量已判 `L2_SIGNAL` 的跳过 L3；只有 `UNCERTAIN` / `L2_PASSTHROUGH` / 低置信件才上门卫。
   - 落点：同上 L3 入口按 L2 verdict 分流。

6. **门卫 prompt 精简**
   - `_GATE_SYSTEM` 从"四步挖核心影响"压成"一句话 verdict（可交易/排除）+ 品种 + 强度 1–10"；确认请求体带 `thinking:disabled`，过滤返回里的 `<think>` 段。

7. **门卫输入裁剪**：只传标题 + 正文前 150 字摘要，不传长正文，降单次输入。

### 第三档：结构性（需先评估内存与通道）

8. **本地小模型兜门卫**：Ollama 装一个 3B 级模型，`GATE_LOCAL_FIRST=1`，门卫先走免费本地，远程只兜底；门卫远程消耗可趋近 0。受 8GB 内存约束，本地模型只做门卫、不做深挖。
9. **L2 走免费/本地通道**，把远程 LLM 门卫只留给规则层拿不准的边界件。
10. **L1 垃圾词表扩面**：招聘 / 广告 / 赛事 / 八卦 / 个股公告 / 旧闻转载等常见垃圾补进 junk 词表，微秒层直接拦下，不进 L2/L3。

## 三、预期收益（粗估，上线后用埋点实测校准）

| 档位 | 门卫调用量 | 门卫输出 | 说明 |
|---|---|---|---|
| 第一档 | 降 30–50% | 随 max_tokens 下调明显下降 | 无锚点件跳过 + 输出压短 |
| 第二档 | 再砍一半以上 | 同步下降 | CORE / SIGNAL 免复核 |
| 合计目标 | **gate 流量降到当前 1/3–1/2** | — | 远程 LLM 只服务边界件 |

## 四、风险与保护

- **少一层复核的代价**：边缘噪声可能多放行进主分析；主分析本身有判定兜底，不会直接变信号。
- **fail-open 不销毁**：通道不可用时沿用 v322 语义——不当噪音丢弃、留库等回放，不出现"零信号且不可恢复"。
- **可灰度**：先只开第一档配置，观察门卫调用量与信号质量，再上第二档源码改动；每档独立可回滚（env 改回 `all`、源码回退）。
- **不建议直接全关门卫**：会让噪声直接灌进主分析，主分析 LLM 调用反而涨，得不偿失。

## 五、验证口径（上线后对比 `ai_call_stats`）

1. `purpose=gate` 的 calls / tokens_in / tokens_out / 单次均值，前后对比；
2. 信号质量：每日 signal 数、BUY/SELL 分布、主分析判 NONE 的占比，不应明显恶化；
3. PENDING 消化速度：门卫减量后队列是否更顺，而非积压上涨。
