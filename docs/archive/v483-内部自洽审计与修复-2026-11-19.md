# 第二轮（v484）：暂停契约硬化

## 为什么要再来一轮

v483 把暂停写进了文档、watchdog 和 service-guard，但 17:14–17:29 之间又被绕过三次：
pytest 截断 `ai_decisions`、摘掉两道探针触发器、引擎被外部 `restart_backend.sh` 两次拉起。
结论：**"暂停"此前只是约定，没有一个所有路径都必须经过的开关。**

## 四处硬化

| # | 位置 | 改动 | 为什么 |
|---|---|---|---|
| H1 | `db.get_connection()` | `TRIDENT_BLOCK_PROD_WRITE=1` 且目标是生产库时替换为 `_ProdWriteGuardConnection`，写语句抛 `OperationalError` | 测试进程的守卫罩不住 shell 出去的子进程，而事故正是子进程写库 |
| H2 | `tests/conftest.py` | `_migrate_without_probe_guards` 加 `_is_prod_conn()`（`PRAGMA database_list` 真实路径），生产库跳过并打印 `[conftest] 跳过摘触发器` | 这就是 17:14 触发器第二次被摘的直接原因 |
| H3 | `engine.py` 入口 | `DATA_PAUSED` 存在 → `[ENGINE-REFUSED]` + `SystemExit(0)` | 谁都能直接 `python engine.py`，只拦启动器拦不住 |
| H4 | `run_py_with_proxy.sh` | 暂停期非白名单脚本 `[PAUSED-SKIP]` 退出（白名单：bridge/api/守护类） | 100+ 作业和临时运行共用这一个入口，一闸覆盖所有启动路径 |

## 顺带修的语义错误（fake_data）

F11/F12 只补"降级位没置"的状态标签，但初版把它们放在 purge 前面 → 刚标记成降级的决策会立刻让引用它的成交被 F4 删掉。实测在测试夹具里会误删 `quick_sim_trades` 201。修法两条：
1. F11/F12 排除**已被成交引用**的决策（改标签的手不许碰已被使用的历史）；
2. 标记动作挪到 purge 最后一步，不参与任何删行级联。
