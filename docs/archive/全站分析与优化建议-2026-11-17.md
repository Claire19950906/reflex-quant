## 3. 优化方案（P0 先做，做完再谈策略）

### P0-1 门卫批处理 + 指纹缓存 + 规则前置

- **做什么**
  1. 门卫改**批量**：一次请求判 10–20 条（同源同类型合并），返回逐条 verdict；
  2. 按 `content_fingerprint` 做 verdict 缓存（重复新闻直接复用，24h TTL）；
  3. 高置信规则先判（关键词/来源白名单/纯数字行情快讯），只有"边界样本"才进 LLM。
- **改哪里**：`backend/src_python/realtime_filter.py`（`evaluate_news` 主入口）、`engine/ai_worker.py` 认领前的 gate 调用点。
- **验收**：`gate` 调用/新闻 ≤ **0.5**；门卫 P95 ≤ 3s；14:00 高峰不再出现 gate 调用 <50 而入库 >300 的时段。
- **收益（估）**：10.6h → **0.5h 以内**，门卫不再是瓶颈。

### P0-2 结构化输出一次成型，砍掉抢救链

- **做什么**
  1. 主分析走 `response_format=json_schema`（或厂商等价的结构化输出），把 8 个必填字段变成**解码约束**，不靠事后补；
  2. system prompt 从 17.4k 字符压到 ≤8k（`syslen=17366`、`userlen=9329`，其中「回归块/维度清单/微观结构」有重复）；
  3. `schema_fill`/`two_step`/`persist_fix` 从**默认路径**降级为**最后兜底**（同一决策最多 1 次）。
- **改哪里**：`engine/ai_worker.py`（主调用与重试策略）、prompt 组装模块、「P0-2 必填字段」校验处。
- **验收**：`main` 调用/决策 ≤ **2.0**；`schema_fill_lean+two_step+failover` 合计 < 10%；单条决策 ≤ 60s。
- **收益（估）**：同额度下产能 ×3。

### P0-3 门卫故障要「可见」，不要「归档」

- **做什么**
  1. `gate_unavailable=2` 的行不再写 `FILTERED/degraded_stale`，改为独立状态 `GATE_DOWN`（或 `PENDING` + `hold_reason='gate_down'`）；
  2. 2 小时只表示"退出建仓候选"，**不删档**：仍进新闻雷达/事件库，可回放、可审计；
  3. 看板加一格「门卫故障滞留」，与「分析完成」「噪音归档」并列；数值 >0 超 10 分钟触发告警。
- **改哪里**：`engine/ai_worker.py` 的 `_deg_sql`（v432 那段）、看板漏斗、`pipeline_guard.py` 加一条断言。
- **验收**：`filter_reason='degraded_stale'` 今日归零；`GATE_DOWN` 数与 gate 失败数对得上；关掉门卫做故障演练能看见这条计数涨。

### P0-4 `timestamp` 统一成整数 epoch

- **做什么**
  1. 全表迁移：ISO → epoch int，列类型改 `INTEGER`；
  2. 新写入只允许 epoch（采集器统一走一个 `to_epoch()`）；
  3. `pipeline_guard` 加断言：`timestamp` 非纯数字的行 = 0。
- **验收**：`select count(*) from raw_news where typeof(timestamp)<>'integer'` = 0；用 `timestamp` 算超龄与 `ts` 算结果一致。

### P1-5 通道健康与成本账本

- **anomaly**：今天 153 次全 429/529，先**停用**或换独立 key；它失败不影响主链，但白烧配额还污染指标。
- **verify**：59 次 `network_error: ValueError` 是解析 bug，改成 `status='parse_error'` 并打印原文前缀。
- **gate 错误码为空**：420 次 http_error 没有任何 code，等于不可诊断；补 `error_code`。
- **成本**：从 `ai_call_stats`（已记 tokens）按模型单价日更写 `t2_cost_ledger`；验收：0 行 → 每条调用都有成本行。

### P1-6 路由前移，别让池外标的吃分析额度

- **做什么**：认领后先做**标的解析**（`target_asset`/`asset_route`），池外（`routing_miss`/`target_none`）直接写一条轻量 HOLD（不调 `main`、不调 `verify`）。
- **验收**：`routing_miss` 决策占 main 调用 = 0；`main` 调用/决策 ≤ 1.5。
- **收益（估）**：再省 30–50% 主分析额度。

### P2-7 覆盖率口径改成「新鲜可交易」

现在 2.0% 的分母里混着大量旧闻（`degraded_stale`/`stale_expired`）。建议双口径：
- 对外：`DONE / 入库`（保留）；
- 对内看板：`45 分钟内完成分析的「可交易」条数 / 门卫判「可交易」条数`——今天 36/123 ≈ **29%**，这才是真实产能。

### P2-8 影子账本补样本

16 条、命中 8 条，且 `pre_confirm` 空。建议：日更结算 + 记录"决策前 30 分钟市场是否同向"，把那个 48.7–51.6% 的闸门增量验成可用闸。

## 附录 B · P0-0「长事务锁库」结案（2026-11-17 19:20–19:45）

**结论：不是设计缺陷，是「引擎跑着旧代码」。**

| 时刻 | 事实 |
|---|---|
| 19:22–19:28 | 引擎每批都报 `Batch persist 失败: NameError: name 'analysis_degraded_reason' is not defined`，决策一行没落，行被退 PENDING + 冷却 15 分钟 → 「待分析」只增不减 |
| 19:20 起 | 写锁探针（`scripts/lock_probe.py`，只 `BEGIN IMMEDIATE` 后 ROLLBACK）实测**连续 138 秒一次都抢不到锁**，和「dirty 迁移被挡 23 分钟」是同一件事 |
| 根因 | 引擎进程 18:52 启动时加载的是 **18:26 的文件快照**（`[BUILD] ai_worker.py=8e0b02dc@18:26:38`）；磁盘上的文件 19:16 已被改成「逐条 commit + 变量名修正」，进程内存里还是旧的：整批一个事务、事务里夹 LLM 抢救 → 锁一持几分钟；外加一个未定义变量 |
| 处置 | 重启引擎（42824 → 43623）、api（43629）、bridge（43651），加载磁盘最新代码 |
| 验证 | 重启后：`Batch persist 失败` 计数停在 4 不再增长；批次 19:38:25 `5/6 ok wall=294s` 正常落库；30 分钟内新决策 14 条；写锁探针 100 秒**零次被挡** |

**新增（永久留痕）**：`db.py` 长事务哨兵 —— 任何连接的第一条写语句开始计时，
`commit/rollback` 时若事务跨度 > 5 秒，就往 `/tmp/trident_txn_profile.log` 记一行
（pid + 首个写类型 + 调用栈）。以后再有「谁锁了库」，日志自己会说是谁。
环境变量：`TRIDENT_TXN_PROFILE=0` 可关，`TRIDENT_TXN_SLOW_S` 调阈值。

**教训（写进流程）**：改完 `ai_worker.py` / `db.py` 必须重启对应服务；
引擎日志开头的 `[BUILD] xxx.py=<hash>@<时间>` 就是它到底在跑哪版代码的唯一凭证。

## 附录 H · 锁看门狗上线 + 积压消化实测（2026-11-17 22:00–22:10，v439）

### H2 做法

`backend/scripts/lock_watchdog.py`（新增）

| 项 | 值 |
|---|---|
| 探测动作 | 每 30s 发一次 `BEGIN IMMEDIATE`（超时 2s），抢到立刻 `ROLLBACK`，**零写入** |

- HTTP 内层 `for attempt in range(3)` → `range(_HTTP_RETRIES)`，`REALTIME_GATE_HTTP_RETRIES=2`。
- 最坏耗时 64s → **50s**，成功率从"三连全灭"变成"一次命中"。

实测（重启后 20 分钟）：`purpose=gate` **ok 163 / http_error 21**（成功率 **88.6%**），
`[GATE] MISS` 从 23 点每小时 19 条降到重启后 0 条。

### L4 改动二：回放让位闸（`engine/gate_replay_guard.py`）
深夜只有 2 条新新闻，却记录 **90 次** gate 调用（约每 20 秒一次），来源是回放在补判历史"未判定"新闻：
`50 条/轮 × 300s` ≈ **14,400 次/天**，而门卫日预算只有 **6,000**、全站 **9,000**
—— 回放会一路把额度烧到零，之后新新闻的门卫请求被闸门直接拒 → 又是全员"未判定"。
新增闸门：`usage_by_purpose("gate")` 用量 ≥ `GATE_REPLAY_RESERVE_PCT`（默认 60%）即跳过本轮。

实测（当天门卫已用 5,886/6,000）：

```
[gate-replay] 跳过（通道不可用）：回放让位：门卫今日已用 5886/6000 次（≥60%），额度优先留给实时新闻
```

| 参数 | 值 | 说明 |
|---|---|---|
| `REALTIME_GATE_TIMEOUT_S` | 25 | 覆盖 95 分位（实测最长 31.7s 属尾部） |
| `REALTIME_GATE_HTTP_RETRIES` | 2 | 最坏 50s（原 64s 且几乎全失败） |

## 附录 M（v444）：日预算口径 bug —— 闸门等于没有闸门

### M1 症状
门卫日预算设的是 6,000，但今天实际打了 **5,985** 次也没被拦住；
同时全站预算（`llm_budget`）却报"已用 6,044/6,000 用尽"。
**两个账本对不上** —— 一个说还有额度，一个说早就超了。

### M2 根因：`start of day` 是 UTC 的零点，不是本地零点
```sql
-- 旧写法（错）
strftime('%s','now','start of day','localtime')
```
SQLite 的修饰符是**从左到右**执行：先 `'start of day'`（在 **UTC** 上取零点），
再 `'localtime'` 把结果**当成 UTC 再转本地** → 边界落在**本地 08:00**（跨天后甚至落在昨天 16:00）。

实测同一时刻两种口径：

| 口径 | 当日门卫调用数 | 边界 |
|---|---|---|
| 旧（错） | **1,535** | 2026-11-17 16:00 |
| 新（对） | **5,968** | 2026-11-17 00:00 |

少算 **4,435 次（74%）**→ 预算闸门一直以为"还有额度"→ 门卫一路打到把全站预算烧干，
之后新新闻的门卫请求被真闸门拒掉 → 全员"未判定"。**这就是今天 R6 的底层原因之一。**

```sql
-- 新写法（对）：先转本地时间，再取本地零点，最后转回 UTC epoch
strftime('%s','now','localtime','start of day','utc')
```

### M3 改动
| 文件 | 位置 | 内容 |
|---|---|---|
| `realtime_filter.py` | `_gate_budget_used_today()` | SQL 改新口径 + 函数注释写明坑 |
| `engine/ai_worker.py` | 主分析日预算 `AI_MAIN_DAILY_BUDGET` | 同一处旧口径一并修正 |

`llm_budget.py` 用 Python `time.mktime` 算本地零点，**本来就是对的** —— 所以只有这两个闸错，
形成"两边打架"。

### M4 验收
- 单测 `tests/test_v444_day_boundary.py`（5 项：新口径必须落本地零点、旧口径必须不等价、
  源码里不许再出现旧 SQL）。与 v433/门卫用例合跑 **37 passed**。
- 跨天实测（00:07）：门卫 `66/6000`，`llm_budget` 报 `gate 66` —— **两个账本一致**；
  回放自动恢复（`[gate-replay] #35058 ok verdict=可交易`），门卫调用 7–12s 全部成功。

### M5 一句话
预算闸门不是逻辑错，是**算日界算错了 8 小时**。修完之后，门卫才真正受 6,000 次/天的约束，
配合附录 L 的"回放让位"，额度才会按设计分给实时新闻。
