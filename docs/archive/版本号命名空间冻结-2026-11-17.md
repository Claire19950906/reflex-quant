# 版本号命名空间冻结（P3 第一步，2026-11-17）

## 先说结论

版本号前缀**一条都不能合并**。原因不是懒，是查过了：

- 运行中的路由表里，版本号前缀端点 **79 条**，分布在 8 个前缀（v1 / v186 / v187 / v188 / v189 / v190 / v201 / v275）。
- 把 `/api/vNNN/xxx` 的版本号抹掉，变成 `/api/xxx`，看能不能和新路径对上：**79 条里只有 1 条对上**（`/api/v188/reflection/stats` → `/api/reflection/stats`）。
- 这唯一一条也不是重复：`v188` 版返回 layer/signal 分布，新版返回错误码分布，两个接口名同而实不同。
- 其余 78 条是**版本独有的真实功能**，没有新路径可转发。所以「老路径转发新路径」这个方案在这里走不通 —— 没有新路径。

再加 bridge_server 那侧（8100 自己也挂了一批版本端点），全仓版本号前缀端点 **106 条**，前缀多出 v237 和 v291。

## 所以做的是「冻结 + 护栏」，不是硬删

删不掉的东西，最合理的处置是**不让它继续长大**：

1. **基线落盘**：`backend/reports/baseline/legacy_namespaces.json` 记录当前每个前缀的条数。
2. **CI 红灯**：新增一个版本号前缀、或往老前缀里加端点 → `legacy_namespace_audit.py` 退出码 1。
   - 新端点一律走领域路径（`/api/<域>/<动作>`），不许再开 vXXX。
3. **顺手修真判重口径**：只按路径判重会把 GET/POST、PUT/DELETE 误报成重复。
   实测那 13 条「重复」里 **12 条是同路径不同方法**，真重复只有 `/api/security/watermark` 一条（已删死代码那份，见 `67e17c1`）。
   现在脚本按「路径 + 方法」判，并且区分两种重复：
   - **同一 app 内真重复**（后注册的那份永远匹配不到 = 死代码）→ 报 FAIL，必须删；
   - **跨 server 重叠**（8000/8100 各一份）→ 报 INFO，属 P1 已知范围，bridge 侧优先转发 8000。

## 六、别名层：老路径不删，规范名同时存在（2026-11-17 晚）

判定过「79 条剥掉版本号后能对上已有路径的只有 1 条，且语义不同」——所以**不做合并、不搬家**，
改为新增一层别名：每条 `/api/vNNN/xxx` 在路由表里多注册一份 `/api/xxx`，指向**同一个 endpoint 对象**。

| 项 | 数 | 说明 |
|---|---|---|
| 8000 版本化端点 | 79 | 全部保留（冻结基线，只减不增） |
| 8000 新增规范别名 | 74 | 4 条是蜜罐（`/api/v1/_debug`、`_internal/strategy`、`_internal/weights`、`_test/connection`），不别名；1 条（`/api/v188/reflection/stats`）规范路径已被真实实现占用，保留真实实现 |
| 8100 版本化端点 | 106 | = 8000 的 79 + 桥接自有 27 |
| 8100 新增规范别名 | 27 | 自有那 27 条；8000 那批在 api_server 里已经别过，挂载时带过来 |
| 前端调用点改写 | 25 + 69 处 / 24 个文件 | `/v291/stats` → `/stats` 之类，`fallback` 名单同步改名 |

实现只有一处代码：`backend/src_python/legacy_alias.py` 的
`add_canonical_aliases(app)`——遍历 `APIRoute`，去掉版本号后插一条指向同一 endpoint 的
`APIRoute`（**插在原路由之后**，所以一定排在 8100 末尾的 `/api/{full_path:path}` catch-all 之前），
默认 `include_in_schema=False`（避免同一操作在 /docs 里出现两次、operationId 冲突）。

已验证（`tests/test_legacy_alias.py`，6 条）：

* 每条版本化端点都有规范名，且**指向同一个 endpoint 对象**（不是抄一份新实现）；
* 4 条蜜罐路径没有被别名注册；
* 老路径仍在路由表里（79 条 / 106 条不变）；
* 8100 的别名全部排在 catch-all 之前。

接口对拍（TestClient，改造前后两次取响应）：

* 8100 自有 27 对无参数别名：状态码 **27/27 一致**；
* 8000 的 67 对无参数别名：62 对整段一致，4 对只有**数据内容随采样时间变**（`us5y`、`llm-stats/summary`、`lsr/ranking`、`trade-points`），字段结构完全一致；
* 1 对 `_debug` 蜜罐：老路径 404（蜜罐拦截）、规范名 403（同 IP 已被标记）——**故意不别名**。

顺带修的两个真问题：

1. `frontend/lib/api.ts` 的 `FALLBACK_PATHS` 缺 `/crypto/lsr/latest` —— lsr 面板打的是 8100 独有路径，8000 一 404 面板就空着，补进名单；
2. 零引用统计口径：`/api/stats` 这类短路径用 `text.count` 会把 `/decision/stats` 一起算进去，
   改成带前后边界的正则（`architecture_baseline.py::_count_refs`），并把版本号老路径的引用
   记到它的规范名上。重算后零引用 **100**（旧口径 140 偏低，是子串命中造成的）。

上线后实测（两台服务都 `launchctl kickstart -k` 重启过，启动日志确认「[api] 74 条 / [bridge] 27 条」）：
