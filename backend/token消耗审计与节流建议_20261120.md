### 1. 门卫 gate（最大漏钱口，历史已多次治理）
- 每条入库新闻先过门卫判"可交易 / 噪声"，今日约 1593 条新闻 → 3155 次门卫，**约 2 次/条**（阶梯兜底重试）。
- 历史实测（11-04）：门卫曾 4278 次 / 3.68M token，占全天 40%；当时每条新闻 7.26 次。现已改：本地优先、远程阶梯降级（先单通道、失败才并行）、内容哈希缓存、标题指纹缓存、熔断跳过、预算/速率闸门。
- 剩余问题：
  - 单次输出 **201 tokens**，对二分类偏长；MiniMax 是 reasoning 模型，即使下发 `thinking:disabled` 仍偶发输出 `<think>` 段（代码 1373 行注释已记录），思考段挤占输出额度。
  - 缓存命中率仅 1.3%，重复/转载/回放新闻仍重复付费。
  - 本地兜底模型未装（Ollama 无模型、`LOCAL_LLM_ENABLED=0`），门卫全部走远程付费通道。

## 四、节流建议（按性价比，均待停机窗口落地）

1. **门卫输出压短**：确认 gate 通道 `thinking:disabled` 真正生效，max_tokens 收到 64–128，过滤返回里的 `<think>` 段 —— 直接砍 633K 输出大头。
2. **提高门卫缓存复用**：放宽标题指纹/内容哈希缓存的 TTL 与容量，覆盖多源转载与 gate-replay 回放，把重复门卫调用降到 0 请求。
3. **本地小模型兜门卫**：Ollama 拉一个 3B 级小模型，`GATE_LOCAL_FIRST` 先走免费本地，远程只兜底 —— 门卫远程消耗可趋近 0（受 8GB 内存约束，只做门卫不做深挖）。
4. **主分析上下文裁剪**：按事件相关性动态注入段落，砍掉低相关的历史/图谱段，降单次 5.9K 输入。
5. **peer 复核降级**：失败率 43%，缩短超时、挂掉的通道快速摘除，避免长等。

## 五、关于"多少 G 够"

- **不是内存（GB）问题**：Trident 后端实测 RSS —— bridge 0.17GB、engine 0.16GB、ollama 0.03GB，后端合计不到 0.5GB，8GB 机器跑后端够用。系统内存压力来自外部应用（DoubaoWork / Chrome / VideoFusion 等），不是 Trident 吃内存。
- **真正受限的是 LLM 套餐 tokens**：当前节奏全天约 2.8–3.2M tokens。需要么给 MiniMax 充值/升到能覆盖该用量的套餐，要么接一条独立备用通道分散配额；本地 15M 的 token 预算上限不是瓶颈。
