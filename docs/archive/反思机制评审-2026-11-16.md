### 1.2 现在就能落地的三件事

这三件不需要等样本，今天就能对外交付：

1. **审计日志**：每笔决策有 `decision_errors` + 完整 reasoning_path + 结算结果，

### 1.3 还不能落地的部分（必须写清楚）

> "Reflex Quant 提供逐笔可复核的决策审计与失败归因；交易边际尚在验证中，当前不构成收益承诺。"

## 二、反思机制的七个结构性问题（+1 条复核新发现）

每条按「现象 → 证据 → 影响 → 建议」写。**证据行号以本文写作时的代码为准，重构后会漂移，请按函数名检索。**

### R1 · 推理层只覆盖 0.6% 的样本（最致命）

- **现象**：7 层反思中的 3 个层（`check_causal`、`check_event_logic`、`check_reasoning_logic`）
  都在函数开头对 HOLD 直接 return。
- **证据**：`reflection_checkers.py:430 / 936 / 1207` 三处 `if action not in ("BUY","SELL"): return`。
  结果：当日 3 条方向性决策中 2 条还是降级兜底 → **推理层实际审查对象 = 1 条**。
  `decision_errors` 近两日 51 条里，E003、E014–E017、E021–E027 **全部为 0**。
- **影响**：所谓"33 码 / 7 层"在运行时是空的。对外讲"每笔都被 7 层审过"是站不住的：
  HOLD 才是 99.4% 的主体，而它们被跳过。
- **建议**：
  1. HOLD **也要审，但审的是另一组问题**——"该动没动"（漏单）而不是"推理错"。
     现在 `missed_signal_reflection.py` 有这个方向，但没接进主循环。
  2. 把反思覆盖率做成显式指标：`被审决策数 / 有效判断数`，低于阈值就在看板报警，
     别再让它悄悄变成 0.6%。

### R2 · 它是事后审计，不是事前闸门（表述必须改）

- **现象**：README 写"先把每个信号审一遍，再决定信不信"。代码里没有这条路径。
- **证据**：`run_all_checkers` 的四个调用点（`run_reflection.py:113`、`api_server.py:11752/11962`、
  `review_agent.py:2099`、`paper_reflection_worker.py:470`）**都是读已落库的决策行**；
  `api_server.py:11837` 的注释自己写明"只读决策行 + 可选连接"。
  真正的事前否决是 `decision_guard.evaluate_decision` + risk_manager，与反思层无关。
- **影响**：这不是缺陷，是**定位错误**。懂行的投资人/交易台第一个问题就会问穿，
  而一处表述失真会连带否定掉整套"诚实"叙事，性价比极低。
- **建议**：统一为"**事前：独立闸门 + prompt 自检；事后：逐笔审计 + 归因**"。
  如果确实想要事中拦截，路径是"把 E00x 的判定阈值前移进 gate"，那是另一个工程，不要混讲。

### R3 · 反思语料与错误码体系脱钩，且被基础设施噪音淹没

- **现象**：605 条反思里，`error_signal` 为空的有 **602 条**；分类型上 499 条是 `data_feed_timeout`。
- **证据**：`subcategory` 分布：data_feed_timeout 499、pattern_recognition 86、其余 20 条合计。
  `error_signal` 仅 3 条有值（entered_too_late 2、sentiment_vs_market 1）。
  维度上 C（技术故障）507 / A 88 / B 10。`hit=1` 全库仅 1 条。
- **影响**：反思命中率的分母里 82% 是"喂数断了"，分子几乎为 0 → 指标恒等于 0，
  看起来像"反思没用"，实际是"反思在给断线做记录"。
- **建议**：
  1. **物理隔离**：C 类不写 `trade_reflections_v2`，改走独立 `infra_incidents` 表；
     反思命中率分母只留 A/B。v399 已在接口层拆 `n_reasoning/n_infra`，但产线仍在往同表灌。
  2. **强制绑定错误码**：一条 A/B 反思必须带 `error_signal`（E0xx），否则视为脏数据不入库。
     当前 602 条空值说明这条约束根本没落地。
  3. **修完结算口径要回填反思表**：见下方 R3-b，这是本轮复核最刺眼的一条。

#### R3-b（新发现）· 唯一的 `hit=1` 是坏结算，不是好反思

- **事实**：全库只有 1 条 `hit=1`（`trade_reflections_v2.id=95789`，decision 11816，WTI SELL，
  入场 88.483、**出场 86.42**、`pnl_pct=+2.0315%`）。同一决策在 `quick_sim_trades.id=260` 里是
  **出场 88.335、`-0.1327%`、LOSS**。
- **根因**：86.42 正是 `v396-结算取价口径` 认定的日线兜底污染价（WTI 1m 断档 + `ORDER BY ts ASC`
  取到 11-11 的收盘）。v396 修了**结算器**（`quick_sim_trades` 已是 88.335 / LOSS），
  但**没有任何工具回填反思表**：仓库里唯一的清理脚本 `fix_polluted_outcome_pct.py` 处理的是
  2026-10-26 那批 `actual_outcome_pct`，且文件头明确"只动结算行（`paper_run_id IS NULL`）"，
  而 95789 恰好是 `paper_run_id=2` 的 paper worker 行 —— **制度性地被跳过**。
- **含义**：也就是说——**反思系统至今没有任何一次"真的命中"**。它能显示的 100% 命中率为 0，
  唯一的 1 次是 bug。对任何"命中率/胜率"类叙事，这是必须先修的硬伤，否则一被抽查就爆。
- **建议**：把 v396 的口径修正同步回填到反思表（`pnl_pct`、`hit`、`actual_outcome_pct` 三列），
  并把回填做成幂等脚本挂进 `reflection-enrich` 调度；同时在反思表加 `settle_source` 字段，
  记录该行用的是哪个价（tick / 1m / daily_fallback），让"污染"可事后识别。

### R4 · 闭环只转了半圈，且只在单一信号上空转

- **现象**：`reflection_cycles` 已有 **105 条**产出，但 `finding_kind` **105/105 全部是 `no_baseline_new`**
  （"无历史基线，无法判定"）；且 105 条的 `parent_layer/parent_signal` **全部是同一个**
  `analysis/missed_signal`；下游 `policy_patch_queue` 是 **0 行**。
- **证据**：
  - `SELECT parent_layer, parent_signal, finding_kind, COUNT(*) FROM reflection_cycles GROUP BY 1,2,3`
    → 只有一行：`analysis/missed_signal | missed_signal | no_baseline_new | 105`，`DISTINCT parent_signal = 1`。
  - 时间分布不规律：11-16 的 13:10 / 13:13 / 13:14 / 13:15 / 13:16 / 13:46 各一批，末条 **13:46** 后停止。
    这不是定时器的节拍，是**手工或临时脚本反复触发**的痕迹。
  - **调度事实需要更正**（上一版只查了仓库，结论偏了）：反思类任务其实有 4 个 launchd 在跑——
    `com.trident.reflection-enrich-cron`、`reflection-verify`、`tech-reflections-cron`、`weekly_reflection`
    （定义在 `~/Library/LaunchAgents` + `~/.trident/wrappers`，**不在仓库里**）。
    但在这 4 个 wrapper 和全部 plist 中检索 `meta_reflection_loop` / `policy_updater` = **0**。
    即：**元反思与策略补丁没有任何定时调度，只有 `api_server.py:19257` 的 HTTP 端点**。
- **影响**：这是最值得警惕的一种"闭环假象"——第一环在转（反思→cycle），但产出物 100% 是"不能判定"，
  而且只盯着"漏单"一个信号；第二环（finding→补丁→策略）从未启动。
  仪表盘有了，油门上没有接线，仪表盘显示的读数是"没有读数"。
- **建议**：
  1. **先修 finding 质量**：`no_baseline_new` 不该落库成"finding"。它是"数据不足"的占位，
     应写成 `insufficient_data` 计数（或干脆不写），否则 cycle 数会长期给人"系统在自省"的错觉。
  2. **扩大分组再谈深度**：当前只审 `missed_signal` 一组，等于用元反思解决漏单，方向是对的，
     但 A/B 类的其它信号（`entered_too_late`、`news_direction_inverted`、`pattern_recognition`）
     一条都没进过元反思。先把分组覆盖做全，再谈 level 2。
  3. 把 `reflection_policy_updater` 挂进 `reflection-enrich` 或新增每日任务，产出候选进队列；
  4. 保留 `status='pending'` 人工审（这是安全设计，别改自动 apply），但补两个机制：
     90 天自动 `expired`（代码已有 `expire_old_patches`，没跑）+ 队列积压告警；
  5. 在 `/api` 暴露"候选数 / 已审数 / 已 apply 数 / 生效后指标变化"，否则无法证明闭环存在。

### R5 · 元反思的统计基础不成立

- **现象**：`MIN_SAMPLES_FOR_META = 5` 数的是**反思条数**，不是**独立成交笔数**；
  win_rate 用 `pnl_pct > 0.005` 判定。
- **证据**：`meta_reflection_loop.py:50 / 79`。全局已结算成交 3 笔，而 `reflection_cycles` 有 105 条，
  **全部被判为 `no_baseline_new`，且全部集中在 `missed_signal` 一组**。
  这已经不是"分组切太细"，而是**连基线都构不出来**：对比窗口里同组凑不够 5 条，
  于是既没有 confirmed 也没有 invalidated——105 次运行，0 次判断。
- **影响**：元反思目前**没有下过任何一个实质判断**。如果继续按"reflect 越多越深"的方向投入，
  得到的是越来越多的 `no_baseline_new`，而不是越来越多的洞察。
- **建议**：准入条件改成 **组内 ≥5 笔"已结算且独立"的成交**（不是反思行），
  不满足就**不产出 finding**（宁可不说话）。同时把 `hit` 与结算绑定：
  没有 `trade_uuid` 或未结算的反思，不参与任何 rate 计算。

### R6 · 部分错误码可被 prompt 刷分，测的是"模板合规"

- **现象**：E021（假设未明示）、E022（反事实未考虑）都是**关键词存在性检查**；
  E030（假二择一）、E031（循环论证，Jaccard≥0.5）是表层文本特征。
- **证据**：`reflection_checkers.py:623–635` 关键词表（"假设/前提/如果"、"反之/否则/反例"）；
  而 `ai_worker` 的 prompt 本就强制输出 `[逻辑自检]` 段与"反向预案"（4486–4501、4312）。
  也就是说：**模型只要按模板写，这些码就永远不会触发**——它们测的是"有没有按模板写"，
  不是"写的东西对不对"。
- **影响**：这组码制造了"低错误率"的错觉，同时无法区分"合规且正确"与"合规但错误"。
- **建议**：
  1. 把 E021/E022/E030/E031 标为 `soft`（不计入推理质量分，只做文风提示）；
  2. 真正想测"反事实质量"，应该比对**结构化字段**：`invalidation_condition` 是否存在、
     是否与 `hard_data_evidence` 的具体数值挂钩、是否与最终方向一致（三问，可机器判）；
  3. 这类检查放在生成阶段（prompt 里的自检）比放在事后更有效，事后只留"抽查"。

### R7 · 33 个码没有边际价值度量

- **现象**：没有任何指标回答"加了 E0xx 之后，胜率/回撤/错单率改善了多少"。
- **证据**：全库没有 `code → 拦截 → 结果` 的对照表；`decision_errors` 里能持续触发的只有
  E001a（28 条，缺硬数据，这是**真在拦**的）、E028/E030/E032（文本层）。
- **影响**：码的数量成了叙事资产而非能力资产，且每加一个码都在增加维护面与误报面。
- **建议**：建一张"码有效性台账"（`code`、触发数、其中被后续证明为真错的占比、
  对应成交的胜率差、最近一次有效时间），长期无改善的码降级为 `info` 或下线。
  **下线一个码和新增一个码应该同等光荣。**

## 三、优化方案（按可执行度分层）

### A. 立即改（当天，零风险）

1. **换产能指标**：看板删掉"决策数/日"，改报三个数：
   `有效判断数（degraded=0 且非 HOLD）` / `反思覆盖率` / `已结算笔数`。
2. **改对外表述**：R2 的那句"先审再决定信不信"改成"事前闸门 + 事后逐笔审计"。
3. **语料隔离**：C 类停止写入 `trade_reflections_v2`（或写入时强制 `dimension='C'` 且不进 rate 分母），
   同步修正 `hit_rate` 的分母口径。
4. **回填污染行**（新增，来自 R3-b）：把 v396 修正后的结算价同步回写反思表的
   `pnl_pct / hit / actual_outcome_pct`；回填后"真实命中数"应为 **0**，别再留着那条 +2.03%。
5. **`hit` 改语义**（新增，来自 §5.2）：schema 注释与所有接口文案改成 `trade_won`，
   停止用它代表"反思有效性"。
6. **置信度口径**：不用改代码（见 §5.1），等新数据自证；复查 SQL 见附录 A 第 8 条。

### B. 一周内（需要小改代码/调度）

7. **反思绑定成交**：A/B 反思必须有 `trade_uuid`，且 `settled=1` 才允许进入任何 rate；
   未结算的先挂 `pending`，不进统计。
8. **HOLD 侧补"漏单反思"**：把 `missed_signal_reflection.py` 接进主循环，
   审"该动没动"，与"动了但错"分开计分。
9. **调度落地**：`reflection_policy_updater` 进每日任务 + 90 天自动 expired + 积压告警；
   元反思也挂每日一次，接在 `reflection-enrich` 之后。
10. **元反思准入与覆盖**：`MIN_SAMPLES` 改数成交笔数；不达标不产出 finding；
    同时把元反思的分组从"只有 missed_signal"扩到 A/B 全部信号。

### C. 中期（结构性）

11. **最小可验证闭环（最重要）**：同一信号同一窗口做**对照**——
    一组带教训（prompt 注入该信号的 lesson），一组不带，比较结算胜率与均值。
    没有对照，反思永远只是解释，不能证明有用。

### 5.1 置信度：修复没坏，是没被跑到

- `confidence_availability.is_unavailable()` 只看 `confidence_detail.coverage`，`coverage<=0` 即"没算"。
  实测用一条降级样例行（`suggested_action=HOLD`、`target_asset=NONE`、空 context）跑
  `decision_guard.evaluate_decision`：`confidence=0.0`、`coverage=0.0` → `is_unavailable=True` → 应落 NULL。
- 写入点在 `engine/ai_worker.py:13160`：`None if _conf_unavailable else _evidence_confidence_pre`。
  **逻辑是对的。**
- 但按进程启动时间切分可以确认原因：
  - `created_at < 2026-11-16T21:57`：482 条，NULL 3 / **0.0 442**；
  - `created_at >= 21:57`（engine.py 与 api_server 重启之后）：**0 条**新决策。
  → 当日全部数据都是由**旧进程**写出的，新口径还没有被任何一条新决策验证过。
- **动作**：不用改代码。等下一批决策落库后复查一次（附录 A 第 8 条）；
  若新数据仍是 0.0，再查 `_process_single` 里 `_guard_pre` 是否有 `confidence_detail` 被覆盖。
- **顺带说明**：这也解释了 v399 那组数字——不是修复失效，是修复与数据不同期。
- **附注（22:10）**：库内末条决策停在 **21:05**，重启后到此刻仍无新决策落库，
  所以新口径还没有一条自证样本。若这个空窗继续拉长，需要排查引擎是否在消费新闻队列——
  这属于"落地"层面的另一个隐患：**有进程在，不等于有产出**。

### 5.2 `hit` 是"交易赢了"，不是"反思有用"（口径错位）

     与"反思有没有帮到系统"无关。0 胜 → 该指标恒为 0，是**定义决定**，不是噪音导致。
  2. 唯一的 `hit=1` 还是污染行（见 R3-b），所以连"1/605"这个数都不可信，真实值是 **0/605**。
- **动作**：
  - 把该列语义在 schema 注释里写死为 `trade_won`，避免继续被当成反思质量读；
  - 另起 `reflection_effective` 字段（由"带教训 vs 不带教训"的对照实验填），
    在拿到对照结果前保持 NULL，且不参与任何对外指标。
