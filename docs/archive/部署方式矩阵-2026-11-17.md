# 部署方式矩阵（2026-11-17）

仓库里并存 5 套部署，性质不是「重复」，而是**五个不同目标**。这份表只解决一件事：
新人（或半年后的自己）打开仓库时，知道该动哪一套、哪一套是当前正在跑的。

| # | 形态 | 描述文件 | 目标环境 | 当前是否在用 | 备注 |
|---|---|---|---|---|---|
| 1 | macOS launchd（本机生产） | `deploy/macos/*.plist` + `~/.trident/wrappers/` | 这台 MacBook | **是**（8000 / 8100 / 9000 都在跑） | wrapper 读 `~/.trident/env` 拿代理与凭据，故不入库；plist 是镜像快照 |
| 2 | Linux systemd | `deploy/trident-{engine,api,bridge}.service` + `nginx.conf.example` | Ubuntu 22.04，`/opt/trident` | 否（备用的服务器形态） | 前端用 `npm start` + Nginx 反代 |
| 3 | Windows 三终端 | `deploy/README_windows.md` + `scripts/run_{engine,api,frontend}.bat` | Windows 10/11 | 否（备用） | 不装服务，靠三个终端 + `.bat` 自举 |
| 4 | Fly.io 容器 | `fly.toml` + `backend/Dockerfile.proxy` | 云端反代 demo | 边缘在用（`trident-proxy`，nrt 区） | 只跑代理/反爬壳，`TRIDENT_MODE=demo`，不是主链路 |
| 5 | Vercel | `vercel.json` | 前端静态头策略 | 否（仅 headers 配置） | 只定义安全响应头，不含服务端 |

## 判断口径

- **改主链路** → 只管第 1 套。api / bridge 用 `launchctl kickstart -k`，不要手工 `nohup`（会和 launchd 抢端口）。
- **改对外壳**（反爬、水印、demo 站点）→ 第 4 套，`fly deploy`。
- 第 2、3 套是「换机器时能起来」的保险，**代码改动后不必同步维护**，但每季度至少要能 `systemd-analyze verify` / 手工起一次，否则等于没有。
- 第 5 套只改安全头，改前端部署方式时才碰。

## 已知的不一致（别被误导）

- `deploy/README.md` 里写的是第 2 套（Linux），而本机实际跑的是第 1 套；两套端口一致（8000 对外、8100 完整版、前端 3000），但路径不同（`/opt/trident` vs `~/Desktop/金融1.0`）。
- `scripts/com.trident.engine.plist` 与 `deploy/macos/com.trident.engine.plist` 内容一致，是同一种东西的两个副本；新增服务时优先放 `deploy/macos/`。
- 本机 `~/Library/LaunchAgents/` 下有 126 个 plist（大量 cron 型），仓库只镜像了 3 个常驻服务，其余 cron 属于运维脚本层，不按部署形态管理。
