## 2. ① 标的别名层

### 2.1 它解决什么

模型只能从固定枚举里挑标的（`XAU|XAG|WTI|BTC|ETH|SOL|CN_STOCK|US_STOCK|HK_STOCK|
INDIVIDUAL_STOCK|SKHYNIX|NONE`），而新闻写的是「金价」「油价」「英伟达」「SK海力士」。
模型挑不出来时写 `NONE`，这条决策就变成 `routing_miss` —— 不可能变成交易。

### 2.2 实现

- `backend/src_python/target_resolver.py`：33 个 canonical 标的、约 110 个别名（中英混写）。
  - ASCII 别名走**词边界**匹配（`mu` 不会命中 `must`/`music`，这条专门写了测试）；
  - 中文别名走子串匹配；
  - 一条新闻同时提「黄金」「原油」→ 两个都返回，是否只用第一个由调用方决定。
- `backend/src_python/routers/targets.py`：
  - `GET /api/targets/unresolved?days=7`：捞 `routing_miss` + `unclassified_events(pending)`
    的原文，去重后跑解析，按品种聚合成榜；每条给"为什么会被漏"的一句话。
  - `GET /api/targets/aliases`：当前生效的别名表（默认表 + 覆盖文件合并）。
  - `POST /api/targets/aliases`：往 `backend/config/target_aliases.json` 追加别名（原子写）。

### 2.3 实测

```
扫描 307 条 / 能认出品种 65 条 / 上限救回率 21.17%
NVDA 23  · AMZN 11 · US_STOCK 9 · EUR 5 · TSLA 5 · JPY 5 · GOOGL 3 · CNY 3 · HK_STOCK 3
认不出任何品种 242 条（样本：住宅建筑商情绪、空管现代化拨款、伊朗袭击 —— 确实没有标的）
```

**注意口径**：`recover_rate_upper` 是**上限**，只代表"原文出现了品种词"，不代表这条新闻值得交易。
真闭环还需要模型复核一遍 —— 这一步没做，也不该由这个只读功能偷偷做。

## 3. ② 信号可执行卡片

### 3.1 它解决什么

系统每天在写"BUY/SELL + 一段理由"，但"能不能做、做多少、错了在哪停"没有任何接口回答。
用户看到的是一行结论，落到执行全靠脑补。

### 3.2 算法（全部可复算）

- 入场价：`kline_bars` 最新收盘（日线优先，退 4h/1h/15m）；
- 波动：ATR(14)，`TR = max(H-L, |H-PC|, |L-PC|)`；**不足 15 根就返回 None**，改用 2% 兜底并标 `estimated=true`；
- 止损：`1.5 × ATR`（可调 `atr_mult`）；
- 仓位：风险平价 —— `仓位% = 单笔风险% / 止损距离%`（默认 1%，上限 100%）；
- 目标：1R / 2R / 3R；
- 失效：`blocking` 里列出算不出的原因、K 线过期（日线 >48h）。

### 3.3 实测

```
近 3 天方向性决策 72 条 → 同向去重后 13 张卡（折叠 59 条重复）→ 可执行 11 张
WTI SELL 止损 3.52% 仓位 28.44%   ETH SELL 止损 10.24% 仓位 9.76%
XAU BUY  止损 2.81% 仓位 35.55%   BTC SELL 止损 7.08%  仓位 14.13%
```

聚合标的没有自己的 K 线（库里只有 26 个 symbol），所以 `US_STOCK` 用 `SPX`、
`HK_STOCK` 用 `TENCENT` 做**代理**，卡片上明确标 `proxy`，不让人误以为那是"美股的价格"。

## 4. ③ 源健康看板

### 4.1 它解决什么

`sources/status` 只有 online/error/stale 三态，分不清「没配 key」「三天前停更」「能出但一半失败」。
于是"新闻变少了"只能靠感觉。

### 4.2 分类与打分

| 分类 | 判据 | 建议 |
|---|---|---|
| healthy | 24h 有量、失败率 <50% | 正常 |
| flaky | 24h 有量但失败率 ≥50%（≥5 次样本） | 降频率/退避，仍不好换备源 |
| stalled | 24h 0 条、7 天有量 | 查上游改版/限流 |
| dead | 7 天 0 条且报错 | 停用或换源 |
| not_enabled | access_state 属 needs_key / premium_tier 等 | 申请 key 或标"已放弃" |
| no_data | 注册了但从未入库 | 解析没接上或源本身没内容 |

分数 = 100 − 失败率×50 − 闲置×30（48h 封顶）− 无 24h 量×20 − error×20，夹到 0–100。
**注册表是内存态**（CLI 里读出来是空的），所以允许只用 DB 侧算 —— 这条也有测试。

### 4.3 实测

```
49 源 / 近24h 活跃 37 / 入库 2854 / top3 占 57% / 分类：healthy 37 · stalled 10 · no_data 2
停更点名：eastmoney_ann（7天 26 条，96.2h 没动）、fed_press（4 条，90.9h）
```

### 4.4 边界（写清楚，别让人误会）

「接口返回 200 但 items 为空」这种源侧故障，**从库里看不出来**。本面板只对「有没有真的入库」负责；
接口层的空返回用 `site_audit.py` 的 `empty` 分类看。两条路分开，避免又一次"看着绿其实坏"。

### 6.1 前端发布踩到的坑（值得记一笔）

生产包用的是 `NEXT_DIST_DIR=.next-prod`（`run_frontend.sh` 里写死），`npm run build` 默认写 `.next` ——
**构建成功但页面仍然 404**，因为服务读的是另一个目录。第一次就是这么被绕进去的。

另外官方脚本 `rebuild_frontend.sh` 有资源闸（free≥700MB 且 load≤12），当时**负载 222**、free 135MB，
被直接跳过（这是 11-16 那次"构建把三个服务打崩"的教训留下的保护，不该拆）。
本次做法：构建到 `.next-prod.new` → 成功后再 `mv` 切换，旧包留成 `.next-prod.old2` 可回滚；
构建自动改写的 `tsconfig.json`（加了 `.next-prod.new/types`）已还原。

## 7. 没做 / 下一步

1. **没有把别名命中回灌成决策** —— 那会改决策链，需要你点头。现在的链路是"先看榜单 → 你确认别名 → 再决定要不要重跑"。
2. **`routing_miss` 的真根因有两层**：一层是枚举太窄（本功能治这个），另一层是 prompt 里 `target_asset`
   必须从枚举选；要彻底解决得改 prompt 允许"给具体 ticker"，属于决策链改动，未做。
3. 可执行卡片的仓位是**风险平价机械口径**，没有考虑相关性/组合层面风险；多张卡同时开仓会叠加风险敞口，这一点页面已注明。
4. 源健康没有做"自动降级"（自动禁用/切备源）—— 需要写采集层配置，且要有误杀保护，留待你决定。
