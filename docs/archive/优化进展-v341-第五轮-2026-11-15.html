五、写锁：找到了被误判的真因

快讯脚本明明设了 busy_timeout=20000，锁错误却立即返回。真因是 读事务升级成写事务：SELECT 已开启读事务，随后 INSERT 要升级， 而别的进程刚提交过写 → SQLite 直接返回 SQLITE_BUSY，busy handler 在这条路上不生效。

修法：db_retry.py 提供自动提交连接 + 退避重试（2s / 4s / 6s）， 两个快讯脚本已改走它。

另外三个高频报错点（宏观日历 FF、K 线影响、AI 调用统计）经查 早就有重试，日志里的失败是"重试耗尽后的真丢失"，属突发窗口过长，要继续降只能缩小事务粒度。

但继续往下挖，找到了一处真正的代码缺陷（不是"拥挤"，是这个写法本身就必炸）

真丢数据最多的 tencent_quotes（24h 放弃 188 次）走的是 external_data.ingest_external。它的写法是：

  • 连接用默认隔离级别；
  • 先 SELECT 1 ... WHERE asset=? AND indicator=? AND ts=? 查重 → 这一步已经开启了一个读事务；
  • 紧接着 INSERT 需要把这个读事务升级成写事务；
  • 只要别的进程刚提交过写，SQLite 立刻返回 SQLITE_BUSY —— 而且 busy_timeout 在这里完全不生效（busy handler 只处理"拿不到锁"，不处理快照升级冲突）。

所以每条行情都是"必炸"的，PRAGMA busy_timeout=30000 形同虚设。修法：

改法说明
isolation_level=None每条语句自带事务，不再有"读事务升级"这条路
INSERT 走 db_retry.insert_with_retry真撞上别人才退避重试（按实测的密集快试节奏）
