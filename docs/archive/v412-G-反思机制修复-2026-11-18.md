### 那个 95.9% 为什么是假的
修之前统计的 146 条"可验证"样本里，137 条是「HOLD → pnl 为空 → 判技术错误 → 当日库内有行情 → 判验证」。这是个自我循环：**用"你没有结算"去证明"你判断错了"，再用"当天有行情"证明"这个判断成立"**，转一圈永远是成立。它测的不是反思质量，是结算链路有没有数据。

### 39.7% 才是真话
| 层级 | 条数 | 占比 | 验证 | 否证 | 不可分离 |
|---|---|---|---|---|---|
| 无明显错误 | 83 | 56.1% | 0 | 0 | 81 |
| 信息方向错误 | 56 | 37.8% | 22 | 32 | 2 |
| 买卖判断失误 | 9 | 6.1% | 3 | 6 | 0 |

合计 148 条，一致率 39.7%（n=63）。**56 条"漏掉有效移动"里有 32 条被独立测量否证**——说明反思把"方向错"当成了通用理由，归因准确度是当前最该改的地方。

### `reflection_effective` 的口径（写死在脚本注释里）
- `1` = 这条反思**判的错因被独立测量证实**，不是"这条反思让交易赚了钱"
- `0` = 反思自己判错了
- `NULL` = 判不了（`不可分离`/`不适用`）——**绝不当 0 使用**

### 两个必须记下来的坑（都是我自己踩的）

1. **取价新鲜度**：第一版用"`ts<=目标时间` 的最近一根 tick"当出场价，取到了陈旧价，18 条 `move=0.0000%`，命中率被算成 34.5%。已改为双向 ±30 分钟窗口，取不到就判 `no_exit_price` 作废。
2. **假 tick**：即使窗口正确，仍有 11 条 4 小时变化恰好 0.0000%（等待时间 235–248 分钟都正常），说明数据源把同一个价反复写进不同 `ts`。已加 `FLAT_PCT=0.01` 判 `flat_price_suspect` 剔除。

> 结论：**34.5% 那个数是假的**（假 tick 压低了命中率），干净样本是 55.6%。两次修正都记在脚本注释里。

## 十一、P3：新闻准入（prefilter 范围前置过滤）

### 为什么要做

848 条 HOLD 里 648 条是「分析降级」，而 `out_of_scope` 一侧最能省：**343 条判越界**的决策里，**234/341（69%）闸门其实已经识别出资产**（黄金/原油/美股），是决策层按 prompt 指令又写了 NONE。改 prompt 风险高（明令「无传导就 NONE」），所以改走**入口拦**——不让越界新闻进分析队列。

### `analysis/route.py` 两个判据 bug（本轮修）

| bug | 现象 | 修法 |
|---|---|---|
| 顺序错 | 「桶标签判定」排在「正文别名检查」之前 → 正文明写「比特币/白银」也被整条丢掉 | 把 `_find_alias(news_text)` 提到桶判定之前 |
| 词表窄 | 别名表只认品种、不认宏观传导（美联储/战争/制裁/OPEC），这类源头被丢 | 新增 `_MACRO_HINTS` 20 个词，命中且无核心别名 → `adjacent/text_macro`（**仍然进分析**） |

**实测（14 天全量 18,851 条）**

| 指标 | 修前 | 修后 |
|---|---|---|
| 误杀（判越界但正文含核心/宏观词） | 126 条 | **2 条**（0.01%） |
| `out_of_scope` 合计 | — | 3,451 条（18.3%） |

修后分布：`unknown/no_evidence` 8,454、`adjacent/text_macro` 2,500、`core/text_core` 2,489、`out_of_scope/bucket` 1,929、`out_of_scope/stock_hints` 1,517、`adjacent/text_adjacent` 771、`core/gate_core` 640、`core/gate_class_word` 380、`core/gate_assets_core` 153。

### prefilter 的三重故障链（**它从上线起一条都没过滤过**）

打开开关之后仍然零过滤，逐层剥出来三个独立故障：

| # | 故障 | 后果 |
|---|---|---|
| 1 | 历史 `[PREFILTER] 跳过（ImportError: cannot import name 'os' from 'signals'）` | v406 期间整段被跳过 |
| 2 | 引擎连接**没设 `row_factory`**，`UPDATE ... RETURNING *` 返回**元组**；`_get()` 只捕获 `(IndexError, KeyError)`，`row["content"]` 抛 **TypeError** → `judge()` 的 `except Exception` 兜成 `judge_error` → **全部判 keep** | 静默全放行，且不报错 |
| 3 | `enabled()` 默认 `"0"` | 即使代码对，也压根不进这个分支 |

**证据**：19,838 条 `FILTERED` 里 `filter_reason like 'prefilter_scope%'` = **0**；`grep -c PREFILTER engine.out.log` 只有 1 条（就是那条 ImportError）。而且拿 357 条 PENDING 重跑 route：**178 条该丢（50%）却一条没丢** —— 池子不干净，是过滤器没工作。

### 修法

| 位置 | 改动 |
|---|---|
| `prefilter._get()` | dict → `get`；其余 `row[key]` 用 `except Exception` 兜住（元组不再炸） |
| `prefilter._row_id()` | dict → `row["id"]`；否则先 `row["id"]` 再回落 `row[0]`（`RETURNING *` 第一列就是 id） |
| `prefilter.apply()` | **不再从 row 读字段**，改为按 id 回查 `raw_news` 取 `content/gate_main_asset/gate_assets/gate_kind` 再交给 `judge`。批只有几十条，多的几十个 SELECT 可接受，换来「判据真被执行」 |
| `prefilter.enabled()` | 默认 `"0"` → `"1"`，docstring 写明抽查依据与保留 `ANALYSIS_PREFILTER=0` 开关 |

## 十二、这一轮最贵的一课：**开关打开 ≠ 功能在跑**

同一件事上连踩两次：

1. `reflection_effective` 全 NULL —— 以为「字段在」，其实没有任何地方写；
2. prefilter —— 以为「开关打开就生效」，其实因为**行是元组**，判据每次都在异常里被吞掉，跑了几周、过滤 0 条、连一行报错都没有。

共同点：**故障被 `except Exception` 静默吞掉**，而且统计口径（`filter_reason` 计数）本身是「过滤器自己写的」，所以「看起来正常」和「根本没跑」长得一模一样。

以后验证「某个机制是否生效」，一律看**它自己产生的副作用计数**（`prefilter_scope%` = 0 就是没跑），而不是看开关值、不看日志里有没有报错。日志里「没有报错」在 `except Exception` 面前等于「什么都没发生」。
